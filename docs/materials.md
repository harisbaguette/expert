# 재료 55개

[목표 문서로](../전문가%20에이전트%20정의.md)

## 쓰는 법

재료는 능력을 실행할 기능과 책임의 목록이다. 개수와 폴더 모양은 합격 조건이 아니다. 각 업무에서 필요한 기능을 고르고, 입력·출력 계약과 검증 증거로 구현 여부를 확인한다. 공통 규칙은 [실행과 데이터](runtime.md), 최종 성과 판정은 [평가와 대체 판정](evaluation.md)에 둔다.

재료 상태는 `id`, `applicability`, `activation_condition`, `condition_dependencies`, `dependencies`, `implementation_status`, `reason`, `owner`, `evidence`로 관리한다. 적용 여부는 required·conditional·not_applicable, 구현 상태는 planned·implemented·verified다. not_applicable의 구현 상태는 null이다. condition_dependencies는 조건 확인에 필요한 진단·관측의 의존, dependencies는 본 실행의 의존이다. 조건부 기능이 켜지면 해당 경로에서는 필수이며 의존 재료도 함께 확인한다.

### 재료의 적용 구분

구성 전개식과 재료 표는 재료를 **상시·단계별·조건부**로 구분한다. 아래 각 재료의 「적용 구분·시점」이 분류의 정본이며, 그림은 이 값을 읽어 표시한다.

| 구분 | 뜻 |
|---|---|
| 상시 | 모든 업무의 진행 전반에서 유지·적용하는 책임. 매 순간 도구를 호출하거나 같은 검사를 반복한다는 뜻은 아니다 |
| 단계별 | 모든 업무의 접수·자료 확인·계획·검증·납품 등 해당 단계에서 수행하는 책임. 보통 그 단계에서 처리하고, 자료·전제·결과가 바뀌면 다시 수행한다 |
| 조건부 | 업무 특성이나 진행 중 상황에 따라 필요한 기능. 해당 조건이 충족되면 필수이며, 활성화에 필요한 의존도 함께 갖춘다 |

이는 개별 업무의 적용 여부(required·conditional·not_applicable)나 구현 상태와 다른 구분이다. 상시·단계별은 각 업무에 책임을 배정하고, 조건부는 업무별로 활성 조건을 판단한다. 조건이 불명이면 확인 경로를 남긴다. 조건부 계약·회사 규칙도 일단 적용되면 유효한 동안 계속 지켜야 한다. 사용하지 않는 기능과 반드시 갖춰야 하는 판정·대체·검증 경로를 구별한다. 단계별을 ‘최초 1회만 확인하고 다시 보지 않음’으로 구현하지 않는다.

### 직무별 조립

공통 정의를 재사용하고 **직무 정의와 개별 위임 조건을 적용**한다. 여러 전문 분야가 필요한 업무는 정의를 함께 연결하되, 충돌을 마지막 값으로 덮어쓰지 않는다. 아래는 새 재료가 아니라 기존 재료를 채우는 공통 형식이다.

| 직무 정의에서 채울 것 | 담당 재료 |
|---|---|
| 세부 업무·대상·난도·관할·목표·권한·외부 의존 | M17·M27·M31·M33·M36·M39 |
| 핵심 객체·관계·방법·질문·판단 지점·예외·숙련 사례 | M18·M21·M22·M25·M34·M35 |
| 입력·산출·행동·전문 도구·작업 환경·재사용 자산 | M07·M09·M10·M52·M53·M54·M55 |
| 상대·채널·언어·관계·설명·교육·협상·개입 | M08·M23·M38 |
| 조건부 기능·의존·대체 경로·공동 작업·전환·복구 | M02·M03·M04·M25·M35·M41·M50 |
| 완료·인수·허용 결론·실패 기준·성과·비교 평가 | M36·M40·M42–M49·M51 |

기능 선택은 직무명이나 파일 확장자만으로 정하지 않는다. 실제 요구·작업·환경으로 적용을 판단하고 필요한 재료·자산·도구·외부 수행의 의존을 빠짐없이 연결한다. 조건을 모르면 미적용으로 넘기지 않고 확인할 정보와 해당 경로의 대기를 남긴다. 새 사실·요구·권한·환경 변경 때 관련 선택을 다시 계산한다.

계통은 재료의 주된 출력과 책임으로 구분한다. 구현 도구·저장 위치·호출 시점이나 다른 계통에서 그 결과를 사용한다는 이유로 소속을 바꾸지 않는다. 한 책임은 한 재료가 소유한다. M21은 업무 방법, M22는 숙련 선택, M35는 이번 업무의 설계·순서, M55는 재사용 자산, M09는 제작, M10은 실행 환경, M40은 인수다. 코드·파일은 공유할 수 있으나 같은 내용을 여러 정본에 복사하지 않는다. 기존 책임으로 표현할 수 없는 입출력·판정이 확인될 때만 재료 추가를 검토한다.

[조립 계약](runtime.md#직무-조립-계약)에 따라 누락·충돌·의존과 조건별 경로가 정리되면 정의가 완성된다. 재료의 구현·실증 상태와 실제 전문가 대체 판정은 별도로 관리한다.

계통별 재료 수는 환경 9, 자료·검색 11, 지식·경험 2, 기억·상태 2, 규칙·권한 9, 행동 체계 5, 실무 7, 검증·평가 8, 학습·개선 2로 합계 55개다.

모델 공급자의 기능·캐시·가격은 어댑터와 기술 결정 기록에서 관리한다. 모든 모델이 같은 캐시 구분점·수명·추론 설정을 가진다고 가정하지 않는다. 추론 강도를 건마다 또는 단계마다 고정할지는 실제 품질과 캐시 동작으로 결정한다.

실시간 통로에서 검색이 필요하면 비동기로 조회하고 불확실성을 드러낸다. 만남 전 자료만 보도록 고정해 새 사실에 대응할 수 없게 만들지 않는다. 되돌릴 수 없는 약속은 사전 위임의 범위 안에서만 하며, 범위 밖이면 확인 뒤 답할 시간을 확보한다.

## 자료·검색 — 근거·업무 자산 확보

판단 근거와 재사용 업무 자산을 확보·읽기·관리·조회하는 체계다. 원본의 내용·구조와 출처·판본·권리·호환성을 제공하고, 이를 가공하거나 사용해 업무 결과를 만드는 일은 실무에 연결한다.

## 연결 확인

각 업무의 기능 연결은 입력 → 해석 → 판단 → 권한 → 실행 → 외부 확인 → 결과와 후속 성과로 이어져야 한다. 재료마다 담당 모듈 또는 외부 서비스와 증거 참조를 붙여 누락된 연결을 찾는다. 모듈 이름이 재료 이름과 다르다는 이유로 실패시키지 않는다.

공통 재료도 업무별 검증은 필요하다. 예를 들어 저장 기능 코드는 같아도 기한·보존·기억의 의미가 다르고, 모델은 같아도 필요한 판단 능력과 데이터 이동 조건이 달라진다. 둘째 직무에 그대로 적용할 수 있는지는 실측으로 결정한다.

## 전문 작업의 연결

요구·설계 명세(M35·M36) → 자료·구조 읽기(M07)·업무 자산(M55) → 필요한 데이터 처리(M52)·계산(M53)·실험(M54)·제작(M09) → 대상별 검증(M42·M46) → 납품·인수(M40)로 잇는다. 전 과정의 실행 환경은 M10, 상태·변경 영향은 M25, 새로운 기능 확보는 M50이 맡는다. 파일 없는 거래·서비스 운영은 M10의 외부 상태와 M36·M51의 성과로 끝을 확인한다.

각 기능은 형식·프로그램/버전·작업 종류·환경별 지원·미지원·미검증 조건과 증거를 가진다. 구현 상태(planned·implemented·verified)와 실제 지원 범위는 구별한다. 새 능력은 기존 시험의 통과만으로 인정하지 않는다. 공통 입출력 계약은 [실행과 데이터](runtime.md#전문-작업과-산출물-계약), 대상별 인수 시험은 [평가 규약](evaluation.md#전문-작업의-평가-범위)을 따른다.

## 복합 업무의 연결

사건·당사자·쟁점·증거·가설의 상태(M18·M25)에서 통합 전략(M34)을 세우고, 조건부 계획(M35)을 공동 작업(M04)으로 실행한다. 당사자별 권한·정보 경계(M27·M31·M32)와 결합 손실(M33·M53·M54)을 전 과정에 적용한다. 상대 반응(M38)·새 관측·검증(M43)으로 전략을 갱신하며, 현실에서 확보하지 못한 증거와 전문 개입(M39)을 완료 판정에서 숨기지 않는다.

55개는 기능의 개수다. 업무별 연결·상태·제약과 실제 실행 증거가 있어야 해당 범위의 능력을 주장할 수 있다. 세부 계약은 [복합 업무의 상태·전략·협력](runtime.md#복합-업무의-상태전략협력), 직무별 업무 검토는 [166개 직무 검토](reviews/occupation-work-review.md)를 따른다.
