# 파일·폴더 구조안 자기 비판

**초안은 자료를 어디에 나눠 둘지는 설명했지만, 합친 결과의 권한·재처리 결과의 보존·복구 때 따를 최신 기록을 충분히 정하지 못했다. 그대로 구현하면 폴더는 깔끔해도 자료가 새거나 근거가 바뀔 수 있었다. 아래 결함을 구조안에 반영해 고쳤다.**

2026-10-22. 대상은 [파일·폴더 구조안](../../../파일-폴더-구조.md)이다. 작성자가 초안을 만든 뒤 직접 반례를 대입한 자기 검토다. 다른 모델이나 독립 검토자가 심사한 결과가 아니다. 실제 제품 실행·권한 공격·장애 복원 시험도 아니다.

## 1. 읽은 범위와 검토 기준

- [정의 1](<../../../전문가 에이전트 정의 1.md>)의 처음부터 끝까지 읽었다. 읽기 시작 때 고정한 사본은 4,563줄이고 SHA-256은 `06c1c45e2046aa93df724904e9fef2004999df2d6cc76b0f1b70829a086391af`이다.
- 이어진 원본 변경도 대조했다. 구조안 작성 중 확인한 추가분은 삽화 링크와 빈 줄이며 기존 본문 변경은 없었다. 원문 파일은 이 작업에서 수정하지 않았다.
- 기존 278줄의 구조안, [공장 구현 설계](<../../../공장 구현 설계.md>), 프로젝트 지도에 남은 ‘코드 배치보다 지식·원본 보관이 중심’이라는 범위를 함께 확인했다.
- 현재 획득 프로젝트의 폴더·파일 존재와 원본·지식 README를 확인했다. README의 구현 주장은 실제 실행으로 다시 검증한 결과와 구분했다.
- 1차 초안은 381줄, SHA-256 `bb379d96c71e0e377a62fd95a51e2b423e921520364bcb857fdb60cccbf5d20f`이다. 아래 ‘초안 줄’은 수정 전 이 판본을 가리킨다.

검토 기준은 요구 누락, 정본 중복, 권한 경계, 중단·변경·복원, 기존 자료 이관, 사람의 탐색 부담이다. 79개 이름을 표에 적었다고 79개 구현이 검증됐다고 보지는 않았다.

## 2. 초안에 대한 비판과 수정

‘중대’는 그대로 구현할 때 노출·근거 손실·잘못된 복원을 만들 수 있는 설계 결함이다. ‘보완’은 배치·관리 판단을 구현자에게 다시 떠넘긴 부분이다. 모두 문서 수정이며 구현 결함을 실제 고쳤다는 뜻은 아니다.

### C01 · 중대 — 읽을 권한만 확인하고 합친 결과의 권한은 비워 뒀다

초안 73줄은 “DB에서 각 참조를 검사한다”고 썼다. 두 자료를 각각 읽을 수 있다는 사실과 그 둘을 합친 요약을 같은 사람들에게 공개할 수 있다는 사실은 다르다. 공통 법령과 비공개 계약을 합친 해설이 공통 분야 지식으로 올라갈 수 있었다.

**수정:** 모든 입력의 사용 제한을 결과가 이어받도록 했다. 허용 열람자의 교집합과 보존·삭제 조건을 검사하고 맞는 범위가 없으면 보호 범위를 만들거나 작업을 나눈다. 대화·임베딩·캐시·납품까지 같은 규칙을 적용한다. [반영: 구조안 3절](../../../파일-폴더-구조.md#3-운영-저장소의-목표-구조)

### C02 · 중대 — 같은 처리법이면 같은 결과가 나온다는 경로였다

초안 46·53줄의 `derived/<source-version>/<recipe-id>/`에는 재실행 결과를 구분하는 자리가 없었다. 같은 원문·모델·설정으로 OCR이나 추출을 다시 해도 결과가 달라질 수 있다. 기존 경로에 덮어쓰면 과거 판단이 실제로 읽은 내용을 잃는다.

**수정:** `result-id`를 추가하고 확정 결과를 불변으로 보관한다. 채택 결과는 DB가 가리키고 판단은 결과 ID·해시에 연결한다. 여러 원문을 합친 산출물은 입력 집합을 별도로 연결한다. [반영: 구조안 6절](../../../파일-폴더-구조.md#6-이름id판본접수-규칙)

### C03 · 중대 — ‘최신 삭제 이력을 복원한다’고만 쓰고 최신의 기준은 없었다

초안 30·256·260줄은 보호 상태를 따로 보존하고 재적용하라고 했다. 그런데 업무 DB와 보호 폴더 중 어느 쪽이 기준인지, 기록 도중 멈췄을 때 어떻게 맞출지 없었다. 둘 다 과거 사본이면 삭제한 자료가 다시 나타난다.

**수정:** 보호 이력의 용도별 위치, 인증한 단일 변경 경로, 사건 ID·증가 순번, DB 적용 순번, 처리 중 차단과 실패 재처리를 명시했다. 최신성을 확인하지 못하면 접근을 열지 않게 했다. 보호 이력도 별도 장애 영역에 보존하도록 하고 암호화 백업의 키 복구 경로를 추가했다. [반영: 구조안 11절](../../../파일-폴더-구조.md#11-용량삭제백업복원)

### C04 · 중대 — 폴더 격리를 강조했지만 누가 무엇을 쓸지는 모호했다

초안 33·186줄에 OS 권한·마운트 원칙은 있었지만 주체별 변경 권한은 없었다. 180줄의 ‘실행자는 출력·임시 경로만 쓴다’와 182줄의 ‘SDK는 지속 대화를 저장한다’도 쓰기 대상이 구분되지 않았다. 같은 계정이 전체 저장소를 읽거나 DB 우회 권한을 받으면 트리가 무의미해진다.

**수정:** 등록·확정, 도구, SDK, 업무 관리, 평가, 운영 담당의 쓰기 범위를 표로 정했다. 업무 DB 계정과 소유자·`BYPASSRLS` 계정을 분리하고 고객·범위 소속을 참조에서도 검사한다. SDK의 기록 쓰기와 도구 출력 쓰기를 구분했다. 감사 증거와 샘플링 가능한 운영 로그의 역할도 나눴다. [반영: 구조안 5절](../../../파일-폴더-구조.md#5-무엇을-db에-두고-무엇을-파일에-두는가), [8절](../../../파일-폴더-구조.md#8-업무-한-건의-작업대화외부-행동)

### C05 · 보완 — 독립적으로 바꿔야 할 지식을 프로그램 판본 안에 묶었다

초안 213–217줄은 프로그램 배포 폴더 안에 지식과 전문가 구성을 함께 넣었다. 배포 묶음으로는 가능하지만, 실무서만 고쳐도 프로그램 전체를 새로 만들거나 복제하는 방식으로 구현될 여지가 있었다.

**수정:** `applications/`, `knowledge/`, `experts/`, `components/`의 판본을 독립적으로 두고 실행 당시 조합과 호환 결과를 DB에 기록한다. 고객 전용 구성도 공용 설치 트리 밖으로 명시했다. [반영: 구조안 10절](../../../파일-폴더-구조.md#10-설치-판본과-업데이트)

### C06 · 보완 — 설정 파일과 DB 사이의 변경 책임을 다 쓰지 않았다

초안 40–42줄은 위치·보존·수집 설정을 YAML에 두고 123줄은 자료·보존 상태를 DB에 뒀다. 둘의 역할을 아는 작성자에게만 분명한 설명이었다. 구현자는 같은 값을 양쪽에서 갱신하거나 파일 수정 시각을 현재 상태로 쓸 수 있었다.

**수정:** 설정은 검사·판본 관리하는 입력, 수집·용량·권한·삭제 처리 상태는 DB의 운영 기록으로 구분했다. 실행에 적용한 설정 판본을 연결하도록 했다. [반영: 구조안 5절](../../../파일-폴더-구조.md#5-무엇을-db에-두고-무엇을-파일에-두는가)

### C07 · 보완 — 목록 파일의 이름은 있었지만 최소 계약이 부족했다

초안 56·65·200·214줄에는 스냅샷과 여러 `manifest.json`·`release.json`이 있었다. 납품 목록 외에는 자료의 소속·스키마 판본·생성 주체·입력·검사 연결을 어디까지 공통으로 넣을지 없었다. 이름이 같은 JSON 파일끼리 호환될 것으로 오해할 수 있었다.

**수정:** 목록의 용도와 함께 스키마 판본·ID·범위·생성 시각·주체·자료 판본·해시·입력·검사 참조의 공통 항목을 정했다. 상세 JSON Schema와 실제 생성·읽기 함수는 구현 단계의 일로 남겼다. [반영: 구조안 6절](../../../파일-폴더-구조.md#6-이름id판본접수-규칙)

### C08 · 보완 — 기존 폴더를 찾고도 구체적인 이관 연결표가 없었다

초안 268–277줄은 현재 위치를 확인했지만 283–289줄의 단계는 일반적인 순서에 머물렀다. 기존 `knowledge/domains/`, `professions/`, `cases/` 중 무엇을 작성 원본·운영 지식·시험 자료로 보낼지 구현자가 다시 조사해야 했다.

**수정:** 현재 위치별 목표와 판별 조건을 추가했다. 범위를 모르는 자료를 공용으로 올리지 않고, 실행 중 DB를 파일 이동으로 이전하지 않으며, 예전 시험 자료를 새 독립 시험으로 취급하지 않게 했다. 파일별 실제 분류는 전수 목록 작성 때 수행한다. [반영: 구조안 13절](../../../파일-폴더-구조.md#13-실제-적용-순서와-확인할-결과)

### C09 · 보완 — 저장 기계에는 편하지만 사람이 찾는 방법이 약했다

초안 150줄은 제목을 DB에 보관하고 내려받을 때 표시한다고 했다. 그러나 독자가 평소 어디에서 법률·분야 지식·고객 결과물을 찾는지는 설명하지 않았다. 해시 경로만 제시하면 파일 정리의 부담을 사용자에게 넘기는 셈이다.

**수정:** 관리 화면에서 공통 자료·분야·고객 업무로 탐색하는 경로와 표시할 이름·판본·사용 가능 상태를 적었다. 사람이 보는 분류를 추가해도 실제 원본을 복제하지 않도록 했다. 새 화면을 이번에 구현한 것은 아니다. [반영: 구조안 3절](../../../파일-폴더-구조.md#3-운영-저장소의-목표-구조)

## 3. 고친 뒤에도 남는 한계

| 남는 일 | 왜 문서만으로 끝낼 수 없는가 | 다음에 필요한 증거 |
|---|---|---|
| 실제 자료 전수 분류·용량·사용 조건 | 폴더와 README만으로 각 파일의 성격·보존 의무를 확정할 수 없음 | ID·해시·크기·권한·참조가 있는 목록과 이관 대상 표 |
| OS별 권한·마운트·세션 복구 | 경로 설계가 실행 계정의 실제 접근 차단을 증명하지 않음 | 다른 고객·같은 고객의 다른 범위·평가 정답 접근 실패, 허용 작업 성공 |
| DB 구조와 검색 범위 분리 | 테이블·파티션·색인 수·실제 부하에 따라 비용과 성능이 달라짐 | 범위별 격리·검색 품질·성능·재색인 공간 측정 |
| 보호 이력·DB·파일의 장애 처리 | 여러 저장 대상을 한 트랜잭션으로 만들 수 없음 | 단계별 강제 중단 후 최신 차단 재적용과 누락·잘못 공개 방지 |
| 5분 손실·1시간 복구 | 원본·모델·WAL·색인·키를 실제로 복원해 보지 않음 | 장비 장애를 가정한 격리 복원과 시간·해시·중복 행동 검증 |

이 한계는 문서를 한 번 더 길게 써서 해결할 문제가 아니다. 첫 구현에서 **고객 둘, 같은 고객 안의 범위 둘, 업무 한 건, 중간 장애 한 번**을 실제로 통과시키며 확인해야 한다. 그 전에는 이 구조안을 ‘보관·이관 기준’으로 사용하고 ‘운영 가능 증명’으로 사용하지 않는다.

## 4. 이번 작업에서 확인한 것

- 원문 재료 1–79의 번호·이름과 구조안 대응표를 프로그램으로 비교했다. 누락·중복·이름 불일치 없이 일치했다.
- 최종 구조안과 이 기록의 로컬 링크·문서 내부 절 연결, 코드 블록과 표 구조를 확인했다. 기계 검사 기록은 [검증 기록](파일-폴더-구조-검증-2026-10-22.json)에 남겼다.
- 실제 자료 이동·삭제·DB 변경·서비스 실행은 하지 않았다. 기존 코드 성능·보안·백업·전문 능력 시험은 미실시다.

**판정: 초안의 중대 4건과 보완 5건을 문서에 수정했다. 현재 구조안은 다음 구현의 배치·보관 기준으로 사용할 수 있다. 실제 운영의 안전성과 복구 능력은 아직 검증되지 않았다.**
