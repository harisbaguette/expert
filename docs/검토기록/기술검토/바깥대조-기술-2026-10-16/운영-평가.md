# 운영 감시, 실행 기록, 평가에 쓸 기술을 오늘 기준으로 다시 확인한 결과 (2026-10-16)

`재료 별 구현.md`에서 고른 기술을 2026-10-16 기준 최신 버전, 유지 상태, 사용 허가, 사내 설치 가능 여부로 다시 확인하고 같은 일을 하는 대안과 견줬다. 대상은 `사용량 모으기`, `운영 감시와 복구`, `업무 능력 시험`, `장치마다 효과 재기`에 적힌 기술이다. 공격 시험은 문서에 제품 이름이 없어 후보를 새로 골랐다.

후보는 다섯 기준을 차례로 걸러 골랐다.
1. 세 환경(한 사람의 PC, 사내 서버, 사내 서버와 DGX Spark) 모두 사내에 설치할 수 있다.
2. 바깥 서비스가 끊겨도 일이 멈추지 않는다.
3. 공개된 성능 평가가 있으면 점수가 가장 높다.
4. 같은 일을 하는 부품을 이미 쓰고 있으면 그것을 쓴다.
5. 부품 수가 적다.

## 1. 생존 신호 확인과 경보

**확인한 사실**
- Prometheus v3.15.0(2026-09-25), 함께 지원하는 버전 v3.13.4(2026-10-02). Apache-2.0. 지난 6개월 동안 커밋 1,499건, 작성자 180명.
- Alertmanager v0.34.1(2026-09-17). Apache-2.0. 둘 다 linux-arm64 실행 파일을 낸다.
- Prometheus 공식 문서: "Alerting rules in Prometheus servers send alerts to an Alertmanager. The Alertmanager then manages those alerts, including … sending out notifications". 문서의 "Prometheus가 신호가 끊기면 경보한다"는 Alertmanager가 있어야 성립한다.
- "A Prometheus server cannot evaluate its own alert rules while it is stopped." 감시하는 Prometheus가 죽으면 그 위의 경보 규칙도 함께 멈춘다. 흔히 쓰는 해법은 늘 울리는 Watchdog 경보(`expr: vector(1)`)를 감시 장비 밖의 생존 신호 수신기로 보내고, 신호가 끊기면 다른 길로 알리는 방식이다.
- 생존 신호 수신기 후보: Healthchecks v4.4(2026-08-31, BSD-3), Uptime Kuma 2.5.6(2026-10-09, MIT). 둘 다 사내에 설치한다. 두 Prometheus가 서로를 감시하는 구성도 있다.

**세 환경**: 감시 장비는 실행 장비와 따로 둔 사내 리눅스 한 대다. ③의 DGX Spark는 llama.cpp에 `--metrics`를 켜면 `/metrics`를 열고("This endpoint is only accessible if `--metrics` is set."), vLLM은 `vllm:`로 시작하는 측정값을 `/metrics`로 낸다. ①의 PC는 감시 대상이 아니고 측정값을 보내는 쪽이다. 바깥에 기대는 곳은 없다.

**판정**: 유지(보완). 표의 `생존 신호 확인` 줄에 Alertmanager를 넣고, Watchdog 경보를 감시 장비 밖의 수신기가 받게 해야 문서가 말하는 동작이 실제로 성립한다.

## 2. 서버 상태와 경보: Prometheus와 Grafana

**확인한 사실**
- Grafana v13.2.4(2026-10-13). 같은 날 13.1.8, 13.0.11, 12.4.13도 나왔다. AGPL-3.0이고 지난 6개월 커밋은 6,365건이다. 회사 안에서만 쓰면 AGPL의 공개 의무가 생기지 않는다(소스를 고쳐 바깥에 서비스할 때만 해당).
- Grafana는 기본값으로 바깥에 연결한다. "When enabled Grafana sends anonymous usage statistics to stats.grafana.org"(`reporting_enabled` 기본 true), `check_for_updates`는 10분마다 GitHub에서 새 버전을 확인한다. 막혀도 Grafana는 멈추지 않지만, 회사 밖으로 나가는 연결이므로 둘 다 끈다.

**견준 대안**

## 3. 실행 시간과 오류, 사용량: OpenTelemetry

**확인한 사실**
- Collector 배포 묶음 v0.162.0(2026-09-29), contrib v0.163.0(2026-10-14). Apache-2.0. 아직 1.0 전이라 버전마다 설정 이름이 바뀔 수 있다.
- 생성형 AI 의미 규약은 "Status: Development"이고, 의미 규약 본체는 v1.44.0(2026-08-04)이다. 에이전트 단계와 모델 호출 속성의 이름이 아직 바뀔 수 있다.
- Claude Code는 측정값과 이벤트(로그)를 OTLP로 내보내고, 추적은 베타다("Tracing is off by default."). `-p`로 띄운 세션은 환경 변수 `TRACEPARENT`를 읽어 바깥 프로그램의 추적에 이어 붙는다. 그래서 ①의 상주 프로그램이 하네스를 띄울 때 업무 번호로 추적을 이을 수 있다. 프롬프트와 도구 내용은 기본으로 가려 보낸다. `claude_code.token.usage`와 `claude_code.cost.usage`가 320줄 `사용량 모으기`에 그대로 쓰인다.
- Codex는 `[otel]` 설정으로 로그를 OTLP로 내보낸다("Disabled by default; opt in via `[otel]`"). 그런데 기본으로 익명 사용 자료와 상태 자료를 OpenAI에 보내고, `[analytics] enabled = false`로 끄면 "This also disables custom OTLP metrics exporters in Codex CLI." 사용량은 Codex 측정값 대신 OTLP 로그와 자체 실행 기록에서 세야 한다.
- Prometheus는 OTLP 측정값을 직접 받는다(`--web.enable-otlp-receiver`, 기본 꺼짐). 측정값만 보낼 때는 Collector 없이도 된다.
- 추적에서 측정값을 뽑는 Collector의 span metrics 부품은 아직 alpha다.

**세 환경**: ①은 PC의 하네스와 상주 프로그램이 사내 Collector로 보낸다. ②와 ③은 Temporal 실행 코드가 같은 Collector로 보낸다. 모두 사내 설치이고, 받는 곳이 멈추면 내보내기만 실패할 뿐 업무는 계속된다.

**판정**: 유지. 같은 일을 하는 표준이 따로 없다. Codex의 바깥 통계를 끄는 설정과, 끄면 사라지는 측정값을 어디서 셀지를 함께 정해야 한다.

## 4. 데이터 복구: PostgreSQL WAL과 다른 장비의 원본 백업

**확인한 사실**
- PostgreSQL 18.6이 지원 중인 최신 버전이다(18은 2025-09-25 출시, 2030-11-14 지원 종료). 14는 2026-11-12에 지원이 끝난다.
- PostgreSQL 19 RC 1이 2026-10-15에 나왔다. "The planned date for the general availability of PostgreSQL 19 is November 19, 2026." RC 2는 11월 12일에 나온다.
- WAL만으로는 복구가 되지 않는다. 기본 백업과 WAL을 다른 장비에 보관하고, 보관 기간을 관리하고, 백업을 검증하는 도구가 필요한데 문서에는 그 이름이 없다.

**견준 대안**

|---|---|---|---|---|
| pgBackRest | 2.59.3(2026-10-04) | MIT | 299건(David Steele 280건) | 병렬 백업과 병렬 복원, 블록 단위 증분, 비동기 WAL 보관, 원격 저장 장비. 2.59.1에서 PostgreSQL 19 베타를 지원했다. 2026-04-27 "pgBackRest is no longer being maintained."를 발표했다가, 2026-05-18 AWS, Supabase, Percona 등 후원사 연합으로 계속한다고 밝혔다. 2.59.3 이전 버전에는 약한 암호화 키가 만들어질 수 있는 결함이 있었다 |

- 실사용 보고: Langfuse 이슈 #6572 "Since upgrading to V3, it seems Clickhouse consumes a lot of CPU frequently even if there's no usage of Langfuse."
- 이 도구들 사이에 공개 성능 평가는 없다. 찾은 비교 글은 mlflow.org, Braintrust처럼 제조사가 쓴 것이거나 출처 없는 SEO 글이었다.

**판정**: 유지. ①②는 후보 모두 통과하고 ③은 쓸 평가가 없다. ④에서 자체 실행 기록이 이미 건별 기록과 근거를 맡고 있어, LLM 추적 도구는 같은 일을 겹쳐 한다. ⑤에서는 부품을 1~10개 늘린다. 게다가 프롬프트와 도구 결과를 그 도구의 저장소에 두면, 고객마다 나누고 고칠 수 없게 잠근 기록 설계 밖에 사본이 하나 더 생긴다. 실행 시간과 오류는 측정값으로 Prometheus에 모으고, 단계별 흐름 그림이 꼭 필요해지면 Grafana에 붙는 Tempo 모놀리식 하나만 더한다.

## 6. 업무 능력 시험과 장치별 효과 재기: Inspect와 Docker 샌드박스

**확인한 사실**
- inspect_ai 0.3.281(2026-10-15), MIT, 영국 AI Security Institute와 Meridian Labs. 지난 6개월 커밋 2,779건, 작성자 191명.
- 채택: "METR migrated from their in-house Vivaria platform to Inspect." Apollo Research는 3개월 써 본 뒤 자체 틀을 접었다(AISI 2026년 6월 글). AISI는 미국 CAISI, METR, Apollo Research가 Inspect 샌드박스 도구를 쓰도록 도왔다.
- 샌드박스 종류: docker(기본 내장), k8s, Proxmox, Vagrant, NVIDIA OpenShell은 사내에 둘 수 있다. Daytona, Modal, EC2는 바깥 클라우드다.
- 함정: Inspect가 만든 기본 Compose 설정은 `network_mode: none`으로 네트워크를 막지만, 직접 쓴 Compose 설정은 Docker 기본값대로 바깥 인터넷이 열린다. 직접 쓴 설정마다 `network_mode: none`을 넣어야 한다.
- inspect_swe 0.2.71(2026-09-17)은 Claude Code, Codex CLI, Gemini CLI, OpenCode를 Inspect 에이전트로 돌린다. "Agents run inside the sample sandbox and their model API calls are proxied back to Inspect." 기본으로 최신 안정 버전 Claude Code를 내려받으므로, 운영과 같은 버전으로 시험하려면 그 버전을 이미지에 넣고 `version="sandbox"`로 고정해야 한다. 모델 호출이 Inspect의 모델 연결로 가므로, ①의 시험은 PC의 구독 로그인이 아니라 Inspect에 설정한 모델 연결로 돈다.
- 운영 코드 실행은 gVisor로 격리한다. Docker Compose 규격에는 서비스마다 실행기를 고르는 `runtime` 항목이 있고(`runtime` specifies which runtime to use for the service’s containers), gVisor는 Docker에서 `--runtime=runsc`로 쓴다. 그래서 직접 쓴 Compose 설정에 `runtime: runsc`를 넣으면 시험도 운영과 같은 격리로 돌린다.
- 모델 연결: vLLM, llama-cpp-python, OpenAI 호환 주소를 지원하므로 ②의 vLLM과 ③의 llama.cpp 서버를 그대로 쓴다.
- inspect_evals v0.24.0(2026-10-08)에 agentdojo, agentharm, b3, strong_reject, cyberseceval 2~4가 있다.

**견준 대안**
- Harbor v0.24.0(2026-10-05, Apache-2.0): Terminal-Bench 2.0의 공식 실행 틀이고 채점기를 따로 샌드박스에 둘 수 있다. 다만 터미널 과제 중심이고, 논문 실험은 Daytona 클라우드 샌드박스로 돌렸다.
- DeepEval(Apache-2.0)과 promptfoo 평가 기능: 응답 채점 중심이라 샌드박스 안 에이전트 실행과 정답 격리를 따로 짜야 한다.
- Inspect와 Harbor를 같은 기준으로 견준 공개 평가는 찾지 못했다.

**판정**: 유지. ①②를 통과하고(Docker와 k8s는 사내), ③의 공개 평가는 없다. ④에서 공격 시험(AgentDojo)과 Claude Code와 Codex 실행(inspect_swe)이 같은 틀 위에 있어 부품이 늘지 않는다. 문서의 시험 환경 기준("운영과 같은 제품과 설정")을 지키려면 Claude Code와 Codex의 버전 고정과 `network_mode: none`을 시험 기준에 넣어야 한다.

## 7. 공격 시험(문서에 제품 이름 없음)

문서가 요구하는 것은 셋이다. 우리 방어를 아는 공격용 AI가 막힐 때마다 문장을 고쳐 다시 시도하는 시험, 안전 규칙을 피하게 하거나 정보를 빼내려는 요청을 한꺼번에 던지는 자동 시험, 글을 숨겨 넣은 파일로 하는 시험이다.

**왜 적응형 공격이 필요한가**: Nasr, Carlini 등 14명의 논문(arXiv 2510.09023, 2025-10-10)은 "we bypass 12 recent defenses … with attack success rate above 90% for most"라고 적고, 그 방어 대부분이 원래 0에 가까운 성공률을 보고했다고 밝힌다. AgentDojo에서 Spotlighting과 Prompt Sandwiching은 정해 둔 공격으로는 성공률이 1%까지 낮았지만, 탐색형 적응 공격에서는 95%를 넘었다. 문서의 "미리 써 둔 공격 문장만 쓰면 실제보다 잘 막는 것처럼 나온다"와 맞는다.

**견준 대안**

- 세 도구의 공격 성공률을 같은 기준으로 잰 공개 평가는 찾지 못했다. 비교 글(aisecbench 2026-06-13, threatclaw, Mindgard)은 기능표뿐이고 Mindgard는 경쟁 제품을 판다. 공통된 결론은 "garak은 일괄 검사, PyRIT은 다회 공격, promptfoo는 CI 관문"이다.
- PyRIT의 공격 자료 66개에는 garak 자료(garak_dataset), HarmBench, JailbreakBench, system prompt 빼내기 자료가 들어 있다. PyRIT 하나로 적응형 시험과 일괄 시험을 함께 돌릴 수 있다.

**판정**: 확인 필요. 추천은 PyRIT 1.1.0 하나다. ①에서 넷 다 사내 설치가 된다. ②에서 promptfoo는 기본이 바깥 생성이라 뒤로 밀린다. ③의 공개 점수는 없다. ⑤에서 PyRIT 하나가 적응형 공격과 일괄 공격 자료를 함께 갖춰 부품이 가장 적다. 공격 대상은 운영과 같게 갖춘 에이전트의 HTTP 주소(http_target)로 두고, 공격 모델과 채점 모델은 사내 vLLM에 둔다. 글을 숨겨 넣은 파일 시험은 어느 도구에도 우리 형식(HWP, 스캔 PDF 등)에 맞는 것이 없어 직접 만든다.

## 반대 가설

- **"VictoriaMetrics가 자원을 덜 쓰니 바꿔야 한다."** VictoriaMetrics 측정에서는 같은 자료를 담는 데 디스크를 2.5배, 메모리를 1.8배 덜 썼다. 하지만 제조사가 잰 수치이고, 이 차이는 감시 항목이 수백만 개일 때 비용 문제가 된다. 우리 감시 대상은 서버 몇 대와 DGX Spark 한 대라 그 규모에 한참 못 미친다. 감시 항목이 수백만 개로 늘면 이 판정을 다시 본다.
- **"에이전트가 왜 실패했는지 보려면 Langfuse나 Phoenix 같은 화면이 필요하다."** 문서는 성공한 건과 실패한 건의 실행 기록을 견줘 처음 달라진 단계를 찾고, 이 일은 자체 실행 기록이 맡는다. 그래도 화면이 필요해지면 Phoenix가 가장 가볍다. 프로그램 하나에 이미 쓰는 PostgreSQL만 있으면 된다. 다만 Phoenix의 사용 허가(Elastic License 2.0)는 남에게 서비스로 제공하는 것을 막으므로, 고객이 그 화면을 쓰게 해서는 안 된다.
- **"pgBackRest는 한 사람이 대부분 개발하니 Barman이 더 안전하다."** 오래 이어질지만 보면 맞다. 판정 기준은 성능을 앞에 두므로, 여러 파일을 동시에 되살리는 기능이 있는 pgBackRest를 골랐다. 2026년 4월처럼 유지 중단을 다시 발표하면 Barman으로 옮긴다.
- **"promptfoo가 GitHub 별과 커밋이 가장 많다."** 활동은 가장 활발하다. 하지만 공격 문장을 기본으로 바깥 서버에서 만들고, 바깥 서버를 끄면 공격 문장의 질이 떨어질 수 있다고 공식 문서가 직접 밝힌다. 그래서 쓰지 않는다.

## 편향

- 영어 자료가 대부분이다. 한국어로 찾은 실사용 후기는 Langfuse를 직접 설치한 글 1건뿐이었고, 판정을 바꿀 내용은 없었다.
- 유지 상태를 GitHub 별과 커밋 수로 봤으므로 사용자가 적은 도구는 덜 보였다. 그래서 별 수와 관계없이 공식 문서에 바깥 의존이 없다고 적힌 후보도 함께 견줬다.
- VictoriaMetrics 수치, mlflow.org의 비교, Braintrust와 Mindgard의 글은 모두 자기 제품을 파는 쪽이 썼다. 판정 근거로는 공식 문서, 저장소, 논문만 썼다.

## 이 분석이 답하지 않는 것

- 우리 감시 장비가 실제로 쓸 디스크와 메모리. 감시 대상을 정한 뒤 잴 수 있다.
- PyRIT의 적응형 공격이 우리 방어를 얼마나 자주 뚫는지. 방어 장치를 만든 뒤 시험해야 나온다.
- pgBackRest와 Barman이 같은 자료를 되살리는 데 걸리는 시간. 둘을 같은 조건에서 잰 공개 측정이 없다.

## 가정

- 감시 대상은 사내 서버 몇 대와 DGX Spark 한 대다. 그래서 감시 항목은 100만 개보다 훨씬 적다.
- 감시 장비는 실행 장비와 다른 사내 리눅스 장비다.
- 건마다의 실행 내용은 자체 실행 기록이 맡고, OpenTelemetry로는 내용 없이 걸린 시간, 오류, 업무 번호만 보낸다.

## 다음에 할 일

1. `운영 감시와 복구`의 표에 Alertmanager와, 감시 장비 밖에서 Watchdog 경보를 받는 곳을 넣는다. Codex의 사용 통계를 끄는 설정도 같은 절에 적는다.
2. 같은 표의 `데이터 복구` 줄에 pgBackRest 2.59.3을 넣고, 대체로 Barman을 적는다.
3. `업무 능력 시험`의 `시험 도구`에 공격 시험 도구 PyRIT을 넣는다. Inspect로 Claude Code와 Codex를 돌릴 때 운영과 같은 버전으로 고정하고, 직접 쓴 샌드박스 설정마다 바깥 연결을 막는 `network_mode: none`과 운영과 같은 gVisor 실행기(`runtime: runsc`)를 넣는다는 기준도 함께 적는다.
