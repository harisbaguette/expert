# 계산, 분석, 최적화, 법 계산 규칙 기술 바깥 대조 (2026-10-16)

`재료 별 구현.md`의 계산과 분석 기술 열네 가지를 오늘 기준 원문과 대조했다. 세 실행 환경은 ① 한 사람 PC의 Claude Code나 Codex, ② GPU 서버(vLLM), ③ DGX Spark(llama.cpp)다. 모든 출처의 확인일은 2026-10-16이다.

**결론**

- 열네 가지 가운데 열하나는 그대로 둔다. 모두 세 환경에 사내 설치할 수 있고, 바깥 서비스가 끊겨도 일이 멈추지 않는다.
- 차량 경로는 OR-Tools를 PyVRP로 바꾼다. 공개 평가에서 알려진 가장 좋은 답보다 이동 거리가 OR-Tools는 4.42%, PyVRP는 0.31% 길다. 방문 시간이 정해진 문제에서는 9.38% 대 0.65%다.
- Semantic Entropy는 그대로 쓰되, 판단 전체가 아니라 판단의 결론만 짧게 받아 묶는다는 조건을 붙인다.
- HiGHS는 선형계획에는 그대로 둔다. 이차계획은 HiGHS가 새 해법을 넣은 뒤 잰 공개 평가가 아직 없다. 평가가 나와서 다른 오픈소스 PIQP가 성공률에서 20%p 넘게 앞서면 이차계획만 PIQP로 바꾼다.

## 판정 순서

후보는 다섯 단계로 걸렀다.

1. 세 환경에 모두 사내 설치할 수 있는가
2. 바깥 서비스가 끊겨도 멈추지 않는가
3. 공개 성능 평가가 있으면 그중 가장 높은가
4. 같은 일을 하는 부품을 이미 쓰고 있는가

## 선택마다 확인한 사실

### Catala — 유지

**확인한 사실**
- 최신 버전은 1.3.0이다(2026-10-01). 직전 버전은 1.2.1(2026-07-06)이다. 마지막 커밋은 2026-10-15이고 별은 2,420개다. 사용 허가는 Apache-2.0이다.
- 1.3.0은 C, Java, Python, OCaml 코드를 만든다. 실행 기록(trace)은 Java, Python, OCaml 생성 코드에서도 나오고, 인터프리터가 낸 기록과 같다. 런타임과 표준 라이브러리는 만든 코드와 함께 `libcatala` 꾸러미 하나로 나온다. 그래서 세 환경은 바깥 의존 없이 같은 Python 코드를 부른다.
- 컴파일러는 미리 빌드된 실행 파일이 없고 opam(OCaml)으로 소스에서 빌드한다. 다만 규칙을 쓰는 한 곳에만 있으면 되고, 세 환경에는 만든 Python 코드만 간다.
- Catala 책임자(Denis Merigoux)는 자기 누리집에 DGFiP 소득세 계산 기여가 2024년부터 운영 중이고, CNAF 가족수당 계산 기여가 2027년 운영에 들어간다고 적었다. 누리집은 DGFiP 일에 쓴 도구 이름을 밝히지 않는다.
- CNAF와 Inria는 2026-06-03에 협약을 맺었다. CNAF는 1년 동안 비교한 끝에 Cobol 규칙 엔진을 Catala로 바꾸기로 했고, 선정 기준에 기술 주권을 넣었다.
- 법 조문을 LLM으로 Catala 코드로 옮기는 평가 자료가 2025년에 나왔다(NLLP 2025). 저자들은 다른 언어의 코드 생성과 비슷한 수준이라고 보고했다.

### Python `Decimal` — 유지

- 표준 라이브러리다. Python 3.15.0이 2026-10-09에 나왔고, 3.14.8과 3.13.16은 2026-09-30에 나왔다.
- 따로 들일 부품이 없어 1~5단계를 모두 통과한다. 금액 계산에서 같은 역할을 하는 바깥 대안은 찾지 않았다.

### Pint — 유지

- 최신 버전은 0.26.1(2026-09-10)이고 Python 3.12 이상이 필요하다. 마지막 커밋은 2026-10-12다. 사용 허가는 BSD다(GitHub는 NOASSERTION으로 표시하지만 LICENSE 파일은 BSD 문구다).
- 대안: astropy.units(astropy 8.0.2, 2026-10-15)는 천문학 패키지 전체를 함께 들여야 한다. unyt(3.1.0, 2026-01-15, BSD-3)는 천체물리 yt 생태계용이다.
- 단위 변환 라이브러리를 견준 공개 평가는 없다. 그래서 4~5단계로 갈랐고, 이미 쓰는 Pint가 부품이 가장 적다.

### SymPy — 유지

- 최신 버전 1.14.0은 2025-04-27에 나왔다. 그 뒤 18개월째 새 버전이 없다.
- 개발은 멈추지 않았다. 2026-07-16 이후 커밋이 100건을 넘고(한 번에 받을 수 있는 최대치), 마지막 커밋은 2026-10-15다. 1.15 이정표에는 열린 이슈 10개가 남아 있다.
- 대안: SymEngine 0.14.1(2025-04-21, MIT)은 빠르지만 기능이 좁다. python-flint 0.9.0(2026-07-03)은 MIT와 LGPL-3.0이 섞였고 다항식과 정수론 위주다. 둘 다 SymPy의 기호식 전반을 대신하지 못한다.
- 판정: 유지. 새 버전이 늦어지는 것은 위험 신호지만, 바꿀 대상이 없다.

### SciPy — 유지

- 최신 버전 1.18.1(2026-08-21), BSD-3, Python 3.12 이상. 마지막 커밋은 2026-10-15다.
- 수치해석과 그 밖의 수치 최적화에서 같은 범위를 덮는 대안이 없다.

### statsmodels (Newcombe 신뢰구간) — 유지

- 최신 버전 0.15.0(2026-08-27), BSD-3. 직전 버전은 0.14.6(2025-12-05)이다.
- 0.15.0 소스의 `confint_proportions_2indep`는 두 독립 비율의 차이에 Newcombe 방법을 기본으로 쓴다(`"diff": "newcomb"`).
- SciPy 1.18.1의 `binomtest().proportion_ci`는 비율 하나의 구간(exact, Wilson)만 낸다. 두 비율 차이의 Newcombe 구간은 statsmodels에만 있다.
- 같은 날 다른 갈래(개인정보-보안)도 Fairlearn 대신 statsmodels를 쓰기로 판정했다. 그래서 4단계(이미 쓰는 부품) 근거가 더 굳어진다.

### statsforecast — 유지 (기준선 역할)

**확인한 사실**
- 최신 버전 2.1.1(2026-07-16), Apache-2.0, 마지막 커밋 2026-10-16.
- 두 공개 평가의 원자료를 받아 직접 다시 계산했다. fev-bench 100과제 전체로 낸 Chronos-2 점수가 논문 값(47.3%)과 같게 나와 계산 방식이 맞음을 확인했다. 아래 표의 fev-bench 수치는 통계 모델 결과가 모두 있는 94과제만으로 다시 낸 값이라 조금 다르다.

| 평가 | 비교 단위 | 통계 기준선 | 기초 모델 |
|---|---|---|---|
| fev-bench (autogluon/fev, 100과제) | 계절 단순 예측 대비 개선율(높을수록 좋음), 통계 모델이 모두 있는 94과제 | AutoARIMA 22.8%, 통계 앙상블 23.0%, AutoTheta 9.6%, AutoETS -233.5%(일부 과제에서 크게 실패) | t0-gamma 49.9%, Chronos-2 47.8% |
| GIFT-Eval (97설정, 151모델) | 계절 단순 예측 대비 CRPS 기하평균(낮을수록 좋음) | AutoARIMA 0.912(145위), 계절 단순 1.000, AutoTheta 1.244 | 1위 EXAONE-Forecast-Agent 0.419, t0-gamma 0.452(14위), Chronos-2 0.485(69위) |

- 기초 모델의 사용 허가는 제각각이다.

| 모델 | 사용 허가 | 매개변수 수 | fev-bench 순위 | 비고 |
|---|---|---|---|---|
| t0-gamma | Apache-2.0 | 2.6억 | 2위 | 2026-10-12 공개 |
| Chronos-2 | Apache-2.0 | 1.2억 | 5위 | 내려받기 1,800만 회 넘음 |
| TimesFM 3.0 | 비상업 허가 | 3.3억 | 3위 | 회사 업무에 쓸 수 없다 |
| Timestral-209M | 수정 MIT | 2.1억 | 미등록 | 직전 달 연결 월매출 2천만 달러를 넘는 회사는 쓸 수 없다. 2026-10-14 공개 |

**판정**: 유지. 문서에서 statsforecast가 맡은 일은 "직전 값이나 계절성을 쓰는 단순한 방법부터 시험"하는 기준선이다. 기준선 구현으로는 바꿀 까닭이 없다. 다만 기초 모델이 기준선보다 계절 단순 예측 대비 개선 폭이 두 배쯤 크므로, 문서의 '다른 모델' 후보는 따로 정해야 한다. 회사가 쓸 수 있는 허가 가운데 가장 높은 것은 t0-gamma이고, 가장 오래 검증된 것은 Chronos-2다.

### OR-Tools CP-SAT — 유지

- 최신 정식 버전 v9.15(2026-01-12). 다음 정식 버전은 아직 없지만, main 가지의 `Version.txt`는 `OR_TOOLS_MAJOR=10`, `OR_TOOLS_MINOR=0`, `RELEASE_CANDIDATE=YES`다. 2026-07-16 이후 main 커밋이 100건을 넘는다. Apache-2.0.
- MiniZinc Challenge 2026: Fixed, Free, Parallel, Open 부문 금메달. Local Search 부문은 QiuQi-MIXSolver가 금메달이고 OR-Tools CP-SAT LS는 은메달이다.
- MiniZinc Challenge 2025: Fixed, Free, Parallel, Local Search 부문 금메달(Open 부문은 참가자가 없어 메달이 없었다).
- 대안 Choco, Pumpkin, PicatSAT는 같은 대회에서 은메달이나 동메달에 그쳤다.

| HGS-CVRP (2023-02-28) | 0.11% | — | — | — | — |

- Mittelmann 교수의 CVRP 평가(2026-08-04, CVRPLIB X 세트)에서 이동 거리 간격의 기하평균은 HGS 1, PyVRP 2.52, 상용 Hexaly 2.57이다. PyVRP는 한 스레드, Hexaly는 열두 스레드로 돌렸다. 이 평가에 OR-Tools는 없다.
- 다른 연구진의 CaDA 논문(arXiv 2412.00346)은 같은 시간(10.4분, 20.8분)을 준 50지점과 100지점 문제에서 OR-Tools가 PyVRP보다 CVRP는 1.9%와 4.2%, VRPTW는 0.35%와 1.5% 나빴다고 보고했다. PyVRP 논문(INFORMS JoC 2024)도 OR-Tools의 성능이 "최신 수준과 거리가 멀다(far from the state of the art)"고 적었다.
- PyVRP 0.14.0(2026-08-20)은 MIT이고 세 환경 설치 파일이 모두 있다. 마지막 커밋은 2026-10-14다. 방문 가능 시간, 여러 차고지, 차종마다 다른 용량과 비용, 짝을 이룬 수거와 배송, 차고지에서 다시 싣기, 골라서 방문하기를 지원한다.

**견준 대안**
- HGS-CVRP: CVRP만 푼다. 문서의 '차량 경로' 일반에는 좁다.
- NVIDIA cuOpt(26.10.0, Apache-2.0): GPU가 없는 ①에 깔리지 않아 1단계에서 빠졌다.
- VROOM(BSD-2, v1.15.0, 2026-03-12): 길찾기 서버와 함께 쓰는 구조이고, 같은 공개 평가에 없다.
- Timefold(Java, Apache-2.0): Python 꾸러미가 2025-07 베타 버전에 멈췄다.

**판정**: 교체. 3단계(공개 성능)가 4단계(이미 쓰는 OR-Tools)보다 앞선다. 간격 차이가 열 배 넘게 나서 부품 하나를 더하는 값어치가 있다. PyVRP가 표현하지 못하는 제약이 실제로 나올 때만 OR-Tools 경로 최적화로 돌아간다.

### HiGHS — 유지 (이차계획은 확인 필요)

**선형계획과 혼합정수계획 (Mittelmann 평가)**

| 평가 (날짜) | 지표 | 결과 |
|---|---|---|
| LPopt, 최적 기저해 (2026-10-07) | 축척 이동 기하평균(낮을수록 좋음) | COPT 1, MOSEK 5.27, XOPT 6.63, HiGHS 12.8, CLP 27.4, GLOP(OR-Tools) 59.7, SoPlex 101 |
| LPfeas, 실현 가능해 (2026-09-16) | 같은 지표 | HPR-LP-C 1, cuOpt 1.17, COPT 1.67, HiGHS 16.9, OR-Tools PDLP 27.8. GPU 코드는 NVIDIA B200에서 돌렸다 |
| MILP, MIPLIB2017 240문제 (2026-10-10) | 푼 문제 수 | COPT 219, OptVerse 210, HiGHS 병렬 179, HiGHS 158, SCIP 136 |

- CPU 오픈소스 가운데 HiGHS가 선형계획과 혼합정수계획 모두 가장 앞선다. XOPT는 사용 허가와 공개 여부를 확인하지 못했다.
- GPU 해법(cuOpt, HPR-LP-C)은 LPfeas에서 HiGHS보다 열 배 넘게 빠르지만, ①에 깔리지 않아 1단계에서 빠진다. HiGHS 자체에 GPU PDLP 빌드 선택지가 있어, ②와 ③에서 GPU를 쓰려면 같은 부품 안에서 할 수 있다.
- 최신 버전 v1.15.1(2026-07-02), MIT(HiPO를 넣은 빌드는 Apache-2.0). 바깥 의존이 없다.

**이차계획**
- Maros-Meszaros 이차계획 평가는 2024-09-07에 HiGHS 1.7.2로 잰 것이 마지막이다. 기본 설정 성공률은 HiGHS 66.7%, PIQP 95.7%였고, 높은 정확도 설정에서는 HiGHS 0.0%, PIQP 73.2%였다.
- HiGHS는 그 뒤 1.14.0(2026-04-06)에서 내부점 해법 HiPO가 볼록 이차계획을 풀게 했고, 1.15.0에서 Python에서도 쓸 수 있게 했다. 새 해법을 잰 공개 평가는 아직 없다.
- PIQP 0.6.4(2026-08-28)는 BSD-2이고 마지막 커밋이 2026-10-08이다.

**판정**: 선형계획은 유지한다. 이차계획은 확인 필요다. 공개 평가는 25개월 전 것이고, 그 뒤 HiGHS의 이차계획 해법이 바뀌었다. 평가가 갱신되기 전에는 결론을 낼 근거가 없다.

### Optuna — 유지

- 최신 버전 5.0.0(2026-09-07), MIT. 마지막 커밋 2026-10-16.
- 5.0은 단일 목적 TPESampler에 다변량 TPE와 constant liar를 기본으로 켰고, 다목적 기본 해법을 NSGA-II에서 TPE로 바꿨다. `constraints_func`는 폐기 예정이 되고 `trial.set_constraint()`로 옮겨 간다. 옛 코드는 이 부분을 고쳐야 한다.
- 독립 비교 carps(arXiv 2506.06143, 2025)는 3,336과제에서 9가지 계열 최적화기를 쟀다. 결론은 "과제 유형마다 많은 최적화기가 통계적으로 뚜렷하게 다르지 않다"였다. 블랙박스 시험 세트 평균 순위는 SMAC3 1.50, Nevergrad CMA-ES 1.82, 무작위 탐색 2.67이었다.

- 판정: 유지. 3단계에서 뚜렷한 승자가 없어 4~5단계로 갈랐다.

### Semantic Entropy (다시 볼 판단 고르기) — 유지 (답을 짧은 결론으로 받아 묶는 조건)

**확인한 사실**
- LM-Polygraph 벤치마크(TACL 2025)는 방법을 개발한 쪽과 다른 연구진이 낸 공개 평가다. 결론은 "가장 좋은 방법은 표본 다양성 기법인 SAR, DegMat, Semantic Entropy"이고, 긴 답에서는 NLI 유사도를 쓰는 블랙박스 기법(DegMat 등)이 앞섰다.
- ①의 Claude Code와 Codex는 토큰 확률을 주지 않는다. 그래서 확률 가중 방식이 아니라 답의 개수로 세는 이산 방식(DSE)만 쓸 수 있다. 문서의 설명("여러 번 답하게 해 뜻이 같은 답끼리 묶고 몇 갈래로 갈리는지 잰다")이 바로 이산 방식이다.
- ACL Findings 2025 논문(SNNE)은 긴 답에서 이산 방식이 상수값을 낸다고 보고했다. 답마다 따로 묶여 갈래 수가 늘 표본 수와 같아지기 때문이다.
- 대안 Kernel Language Entropy(NeurIPS 2024)는 Semantic Entropy를 일반화하고 블랙박스에서도 쓴다. 다만 SNNE 논문 실험에서는 블랙박스 방식(KLEheat)이 더 단순한 이산 방식보다 낮았다.
- SNNE는 자기 논문에서 SE, KLE, SAR보다 높다고 보고했지만, 논문에 적은 코드 저장소(BigML-CSUCLA/SNNE)는 지금 열리지 않는다(404). 다른 연구진의 재현도 찾지 못했다.
- 원 구현 jlko/semantic_uncertainty는 2024-04-12 뒤로 커밋이 없다. LM-Polygraph 0.7.0(2026-05-04, MIT, 마지막 커밋 2026-10-09)은 Semantic Entropy, 이산 갈래 수, KLE, DegMat, EigV 등을 한 틀에 담고 있다.

**판정**: 유지. 독립 공개 평가에서 상위권이고, 이를 확실히 앞선다는 대안은 저자 자기 보고뿐이거나 코드가 없다. 조건이 하나 붙는다. 판단 전체를 그대로 묶지 않고, 판단의 결론(충족 여부, 금액, 고른 선택지)을 짧은 꼴로 받아 그것끼리 묶어야 갈래 수가 뜻을 가진다.

## 결론과 반대인 가설

| 가설 | 확인한 것 | 결과 |
|---|---|---|
| 기초 모델이 이렇게 앞서면 statsforecast를 빼야 한다 | 문서의 절차는 기준선을 먼저 돌리고 다른 모델이 이를 이기는지 보는 것이다. 기준선 없이는 비교 자체가 안 된다. 두 평가 모두 기초 모델 일부가 시험 자료를 미리 봤을 위험을 지적한다(fev-bench에서 Moirai-2.0 28%, TimesFM-2.5 10% 과제 겹침) | 기각 |
| OR-Tools를 이미 쓰니 경로도 OR-Tools로 두는 편이 부품이 적다 | 4~5단계는 3단계 뒤다. OR-Tools 평가 수치는 2024-05에 v9.10으로 한 번 돌린 것이라 오래됐지만, 다른 연구진의 2024년 비교(CaDA)도 같은 방향이다 | 기각 |
| HiGHS 대신 cuOpt로 가면 더 빠르다 | LPfeas에서 열 배 넘게 빠르지만 ①에 깔리지 않는다. 혼합정수계획은 cuOpt 스스로 베타라고 밝힌다 | 기각 |
| Catala는 프랑스 밖 운영 사례가 적어 위험하다 | 운영 채택은 프랑스 공공기관 중심이고, 한국 법령에 쓴 사례는 찾지 못했다. OpenFisca 등 다른 후보도 한국 운영 사례를 찾지 못했다 | 기각. 위험은 맞지만 후보끼리 차이가 없다 |
| 특일 API 대신 `holidays` 패키지만 쓰면 바깥 의존이 사라진다 | 임시공휴일은 정부 발표 며칠 뒤 패키지 새 버전이 나와야 반영된다. 공식 출처를 날마다 저장하는 쪽이 늦지 않다 | 기각 |

## 한계

- 표본 편향: Mittelmann 평가에는 Gurobi, CPLEX, Xpress가 빠져 있다(2018년에 IBM과 FICO가 결과 삭제를 요구했고, 2024년 8월에 Gurobi가 빠졌다). 오픈소스끼리의 순위에는 영향이 없다.
- 생존자 편향: GIFT-Eval과 fev-bench는 제출 방식이다. 좋은 결과를 낸 모델만 올라올 수 있다. 시험 자료를 미리 봤는지는 제출자가 스스로 적는다.
- 이해 충돌: PyVRP 평가표는 PyVRP 개발진이, ClickBench는 ClickHouse 회사가 운영한다. PyVRP 결론은 Mittelmann 평가와 다른 연구진의 CaDA 논문으로 따로 확인했다. DuckDB 수치는 순위의 큰 흐름만 썼다.
- ClickBench와 GIFT-Eval 점수는 원자료로 직접 계산했다. 공식 화면의 집계 방식(빠진 값 처리, 순위 계산)과 조금 다를 수 있다. fev-bench는 Chronos-2 값이 논문과 같아 방식이 맞음을 확인했다.
- 이 조사는 다음을 답하지 않는다. 회사 실제 자료에서 기초 모델이 기준선을 이기는지, 회사 월매출이 Timestral 허가 한도를 넘는지, 한국 법령을 Catala로 옮기는 데 드는 품, 새 HiGHS 이차계획 해법의 실제 성능.
