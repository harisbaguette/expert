# 기술 묶음 안의 충돌 점검 (2026-10-16)

`재료 별 구현.md`의 기술 전부와, 같은 폴더 여섯 파일의 교체안 여덟 가지(Nemotron-3-Embed-8B, MonkeyOCRv2-S-Parsing, Fairlearn 빼고 statsmodels, PyVRP, ①의 기억을 PostgreSQL로, Ceph RGW, pgBackRest, PyRIT)를 함께 놓고, 서로 부딪히는 곳을 찾았다. 바깥 사실은 모두 2026-10-16에 원문으로 확인했다. 메모리는 모델 파일 크기와 모델 구성 파일로 계산했고, 파이썬 패키지는 `uv pip compile`로 실제로 풀어 봤다.

①은 한 사람 PC의 Claude Code나 Codex와 사내 서버의 상주 프로그램, ②는 GPU 메모리 1.5TB 이상인 사내 서버(vLLM), ③은 사내 서버와 DGX Spark 한 대(128GB, llama.cpp)다.

## 결론

- 충돌은 28개다. 치명 2, 높음 8, 중간 11, 낮음 7이다.
- 치명 둘은 고객 자료가 섞이는 길이다. ③의 llama.cpp는 여러 요청을 한 캐시에 함께 두면 다른 요청의 내용이 보이는 버그가 있고, 이를 고치는 PR이 아직 병합되지 않았다. ①의 Temporal은 기본 설정에서 PC 하나의 자격으로 다른 고객의 대기열과 실행 이력을 읽을 수 있다.
- ③은 지금 고른 주 모델로 문서의 속도 조건을 넘지 못한다. 공개 실측에서 3만 토큰 문서의 첫 토큰이 29~46초(조건 10초), 출력이 초당 21.8~25.6토큰(조건 30토큰)이다. 메모리도 llama-server 기본값 그대로면 140.9GiB가 필요해 119.2GiB를 넘는다.
- 교체안 가운데 Nemotron-3-Embed-8B는 그대로 적용하면 ①과 ③에서 돌릴 곳이 없다. 나머지 일곱은 표의 풀 방법을 지키면 다른 기술과 부딪히지 않는다.
- ②의 GPU 메모리 합계는 문제가 없다. 다만 문서 10행의 "8bit로 약 1TB"는 공식 체크포인트(534.07GiB)와 다르다.

## 충돌마다 근거

### 1. llama.cpp의 Qwen3.8-Flash-Next 다중 요청 버그 (치명, ③)

- ③ 주 모델은 llama.cpp의 `qwen4exp` 구조로 돈다. 이 구조의 희소 주의(QSA) 처리에 대한 수정 PR #29166이 2026-09-20에 열렸고 2026-10-16까지 병합되지 않았다.
- PR 설명은 이렇다. 한 통합 캐시에 요청이 둘 이상 있으면 "one of our blocks can be masked out, one of another sequence's can pass through". 재현에서 모델이 자기 메시지를 못 보고 입력이 비었다고 답했고, 동시 요청 4번 가운데 2번만 맞았다.
- llama-server는 슬롯 수를 자동으로 정할 때 통합 캐시를 기본으로 켠다(`--kv-unified`, "default: enabled if number of slots is auto").
- 문서는 ③에서도 Child Workflow로 단계를 나눠 맡기고(154행), 통화 응답을 같은 주 모델에 맡긴다(629행). 그래서 동시 요청이 생기고, 다른 고객 요청의 블록이 보일 수 있다.
- 풀 방법의 근거: PR 설명은 "Single-sequence caches are unaffected"라고 적었다. `--no-kv-unified`는 요청마다 캐시 흐름을 따로 둔다.

### 2. Temporal 기본 권한과 실행 이력 (치명, ①, 이력은 ②③도)

- Temporal 공식 보안 문서: Authorizer를 따로 정하지 않으면 noopAuthorizer가 "allows every API request, with no authentication or access control".
- 기본 JWT ClaimMapper의 권한은 `<namespace> : <permission>` 꼴이다. 대기열 단위 권한은 없다.
- 문서는 고객마다 PC 대기열을 나누고(130행), 진행 상태와 실행 기록도 고객마다 나눈다(356행). 한 네임스페이스를 함께 쓰면 PC 하나의 워커 자격으로 다른 고객 대기열의 일을 받고 실행 이력을 읽을 수 있다.
- 실행 이력에는 활동의 입력과 결과(고객 자료)가 들어간다. 이 이력은 Temporal DB에 평문으로 남아, 건별 키 암호화(234행)와 사본 삭제(246행) 밖에 있다. Temporal 공식 문서는 Payload Codec으로 암호화하면 "the Temporal Server sees only encrypted data"라고 적는다.

### 3. ③ 메모리 (높음)

DGX Spark는 128GB(119.2GiB)를 CPU, GPU, 운영체제가 함께 쓴다. NVIDIA 문서는 모자라면 스왑으로 밀어낸다고 적는다.

| 항목 | 크기(GiB) | 근거 |
|---|---:|---|
| 주 모델 UD-Q4_K_XL / UD-IQ4_XS | 103.68 / 87.24 | unsloth GGUF 파일 합 |
| d3-mini Q8_0 / d3-flash Q8_0 | 4.80 / 8.87 | ggml-org GGUF |
| Qwen3-Reranker-4B Q8_0 | 3.98 | GGUF 파일 |
| Qwen3-Embedding-8B Q8_0 | 7.49 | Qwen 공식 GGUF |
| 주 모델 작업 메모리 32k / 기본 262,144토큰 | 0.95 / 6.86 | 토큰당 27,648B(QSA 12층×KV 2×256차원×K와 V×2B + 색인 키), 요청당 DeltaNet 상태 108MiB |
| d3-mini 작업 메모리 기본 262,144토큰(생성 모델처럼 잡을 때) | 8.00 | 전체 주의 8층×KV 4×256×2×2B |
| 재정렬과 임베딩 작업 메모리 기본 40,960토큰 | 각 5.62 | 36층×KV 8×128×2×2B |
| llama-server `--cache-ram` 기본 | 8.00 | README "default: 8192" |

- llama-server의 `-c` 기본은 0이고 "0 = loaded from model"이다. 그래서 문맥을 적지 않으면 모델 최대 길이만큼 작업 메모리를 잡는다.
- 기본값 그대로(주 모델 Q4_K_XL + d3-mini + 재정렬): 모델 112.46 + 작업 메모리 20.48 + 프롬프트 캐시 8 = 140.9GiB로 21.7GiB 넘친다.
- 문맥을 32k와 8k로 줄여도 114.8GiB라 운영체제, CUDA 문맥, 계산 버퍼에 4.4GiB만 남는다.
- 임베딩까지 Spark에 두면 모델 파일만 119.95GiB로 넘친다.
- 추천 구성(UD-IQ4_XS + d3-mini + 재정렬 + 임베딩, 문맥 명시, 캐시 0)은 106.95GiB이고 12.2GiB가 남는다. 운영체제가 쓰는 몫은 재지 못했다.

### 4. ③ 속도 조건 (높음)

- llama.cpp 기여자가 DGX Spark(GB10)에서 UD-IQ4_XS로 잰 값이다(PR #29751, 2026-09-30, master 열).
  - 앞에 32,768토큰이 있을 때 읽기: 초당 650.78~763.76토큰. 빈 상태: 885.10~1,022.86토큰.

### 6. 하네스 세션 기록 (높음, ①)

- Claude Code는 세션 기록을 `~/.claude/projects/`에 평문으로 30일 둔다. "Anything that passes through a tool is written to a transcript on disk". 보관 일수는 최소 1일이라 0으로 끌 수 없다. `-p`에서만 `--no-session-persistence`로 끈다.
- Codex는 기본으로 세션 기록을 `~/.codex/history.jsonl`과 실행 기록 파일로 남긴다. `codex exec --ephemeral`과 `history.persistence = "none"`으로 끈다.
- 문서 572행은 승인 답이 오면 "같은 대화를 이어 다시 부른다". 이 재개는 디스크 기록이 있어야 된다. 그래서 기록을 끄면 재개가 안 되고, 켜면 고객 자료가 건별 키 암호화와 삭제 요구 밖에 평문으로 남는다.
- 풀 방법의 근거: 문서는 이미 훅이 서버 업무 기록에서 필요한 내용을 다시 넣는다(189행). 같은 방식으로 새 실행에 넣으면 디스크 기록이 필요 없다.

### 7. 훅과 샌드박스의 실패 시 통과 (높음, ①)

- Claude Code 훅: 종료 코드 2가 아닌 실패, 시작 실패, JSON 오류는 "Non-blocking error ... The action goes ahead". `onFailure: "block"`을 켜면 막는다.
- Claude Code 샌드박스: "When the sandbox can't start, Claude Code runs commands unsandboxed unless you also set failIfUnavailable".
- Codex 훅: PreToolUse가 지원하지 않는 필드를 돌려주면 "marks that hook run as failed, reports the error, and continues the tool call". 웹 검색 같은 호스팅 도구는 훅을 거치지 않는다. 공식 문서가 "Treat tool hooks as a useful guardrail, not a complete enforcement boundary"라고 적는다. 막는 쪽으로 바꾸는 설정은 찾지 못했다.
- Codex `web_search`의 기본값은 `"cached"`라 내장 웹 검색이 켜져 있다. 문서 457행은 내장 웹 검색을 쓰지 않는다.

### 8. Nemotron-3-Embed-8B 교체안 (높음, ①③)

### 9. 건별 키 삭제와 백업 (높음)

### 12. ③의 사내 서버 배치 전제 (중간)

- 문서는 ③에서도 판독(379행), 음성 인식(628행), 음성 합성(630행)을 사내 서버에 둔다. 동시에 "사내 서버에 GPU가 있고 ... 때만"(626행), "vLLM-Omni는 GPU가 있어야 돈다"(630행)로, GPU가 없을 수 있다고 본다.
- GPU가 없으면 음성 합성은 돌지 않고, 판독 모델은 CPU로 느려지며, Nemotron은 CUDA가 필요하다.
- Spark로 옮기는 것도 어렵다. PaddleOCR-VL-1.6 파이프라인은 배치 찾기에 PaddlePaddle 3.2.1 이상이 필요하다. PyPI의 PaddlePaddle 3.3.1에는 리눅스 ARM 설치 파일이 없고(x86_64, Windows, macOS ARM만), Paddle 자체 저장소의 GPU용도 리눅스 ARM은 CUDA 12.9용뿐이다. Spark의 기본 CUDA는 13.0이다. Spark 메모리도 추천 구성으로 12GiB 남짓만 남는다.

### 13. 프롬프트 캐시 고객 분리 (중간, ②③)

- vLLM 0.31.0은 접두 캐시를 기본으로 켠다(`enable_prefix_caching = True`). 요청에 `cache_salt`를 넣어야 "only requests with the same salt can reuse cached KV blocks"가 된다.
- llama.cpp에는 고객별 캐시 키가 없다. `cache_prompt` 기본 true, `--cache-ram` 기본 8192MiB, `--cache-idle-slots` 기본 켜짐이라, 다른 고객 요청과 같은 앞부분을 재사용한다. 응답 시간 차이로 다른 고객의 입력을 짐작하는 공격이 가능하다.
- 문서 189행은 ③에서 llama.cpp 프롬프트 캐시를 쓰고, 356행은 고객이 다른 요청끼리 함께 쓰지 않게 나눈다. llama.cpp에서는 기본값으로 둘을 함께 만족하지 못한다.

### 19. 서버 쪽 바깥 전송 (중간, ②③)

- vLLM: "collects anonymous usage data by default", 받는 곳 `https://stats.vllm.ai`. vLLM-Omni도 vLLM 위에서 도니 같은 값을 함께 넣는다.
- Grafana: `reporting_enabled = true`, `check_for_updates = true`, `check_for_plugin_updates = true`가 기본이다.
- Presidio의 이메일 인식기가 `tldextract.extract`를 부른다. tldextract는 기본으로 공개 접미사 목록을 HTTP로 받는다(README "How to disable HTTP suffix list fetching for production").
- `trust_remote_code` 모델과 허깅페이스 모델 이름으로 띄우는 서버는 시작할 때 허깅페이스에서 받는다.

### 20. `trust_remote_code` (중간)

- MiMo-V2.6-Pro(태그 `custom_code`, vLLM 실행 명령에 `--trust-remote-code`), d3(transformers 경로), MonkeyOCRv2(`serve.py`가 늘 붙임)는 모델 저장소의 파이썬 코드를 서버에서 실행한다.
- 저장소 코드는 바뀔 수 있다. MiMo 두 저장소는 2026-10-09, d3는 2026-10-15에 마지막으로 바뀌었다. 583행은 출처와 버전을 확인한 것만 쓴다.

### 21. Claude Code `--bare` (중간, ①)

- 공식 문서: `--bare`는 스크립트 실행의 권장 방식이고 "will become the default for `-p` in a future release".
- `--bare`는 훅, 하위 에이전트, MCP 서버, CLAUDE.md를 자동으로 읽지 않는다. "In bare mode, Claude Code never reads OAuth credentials", 그래서 API 키가 필요하다.
- 문서는 ①을 구독 요금으로 돌리고(14행), 훅으로 Cedar를 부르며(273행), 자체 MCP 서버로 도구를 연결한다(140행). 기본이 바뀐 버전으로 올리면 이 셋이 함께 빠진다.

- **23.** python-igraph는 GPL이고 검색 도구와 같은 프로세스에 묶인다. 회사 안에서만 쓰면 의무가 없지만, 고객에게 설치형으로 내보내면 검색 도구 전체에 GPL 의무가 생긴다. Pandoc(GPL-2.0), H2Orestart(GPL-3.0), GPL 빌드 FFmpeg, Grafana(AGPL-3.0)는 따로 띄우는 프로그램이라 내보낼 때 소스 제공 의무만 생긴다.
- **24.** 130행은 PC 대기열을 쓰는 까닭을 "그 PC에만 그 고객의 작업 폴더와 기억"이 있기 때문이라고 적는다. 184, 209행은 기억을 PC SQLite에 둔다. 교체안을 적용하면 세 줄이 함께 틀린다. 지금 묶음에서도 202행의 "기억을 꺼내 쓴 판단과 이어 둔다"가 PC와 서버 두 저장소를 건넌다.
- **25.** 509행은 큰 집단은 Fairlearn(부트스트랩), 작은 집단은 statsmodels(Newcombe)로 구간을 낸다. 같은 판정이 집단 크기에 따라 다른 방법으로 갈린다. 교체안으로 풀린다.
- **26.** Codex는 로그인 정보를 기본으로 `~/.codex/auth.json` 평문 파일이나 운영체제 저장소에 둔다. Temporal 워커도 서버에 붙을 자격이 PC에 있어야 한다.
- **27.** inspect_swe는 하네스의 모델 호출을 Inspect의 모델 연결로 돌리고, 기본으로 최신 Claude Code를 받는다(운영-평가 확인). 시험이 운영의 구독 로그인과 버전으로 돌지 않는다.
- **28.** PyRIT의 공격 자료 66개는 바깥에서 받는다(운영-평가 확인).

## 문제 없음

- **② GPU 메모리 합계.** 지금 묶음의 모델 파일은 625.22GiB(MiMo 534.07, d3 BF16 48.59, Qwen3-Embedding-8B 14.09, Reranker-8B 15.25, PaddleOCR-VL 1.78, Qwen3-ASR 4.37, Qwen3-TTS 4.20, Whisper large-v3 2.87)다. 교체안 뒤는 627.40GiB다. 1.5TB(1,397GiB)에서 약 770GiB가 남는다. MiMo의 작업 메모리는 전체 주의 10층×KV 8×(192+128)차원×2B = 토큰당 50KiB와, 창 128토큰 층 60개의 요청당 37.5MiB다. 3만 토큰 작업 하나에 1.47GiB, 100만 토큰에 50.04GiB다. 다만 문서 10행의 "8bit로 약 1TB"는 공식 체크포인트(MXFP4 + FP8, 534.07GiB)와 다르고, "MiMo-V2.6-Pro"라는 저장소는 없으며 -RL과 -MOPD 둘이 있다.
- **llama.cpp의 모델 지원.** `qwen4exp`(Qwen3.8-Flash-Next), `mimo2`, `paddleocr`, 판단 모델 구조가 `src/llama-arch.cpp`에 등록돼 있다. Qwen3.8-Flash-Next는 PR #27742로 2026-08-27에 들어왔다. 도구 호출은 Qwen3.8-Flash-Next의 채팅 틀이 `<tool_call><function=…>` 꼴이라, llama.cpp의 Qwen3-Coder XML 처리기가 받는다.
- **PyVRP와 OR-Tools 공존.** 위 해석에서 함께 풀린다. OR-Tools는 CP-SAT를 위해 남는다.
- **d3의 사용 허가 사슬.** 바탕 모델 Qwen3.8-27B가 Apache-2.0이라 d3의 Apache-2.0 표기와 부딪히지 않는다.
- **Nemotron의 OpenMDW-1.1.** 사용, 수정, 출력에 제한이 없고 배포할 때 고지만 남기면 된다.
- **Kiwi.** 해석 결과 0.24.0(Apache-2.0)이 깔린다.
- **Ceph RGW.** 백업을 Object Lock 버킷에 두지 않으면 다른 기술과 부딪히지 않는다.

## 실측이 남은 것

- DGX Spark에서 운영체제와 CUDA 문맥이 쓰는 메모리: Spark에 추천 구성을 띄우고 `/proc/meminfo`의 MemAvailable과 SwapFree를 잰다(NVIDIA 문서의 방법).
- ③ 속도: 우리 Spark에서 `llama-bench -m <UD-IQ4_XS> -ngl 999 -fa 1 -p 2048 -n 64 -d 0,32768`을 돌리고, 3만 토큰 새 입력의 첫 토큰 시간을 llama-server로 잰다.
- llama.cpp 다중 요청 버그가 지금 master에 남았는지: 두 요청을 동시에 보내 서로의 표식 문구가 답에 섞이는지 본다(문서 799행의 고객 구분 시험과 같은 방식).
- llama.cpp의 구조화 출력이 추론 부분을 형식 제약 밖에 두는지(97행): 공식 문서에서 찾지 못했다. 추론을 켜고 `json_schema`를 걸어 응답을 확인한다.
- MiMo의 MXFP4 커널이 ②의 GPU 종류에서 도는지: ②의 GPU 종류가 문서에 없다.
- PostgreSQL 18에서 Temporal이 도는지: Temporal 시험 묶음을 PostgreSQL 16.x와 18.x에서 각각 돌려 견준다.
