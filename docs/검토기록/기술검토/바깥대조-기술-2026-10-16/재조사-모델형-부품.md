## 결론

- **바꾸는 것 둘**: 임베딩은 Qwen3-Embedding-8B 대신 Nemotron-3-Embed-8B를, 두 번째 판독은 PP-StructureV3 대신 MonkeyOCRv2-S-Parsing을 쓴다. 시계열 예측은 문서에 기준선(statsforecast)만 있는데, 기준선과 견줄 기초 모델로 t0-gamma를 들인다.
- **주 모델에 맡기는 것**: 자료에 몰래 심어 둔 명령을 찾아 빼는 일은 지금처럼 주 모델이 한다. ③의 판단 전용 모델 d3-mini는 주 모델로 대신하는 쪽이 유력하다. 다만 점수가 없어, ③ 환경 담당이 공개 평가로 재어 54.90 이상이면 뺀다.
- **그대로 두는 것**: 나머지는 세 환경 모두 지금 모델을 둔다. 주 모델에 그 기능이 없거나(음성 입출력), 주 모델의 한국어 점수가 없거나 전용 모델보다 낮다(판독, 개인정보, 예측). 양이 많은 일(임베딩, 재정렬, 판단)은 주 모델로 돌리면 시간과 비용이 감당되지 않는다. 2026-07-15 이후 나온 모델 가운데 지금 것보다 나은 것도 없다.

주 모델 넷은 ①의 Claude Opus 5.5와 GPT-6 Astra, ②의 MiMo-V2.6-Pro, ③의 Qwen3.8-Flash-Next다.

- 정확도는 큰 범용 모델이 판단 전용 모델보다 높다. 계약서 123건, 판단 2,091개(ContractNLI)를 견준 2026-10 논문에서 Jev 1.13은 77.38%, GPT-6 Astra는 81.83%, Claude Sonnet 5는 82.40%다. 같은 논문은 "호스팅 언어 모델 일곱 개 모두 Jev보다 추정치가 높다"고 적었다.
- 하지만 같은 시험에서 GPT-6 Astra는 계약당 0.0919달러, 중앙 20.94초가 들었다. Jev는 0.000228달러, 1.24초다. 비용은 403배이고 시간은 17배다.
- 이 부품은 검색 결과마다 관련 여부를 가린다. 질문 하나에 수십 건이라 이 차이가 그대로 쌓인다.
- 이 부품은 보기마다 확률을 내고 한국어 표본으로 그 확률을 바로잡는다. Claude 메시지 API 참조에는 토큰 확률 항목이 없다. 그래서 ①에서는 확률을 받는 방식부터 달라진다.
- ②의 MiMo-V2.6-Pro는 공개 판단 평가에 오르지 않았다.

**③만 다르다**: Jev Decision Index(2026-10-15판)는 같은 세대 Qwen3.8-27B를 고치지 않고 지시만으로 돌린 결과를 싣고 있다.

### 9. 자료 속 지시 찾기

**지금 방식**: 검색이나 실행 도구가 없는 주 모델의 새 대화가 찾는다. 이미 주 모델이 맡고 있다.

| 재정렬은 Qwen3-Reranker 자체가 언어 모델에 예/아니오를 묻는 구조이니, ③의 주 모델이 같은 질문을 하면 된다 | 이론으로는 가능하고 ③에서 메모리 4.3GiB가 빈다. 하지만 미세조정 없이 같은 점수가 나온다는 자료는 찾지 못했다. 판단 모델 순위표에서는 같은 기반이라도 미세조정판(d3 66.26)이 지시만 준 판(51.79~54.72)보다 11~14점 높았다 |

## 표본과 출처의 치우침

- 한국어 점수 대부분은 이해관계가 있는 곳이 만든 표에서 왔다. KURE 표는 KURE-v2를 만든 연구실이 만들었고, MDPBench는 MonkeyOCRv2를 만든 연구실이 운영한다. KoOCR-Bench도 schift-ocr를 만든 회사가 만들었다.
- 판단 모델 순위표는 문제의 절반을 공개하지 않고 관리자가 직접 돌린다. 그래서 개발사 점수만 있는 것보다는 낫다. 다만 d3가 나온 지 6일이라 바깥에서 재현한 글은 아직 없다.
- 실사용자 측정 한 건(2026-09-28 블로그)은 d3 27B 4비트를 M2 Max에서 돌려, 지시 탐지 AUC 0.990에 메시지당 6.8초를 쟀다. 전체 1,947건 가운데 시험 718건으로 잰 개인 측정이다.
- 순위표에 오른 모델만 봤으므로, 평가에 내지 않은 모델은 빠졌다. 특히 주 모델 넷이 거의 모든 전용 평가에 없다. 이것이 주 모델 판정의 가장 큰 빈자리다.

## 이 분석이 답하지 않는 것

- 주 모델 넷의 한국어 판독, 받아쓰기, 개인정보, 재정렬, 판단 점수. 공개된 것을 찾지 못해 "같거나 높다"를 확인하지 못했다.
- 계약서와 판결문에서 개인정보 탐지 모델이 놓치는 비율. 공개 시험은 대화와 서식뿐이다.
- 각 환경에서 실제로 걸리는 시간. 페이지당 50~100초는 문서의 속도 기준으로 셈한 값이다.
- Reddit과 X의 원 글. 직접 받기가 막혀 검색 결과로만 봤다.

## 가정

- 질문 하나에 재정렬과 판단을 거치는 후보는 수십 건이다.
- ③의 주 모델은 문서의 하한 속도(초당 30토큰)에 가깝게 돈다.
- ①에서도 바깥 모델에 넘기기 전에 개인정보를 가리는 문서의 규칙이 그대로다.

## 다음에 할 일

1. ③에서 Jev Decision Index 공개 묶음을 공식 실행기로 Qwen3.8-Flash-Next에 돌린다. 54.90 이상이면 d3-mini를 빼고 주 모델이 판단한다.
2. KoOCR-Bench 채점 코드로 MonkeyOCRv2-S-Parsing을 잰다. 0.7483 근처면 교체를 확정하고, MinerU-4(0.7523)보다 크게 낮으면 MinerU-4를 다시 본다.
3. 임베딩을 Nemotron-3-Embed-8B로 바꿀 때 회사 한국어 질문 표본으로 Qwen3-Embedding-8B와 상위 10건 검색 품질을 견주고, 높으면 세 환경의 색인을 함께 다시 만든다.

## 지시 밖에서 찾은 것

- ①의 PC에서 d3 27B를 4비트로 돌리면 메시지당 6.8초가 걸렸다(M2 Max 실사용자 측정). 검색 결과 수십 건을 가리면 몇 분이 된다. ①의 PC 사양이나 d3-flash로 낮출지를 따로 정해야 한다.
- `재료 별 구현.md`의 "d3 계통은 … Jev보다 점수가 높고"는 ③의 d3-mini(52.61)에는 맞지 않는다. Jev 1.14는 61.53이다. 앞선 조사가 짚었지만 문서에는 아직 그대로 있다.
