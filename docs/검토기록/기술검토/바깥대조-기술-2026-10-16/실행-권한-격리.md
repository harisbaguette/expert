# 실행, 권한, 격리 기반 기술 바깥 대조 (2026-10-16)

## 결론

- 9개 선택 가운데 7개(Temporal, Cedar, OpenBao, gVisor, PostgreSQL, Playwright, LiveKit)는 그대로 둔다.
- 원본 보관 저장소는 문서에 제품 이름이 없었다. 이번에 Ceph RGW로 새로 정한다.
- ①의 고객별 기억은 PC의 SQLite에서 사내 서버 PostgreSQL로 옮긴다.

환경 번호는 원본 문서를 따른다. ①은 한 사람 PC의 Claude Code나 Codex와 사내 서버의 상주 프로그램이다. ②는 사내 서버(GPU 메모리 1.5TB 이상, vLLM)다. ③은 사내 서버와 DGX Spark 한 대(llama.cpp)다.

후보는 다섯 기준을 차례로 적용해 걸렀다.
- 기준 1: 세 환경 모두 사내에 설치할 수 있다.
- 기준 2: 바깥 서비스가 끊겨도 멈추지 않는다.
- 기준 3: 공개 평가가 있으면 점수가 가장 높은 것을 고른다.
- 기준 4: 같은 일을 하는 부품을 이미 쓰고 있으면 그것을 쓴다.
- 기준 5: 부품 수가 적은 것을 고른다.

| 지금 선택 | 판정 | 결정적 이유 |
|---|---|---|
| Temporal | 유지 (조건 1) | PC가 사내 서버로 먼저 연결해 일을 받아 오는 구조와, 한 업무를 하위 업무로 나눠 맡기는 기능(Child Workflow)을 함께 갖췄다. DBOS는 PC마다 DB에 직접 붙여야 하고, Restate는 PC가 들어오는 연결을 열어야 한다. 같은 구조의 Hatchet으로 바꿔도 얻는 것이 없다 |
| Cedar | 유지 | 새 규칙이 운영하는 쪽이 정한 최대 범위를 넘지 않는지 기계로 증명하는 도구를 갖춘 권한 엔진은 Cedar뿐이다 |
| OpenBao | 유지 (조건 2) | 2.7 버전부터 PostgreSQL 저장이 운영용 고가용과 수평 확장을 지원해, 이미 있는 DB를 다시 쓸 수 있다. Vault는 IBM 유료판과 경쟁하는 제공을 막는 BSL 라이선스이고, Infisical은 일부 기능이 유료다 |
| gVisor | 유지 | 2026-06 독립 비교 연구에서 작은 가상 머신(microVM) 셋과 일반 컨테이너(runc)를 포함한 다섯 제품 가운데, 여섯 보안 축 중 다섯 축에서 가장 강했다 |
| Object Lock 저장소 | 새로 정함: Ceph RGW (조건 3) | 권한 받은 계정만 풀 수 있는 잠금(Governance), 아무도 못 푸는 잠금(Compliance), 기간 없이 거는 보류(Legal Hold)를 모두 공식 문서로 보장한다. 다른 후보는 유지가 끊겼거나(MinIO), 기능이 없거나(Garage), 잠금 권한 결함을 2026-09에야 고쳤다(SeaweedFS) |
| PostgreSQL | 유지 (조건 4) | 행 수준 접근 제어, 진행 기록, 앞선 결론 목록을 한 부품이 맡고, Temporal, OpenBao, 바뀐 기억 저장까지 같은 부품에 기댄다 |
| SQLite (① 고객별 기억) | 교체: 사내 서버 PostgreSQL | ①도 진행 상태와 앞선 결론을 이미 사내 PostgreSQL에 둔다. 서버가 멈추면 Temporal도 멈추므로 PC에 따로 두어 얻는 것이 없다 |
| Playwright | 유지 | 한 API로 Chromium, Firefox, WebKit을 다룬다. 문서가 이미 ①의 자체 MCP 서버를 Playwright 위에 두고 있어, 같은 일을 하는 Selenium이나 Chrome 전용 도구로 바꿀 까닭이 없다 |
| LiveKit | 유지 (조건 5) | 통화 중계 서버, 전화망 연결(SIP), 음성 에이전트 틀을 모두 Apache-2.0 라이선스로 사내 설치할 수 있다. 대안 Pipecat은 음성 에이전트 틀이라 통화 중계 서버를 따로 둬야 한다 |

유지하거나 새로 정한 선택에 붙는 조건은 다섯이다.
1. Temporal의 저장 DB는 Temporal이 시험한 PostgreSQL 16.x에 둔다. 18.x에서 Temporal 시험 묶음을 모두 통과하면 업무 DB와 같은 클러스터에 둔다.
2. OpenBao는 PostgreSQL 저장 백엔드를 쓴다. 업무 DB와는 데이터베이스와 계정을 나눈다.
3. Ceph RGW는 cephadm으로 사내 서버 한 대에 띄운다. 업스트림 버전에서 아래 "다음에 할 일" 2번의 잠금 시험을 통과해야 쓴다.
4. PostgreSQL은 18.x로 시작한다. 19는 정식 출시 뒤 첫 소버전(19.1)이 나오면 올린다.
5. LiveKit은 클라우드 인증이 필요한 소음 제거(Krisp, ai-coustics)를 쓰지 않는다. SIP 서버를 위한 Redis가 부품으로 하나 붙는다.

## 1. Temporal (단계 잇기, 끊긴 뒤 이어 가기, Child Workflow)

**원본 문서에서 하는 일.** 세 환경 모두 단계를 잇고, 끊긴 단계부터 다시 시작하는 일을 맡는다. ①에서는 PC 상주 프로그램이 사내 서버의 Temporal에서 자기 대기열의 일을 받아 하네스를 돌린다. 일을 나눠 맡길 때는 Child Workflow를 쓴다.

**확인한 사실**
- 최신 버전은 v1.32.1(2026-10-08)이다. 라이선스는 MIT다.
- 워커가 사내 서버에 먼저 요청을 보내 대기열(Task Queue)의 일을 가져간다. 그래서 PC는 들어오는 연결을 열 필요가 없다.
- Child Workflow는 부모 업무와 다른 워커 묶음이 처리할 수 있다. 고객별 PC 대기열로 나눠 맡기는 설계와 맞는다.
- Temporal이 공식으로 시험하는 PostgreSQL은 13.18, 14.15, 15.10, 16.6이다. 18은 이 목록에 없다.
- SQLite 저장은 개발과 시험용이다.
- 사내 설치에 바깥 의존은 없다. 2026년에 나온 Serverless Workers만 AWS Lambda와 Cloud Run용이다.

**견준 대안**

| 대안 | 최신 버전(날짜) | 라이선스 | 걸리는 점 |
|---|---|---|---|
| DBOS | Python 3.3.0 (2026-10-15) | MIT | 별도 서버 없이 Postgres만 쓴다. 대신 모든 실행 프로세스가 같은 시스템 DB에 직접 붙어야 해서, ①의 PC마다 DB 접속 권한을 줘야 한다 |
| DBOS Conductor | 위와 같음 | 독점 | 프로세스가 죽었을 때 다른 프로세스로 옮겨 잇는 일을 맡는다. 사내 설치판에 라이선스 키가 필요하다 |
| Restate | v1.8.0 (2026-10-14) | BSL 1.1 | 공개 Restate 서비스로 제공하는 것을 막는 라이선스다. 서버가 등록된 서비스 주소를 직접 호출하므로, ①의 PC가 들어오는 연결을 열어야 한다 |
| Hatchet | 2026-10-09 | MIT | API 서버, 엔진, PostgreSQL로 이뤄지고 워커가 gRPC로 붙는다. Temporal과 같은 구조라 바꿔서 얻는 것이 없다 |
| Inngest | v1.46.0 (2026-10-06) | SSPL | 오픈소스 정의에 들지 않는 라이선스다 |
| microsoft/pg_durable | v0.2.9 (2026-10-07) | PostgreSQL License | DB 확장으로 영속 실행을 한다. 2026-02에 공개된 0.x 버전이다 |
| Absurd | 0.5.0 (2026-08-04) | Apache-2.0 | 저장소가 스스로를 "An experiment in durability"라고 소개한다 |

공개 성능 수치는 모두 업체가 직접 쟀고 장비가 서로 다르다. DBOS는 96 vCPU DB 한 대에서 초당 43K 워크플로(2026-04-23)를 냈다. Restate는 초당 94,286 단계(2025-02-20)를 냈다. Hatchet은 초당 10k까지 시험했다고 적었다. 같은 조건으로 Temporal과 견준 독립 평가는 없어서, 기준 3으로는 순위가 갈리지 않는다.

**판정: 유지.** 기준 1과 2는 모든 후보가 통과한다. 기준 3은 비교할 평가가 없다. 기준 4와 5에서는 DBOS가 부품이 하나 적다. 하지만 PC마다 시스템 DB 접속을 열어야 한다. 이는 원본 문서의 "에이전트가 쓰는 계정에 실행 프로그램 밖에서 직접 실행할 권한을 주지 않는다"와 부딪친다. 저장 DB에는 결론의 조건 1이 붙는다.

## 2. Cedar (권한 규칙과 정책 분석)

**원본 문서에서 하는 일.** 세 환경이 같은 규칙으로 실행 요청을 검사한다. ①에서는 훅이 Cedar를 부른다. 규칙을 적용하기 전에는, 운영하는 쪽이 정한 최대 범위 밖을 허락하는 요청이 없는지 기계로 증명한다. 그런 요청이 있으면 그 예를 받는다.

**확인한 사실**
- 최신 버전은 4.13.0(2026-09-15)이다. 2026년에 4.9.0부터 4.13.0까지 여덟 번 나왔다. 라이선스는 Apache-2.0이다.
- 2025-10-08에 CNCF Sandbox 프로젝트로 승인됐다.
- 분석 도구 SymCC는 정책을 논리식으로 바꾸고, 논리식 풀이 도구 cvc5 1.3.1로 검사한다.
- SymCC는 한 정책 집합이 다른 집합 안에 드는지 검사한다. 원본 문서의 "최대 범위 밖을 허락하지 않음"이 이 검사다.
- 이 밖에 정책이 오류를 내지 않는지, 늘 허용하거나 늘 거부하는지, 두 집합이 같은지, 겹치지 않는지도 검사한다.
- CLI에서는 4.10.0부터 `cedar symcc`로 쓴다. 바깥 의존은 없다.

**견준 대안**
- OPA v1.21.2, OpenFGA v1.22.0, SpiceDB v1.56.2, Cerbos v0.56.0, Permify v1.7.5, Topaz v0.33.22, Casbin v3.11.0은 모두 2026-08~10에 새 버전을 냈다.
- 이 가운데 정책 집합의 포함 관계를 기호 증명으로 보이는 기능을 가진 것은 없었다.
- Cerbos는 자기 비교 페이지에 "Cerbos schemas, compile checks, and policy tests do not replace a symbolic prover"라고 적었다.
- 속도 수치는 Cedar 저자들의 논문(OOPSLA 2024)에만 있다. 이 논문은 Cedar 3.0.1로 쟀다. 다른 절과 같은 기준으로 업체가 직접 잰 수치는 판정에 쓰지 않았다.

**판정: 유지.** 원본 문서가 Cedar를 고른 까닭인 정책 분석 도구를 가진 엔진은 지금도 Cedar 하나다.

## 3. OpenBao (비밀값)

**원본 문서에서 하는 일.** 인증 정보를 보관하고, 승인된 실행 프로그램만 꺼내 쓰게 한다. ①에서는 상주 프로그램이 업무마다 그 업무 권한만 담은 짧은 토큰을 받아 넘긴다.

**확인한 사실**
- 최신 버전은 v2.7.1(2026-10-01)이다. 라이선스는 MPL-2.0이고, Linux Foundation의 OpenSSF 아래에서 운영된다.
- v2.7.0(2026-09-23)이 PostgreSQL 저장의 수평 확장을 더했다.
- 공식 문서는 PostgreSQL 저장 백엔드를 "production ready"라고 적는다. 고가용을 지원하고, 최소 PostgreSQL 버전은 9.5다.
- 파일 저장 백엔드는 v2.7에서 없어졌다.

**견준 대안**
- Vault v2.2.0(2026-10-15)은 IBM의 BSL 1.1 라이선스다. 사내 운영은 허락하지만, IBM 유료판과 경쟁하는 방식으로 남에게 제공하는 것을 막는다.
- Infisical v0.166.8은 MIT 핵심에 유료 부분이 붙어 있다. 사내 설치에 PostgreSQL과 Redis가 필요하다. 유료 기능은 라이선스가 끝나면 꺼진다.
- SOPS는 파일 암호화 도구라 서버가 하는 일을 하지 못한다. SPIRE는 워크로드 신원을 맡아 역할이 다르다.

**판정: 유지.** 기준 4에 따라 이미 있는 PostgreSQL을 저장소로 쓴다. 그러면 별도 저장 노드를 운영하지 않아도 된다(조건 2).

## 4. gVisor (컨테이너 격리)

**원본 문서에서 하는 일.** ②와 ③에서 코드를 실행하고, 바깥 파일을 열고, 숨긴 글 검사를 위해 자료를 그리는 일을 사내 서버의 gVisor 컨테이너가 맡는다.

**확인한 사실**
- 최신 버전은 release-20261005.0(2026-10-08)이다. 거의 매주 새 버전이 나온다. 라이선스는 Apache-2.0이다.
- x86_64와 ARM64를 지원하고, Linux 5.6 이상이 필요하다.
- 바깥 의존은 없다.

**견준 대안과 공개 평가**
- 독립 비교 연구 「AI Code Sandboxes: A Comparative Security Study, Part 1」(arXiv 2606.08433, 2026-06-07)이 있다.
- 이 연구는 Cloud Hypervisor, Firecracker, libkrun(세 가지 모두 작은 가상 머신), gVisor, runc(일반 컨테이너)를 여섯 보안 축으로 쟀다.
- 연구는 gVisor에 대해 "the security posture is the strongest in the set on five of six axes"라고 적었다.
- 호스트 공격면은 14개 가운데 5개만 닿아 가장 좁았다. 격리를 뚫는 공개 취약점은 0건이었다.

- kubernetes-sigs/agent-sandbox v1.0.7은 격리를 gVisor나 Kata에 맡기는 관리 도구라, 대체재가 아니다.

## 5. Object Lock 저장소 (고칠 수 없는 원본 보관)

**원본 문서에서 하는 일.** 세 환경 모두 같은 저장소를 쓴다. ①은 상주 프로그램이 실행 기록과 받은 원문을 사내 서버로 보낸다. 원본 문서와 도구 결과 본문은 보관 기간 동안 고치거나 지울 수 없게 잠근다. 따로 권한을 받은 계정만 잠금을 풀고 지울 수 있다. 해시 값과 식별자는 아무도 지우지 못하게 잠근다.

이 요구는 S3 잠금 기능 세 가지와 그대로 맞는다.
- Governance 모드: 우회 권한을 받은 계정만 잠금을 풀 수 있다.
- Compliance 모드: 아무도 잠금을 풀 수 없다.
- Legal Hold: 기간 없이 걸어 두는 보류다.

**후보별 확인한 사실**

| 후보 | 최신 버전(날짜) | 라이선스 | 잠금 기능 | 걸리는 점 |

| Ceph RGW | Tentacle v20.2.4 (2026-08-18). Tentacle 첫 버전은 2025-11-18 | LGPL-2.1 또는 LGPL-3 | 세 가지 모두 있다. Compliance 모드는 RGW 관리자도 S3로 지우거나 기간을 줄일 수 없다 | 데몬이 여럿이라 부품이 많다 |
| MinIO | RELEASE.2025-10-15 | AGPL-3.0 | 있다 | 2026-04-25에 저장소가 보관 처리됐다. README에 "NO LONGER MAINTAINED"라고 적혀 있다 |
| RustFS | 1.0.1 (2026-10-03). 1.0.0은 2026-09-16 | Apache-2.0 | README에 "Object Lock (WORM)"이 있다 | 정식 버전이 나온 지 한 달이다. 2026-01 제3자 측정자는 클러스터 모드가 아직 성숙하지 않았다고 했다 |

- 업스트림 Ceph 프로젝트는 Compliance 모드에서 관리자도 S3로 지울 수 없다고 공식 블로그에 적었다.
- Ceph 계열에는 외부 평가도 있다. Cohasset은 상용판 IBM Storage Ceph가 바르게 설정되면 SEC 17a-4(f)(2) 기록 보관 요건을 충족한다고 결론냈다(2023-10). 이 평가는 업스트림판이 아니라 상용판 대상이다. 그래서 조건 3을 붙인다.
- 단일 바이너리인 RustFS와 SeaweedFS는 기준 5에서 앞선다. 하지만 잠금 결함을 막 고쳤거나 정식 버전이 나온 지 한 달이다.

**판정: 새로 정함, Ceph RGW (조건 3).** 이 잠금은 S3 API로 지우는 것을 막는다. 서버 root가 디스크를 직접 지우는 것은 막지 못한다. 그 경우는 원본 문서가 정한 해시 사슬과 서버 밖 매체 기록이 잡는다.

## 7. SQLite (① 고객별 기억)

**원본 문서에서 하는 일.** ①은 고객별 기억을 작업 폴더 밖 SQLite에 두고, 자체 MCP 도구로 두 하네스가 같은 형식으로 읽고 쓴다. 에이전트가 이 파일에 직접 쓰는 것은 하네스 권한 규칙으로 막는다. ②와 ③은 같은 기억을 PostgreSQL에 둔다.

**확인한 사실**
- 최신 버전은 3.54.0(2026-10-09)이다. SQLite 자체에는 문제가 없다.

- ①은 다음 단계도 사내 Temporal에서 받아 온다. 그래서 서버가 멈추면 SQLite가 살아 있어도 일은 멈춘다.
- 원본 문서는 기억을 꺼내 쓴 판단을 그 기억과 이어 두기로 했다. 지금은 기억이 PC에, 판단이 서버에 있어 이 연결이 두 저장소를 건넌다.

**견준 대안.** 사내 서버 PostgreSQL은 ②와 ③이 이미 쓴다. Turso v0.8.3은 SQLite를 새로 쓴 것이고 아직 0.x다. DuckDB는 ①이 이미 분석에 쓰지만, 작은 쓰기가 잦은 기억 저장에는 맞지 않는다.

**판정: 교체, 사내 서버 PostgreSQL.** 기준 4에 따라 세 환경에 이미 있는 PostgreSQL을 쓴다. 그러면 세 환경의 기억이 한 형식과 한 행 수준 접근 제어 아래 놓인다. 기억과 판단의 연결도 한 DB 안에 들어온다. PC에는 에이전트가 건드릴 기억 파일이 남지 않는다.

## 결론과 반대인 가설

- **"Temporal을 DBOS로 바꿔 부품을 줄여야 한다."** ②와 ③만 보면 맞다. DBOS는 이미 있는 PostgreSQL 위의 라이브러리다. 깨지는 곳은 ①이다. PC마다 시스템 DB 접속 권한을 줘야 하고, 장애 때 옮겨 잇는 일은 독점 라이선스의 Conductor가 맡는다. ②와 ③만 DBOS로 가면 엔진이 둘이 되어 기준 5에서 진다.
- **"Object Lock은 단일 바이너리인 RustFS나 SeaweedFS가 기준 5에서 이긴다."** 부품 수는 맞다. 하지만 잠금이 뚫리면 이 부품을 두는 의미가 사라진다. 그래서 잠금 보장을 먼저 봤다.
- **"SQLite를 PC에 두면 고객 자료가 서버에 덜 모인다."** 원본 문서는 ①의 판단 근거, 실행 기록, 받은 원문을 이미 사내 서버로 보낸다. 기억만 PC에 남겨도 줄어드는 노출이 거의 없다.
- **"gVisor보다 작은 가상 머신이 더 안전하다."** 독립 연구는 gVisor가 여섯 축 중 다섯 축에서 앞섰다고 적었다. Kata는 측정 대상이 아니었다.

## 편향과 한계

- **업체 수치.** 성능 수치 대부분은 업체가 직접 쟀다. 같은 조건의 독립 비교는 gVisor 연구 하나였다. 그래서 업체 수치는 판정에 쓰지 않았다.
- **후보 모으기.** GitHub 별과 Hacker News 언급으로 후보를 모았다. 상용 Object Lock 저장소(Scality RING, Dell ECS)는 사내 설치 오픈소스가 아니라 넣지 않았다.
- **한 회사가 이끄는 프로젝트.** Vault는 2023년에 BSL로 바뀌어 OpenBao가 갈라져 나왔다. MinIO는 2026-04-25에 보관 처리됐다. 유지한 일곱 개 가운데 재단 소속은 Cedar(CNCF), OpenBao(OpenSSF), PostgreSQL이다. Temporal, gVisor, Playwright, LiveKit은 한 회사가 이끈다.

## 이 조사의 범위 밖

- Playwright는 브라우저와 Electron만 다룬다. 원본 문서의 "화면에서 해야 하는 업무"에 데스크톱 프로그램이 들어가면 다른 도구가 필요하다.
- 실제 장비에서 잰 값은 없다. 실측은 아래 "다음에 할 일"에서 한다.

## 가정

- 사내 서버는 Linux 5.6 이상이다.
- ①의 PC는 사내 서버로 나가는 연결만 허용하고, 들어오는 연결은 열지 않는다.
- 잠금을 풀 수 있는 계정은 Governance 모드의 `s3:BypassGovernanceRetention` 권한으로 나타낼 수 있다.

## 다음에 할 일

1. Temporal 시험 묶음을 PostgreSQL 16.x와 18.x에서 각각 돌린다. 18.x에서도 모두 통과하면 Temporal 저장 DB를 업무 DB와 같은 클러스터에 둔다.
2. 업스트림 Ceph RGW를 사내 서버 한 대에 띄운다. Compliance 객체를 관리자 계정으로 지우는 시도 10건과, Governance 객체를 우회 권한 없는 계정으로 지우는 시도 10건이 모두 거부되는지 본다.
3. `재료 별 구현.md`의 원본 저장소 칸에 Ceph RGW를 넣고, ①의 장기 기억 칸을 사내 서버 PostgreSQL로 바꾼다.
