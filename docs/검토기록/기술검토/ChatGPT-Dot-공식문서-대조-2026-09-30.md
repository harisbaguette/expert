# 정의 1·2 보완안 — ChatGPT·dots 공식 문서 대조

확인일: 2026-09-30, 한국 시간. DevDay 공식 문서의 발표일은 미국 기준 2026-09-29다. 여기서 Dot은 이번에 공개된 ChatGPT의 개인 상시 에이전트 **dots**를 가리킨다. [DevDay 2026](https://learn.chatgpt.com/docs/whats-new/devday-2026), [Meet dots](https://learn.chatgpt.com/docs/dots).

**현재까지의 대조에서는 6개 구성 요소·9개 계통·79개 재료를 늘릴 근거를 찾지 못했다. 우선 보완할 곳은 문서 사이의 불일치와 제품별 구현 조건이다.** 지속 업무, 사건별 기억, 위임, 중단·복구, 전문가 비교 평가는 이미 정의·실행 명세·평가 문서에 있다. dots의 기능을 이 원칙을 충족하는 구현으로 쓸 수 있는지 대조해야 한다.

이 문서는 **보완의 근거와 제품 도입 조건**이다. 아래 ‘현재’는 보완 대상으로 대조한 내용을 가리키며, 적용할 구현 기준은 [재료별 구현](<../../../재료 별 구현.md>)를 따른다. 제품의 실제 동작과 계정별 지원 여부는 아직 시험하지 않았다.

**적용 범위:** 정의 1은 ‘재료별 구현 → AI 모델’까지 확정된 기준으로 둔다. 이번 보완은 기존 79개 재료의 이름·개수·책임과 구성·업무 흐름·사용 구조·세 실행 환경·모델 선정 기준을 유지하고, 정의 2의 구현 방법과 필요한 보조 문서에 반영한다. 기존 재료로 처리할 수 없는 필수 기능이 확인된 경우에만 정의 1 변경 필요성을 별도 검토한다. dots·Agents API 등은 기존 조건을 충족하는지 비교할 후보이며, 도입을 위해 확정된 기준을 바꾸지는 않는다.

정의 2의 ‘기술 고르기’는 정식 지원 기능만 채택한다. 따라서 기업용 dots의 베타, Permission profiles의 베타, 초안 규격에 의존하는 MCP Events는 비교·실험 후보로 두고 곧바로 운영 기본값으로 넣지 않는다. 기능을 공식 문서에서 찾았다는 사실과 현재 채택 조건을 충족한다는 판단은 별개다. [Dots 관리](https://help.openai.com/en/articles/20001554-manage-dots-in-chatgpt-workspaces), [Permissions](https://learn.chatgpt.com/docs/permissions), [MCP Events](https://developers.openai.com/plugins/build/mcp-events).

대상 정본: [정의 1](<../../../전문가 에이전트 정의 1.md>), [재료별 구현](<../../../재료 별 구현.md>), [진행 계획](../../../진행-계획.md).

## R01. ‘한 건’ 위에 계속 맡는 책임을 명시한다

**현재:** 정의 1에는 위임형·고용형·운영형이 있고, 정의 2에는 대기·후속 관리가 있다. 지속 업무라는 생각이 없는 것은 아니다. runtime.md에는 책임의 지속·종료·인계와 실행 상태 계약도 있다. 필요한 보완은 이 기존 계약을 dots의 본 대화·위임 작업·예약에 대응시키는 것이다.

**공식 사실:** Dot은 대화가 끝난 뒤에도 맡은 책임을 이어 가며, 후속 작업을 할 시점을 판단하고 별도 작업을 맡길 수 있다. 고정 주기의 반복 업무에는 저장된 예약을 쓴다. [Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory).

**정의 2에 넣을 내용:** ‘모든 재료가 주고받을 내용’과 ‘현재 진행 상태’에 상위 책임, 개별 업무, 실행 회차의 연결을 넣는다. 계속 맡는 책임에는 목적·담당·유효 기간·허용 범위·예산·다음 확인 시점·종료 조건을 둔다. 한 업무가 끝나도 책임이 끝난 것은 아니며, 책임을 끝낼 때는 남은 업무·약속·예약을 정리하거나 인계한다. 기존 지속 업무와 진행·후속 관리의 구현으로 처리하며, 새 재료를 추가하지 않는다.

## R02. ‘먼저 알아채기’에 가설을 세워 찾아보는 경로를 더한다

**현재:** 정의 2 ‘먼저 알아채기’의 명시된 경로는 감시 목록의 문턱값과 하루 한 번의 종합 판단이다. 목록에 없던 사건은 뒤늦게 발견한 뒤 학습·배포를 거친다. 한편 조건을 알아내기 위한 조회·진단과 사건 안의 조사는 이미 허용한다. 추가 후보는 이 진단 원칙 자체가 아니라, 계속 맡은 목적에서 새 조사 질문을 만드는 연결이다.

**공식 사실:** Dot의 선제 조사는 허용된 연결 자료를 읽고 개인 메모를 남길 수 있지만, 그 조사 도구로 메시지를 보내거나 앱을 수정하거나 브라우저·컴퓨터를 조작할 수 없다. 이미 위임한 업무의 백그라운드 실행은 이 선제 조사와 구별한다. [Dots privacy, security, and safety FAQs](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs).

**보완안:** 정의 2의 기존 감시에 ‘맡은 목적과 최근 변화에서 조사할 질문을 스스로 만드는 경로’를 더한다. 정의 1의 ‘먼저 알아채기’가 맡은 범위 안에서 새 문제·기회를 찾는 책임을 구현한다. 조사 범위·허용 원천·예산·중단 조건 안에서 읽기와 가설 비교를 수행하고, 발견한 문제·기회를 실행 계획으로 넘긴다. 실행은 기존 위임에 포함되는지 다시 확인한다. 매일 무조건 새 질문을 만들거나 새 규칙을 배포하게 하지는 않는다.

책임 재료는 ‘먼저 알아채기 → 정보·자료 찾기 → 분석 → 대안·전략 판단 → 업무 권한’이다. 기록은 발견 근거·예상 영향·확인 방법·대응 기한이면 된다.

## R03. 기존 협업 재료의 구현 연결을 보완한다

**현재:** 정의 1의 ‘나눠 맡기기’는 정보 전달·진행 수집·결과 통합·이견·실패 보완을 이미 맡고, ‘실행 제어’와 ‘현재 진행 상태’가 분기·합류·취소·재개를 맡는다. ‘사용 구조 2·3’은 제목만 있지만 그 본문과 그림을 채우는 일은 이번 수정 범위에서 제외한다. 보조 검토의 협력 규약은 정의 2의 구현에 참고한다.

**공식 사실:** Dot이 새로 만든 작업은 자기 대화와 필요한 문맥을 받으며, Dot의 모든 대화를 자동으로 받지는 않는다. 실행이 끝났다는 표시도 목표 달성이나 전달 완료를 보장하지 않는다. [Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory#assigned-work).

**보완안:** 정의 2의 나눠 맡기기·실행 제어·현재 진행 상태에 다음 관계를 연결한다.

| 한 건·여러 전문가 | 맞물린 여러 건·여러 전문가 |
|---|---|
| 최종 책임자와 분담별 책임자 | 책임 묶음과 개별 건의 소유자 |
| 전달할 입력·가정·근거·권한·완료 조건 | 공동 자원·예산·기한·상충 목표 |
| 공유할 상태와 공개하면 안 되는 상태 | 고객·당사자별 자료 경계 |
| 결과 회수·이견 해결·누락 보완·통합 검사 | 한 건의 변화가 다른 건에 미치는 영향 |
| 일부 실패·대기·취소·재위임 | 우선순위 변경·중단·재개·인계 |

정의 2의 기존 위임 계약에 **부모 책임과 취소 전파, 결과가 유효한 상태 판본, 다른 건에 알릴 변경**을 연결한다. 자식의 ‘완료’ 보고를 그대로 합격으로 바꾸지 않는 기존 ‘보고 주체 확인’ 원칙을 유지한다.

## R04. 일회 승인과 반복 위임을 같은 것으로 쓰지 않는다

**현재:** 정의 2 ‘업무 권한’은 모든 승인을 내용 해시에 붙여 한 번 쓰면 닫도록 한다. 그러나 ‘사람에게 넘기기’와 [runtime.md](../../runtime.md)는 이미 맡긴 범위의 반복 실행을 허용한다. 같은 업무가 절에 따라 매번 승인 대상이 되거나 자동 실행 대상이 되는 충돌이다.

**공식 사실:** Dot은 범위가 구체적인 지시로 미래 행동을 미리 승인할 수 있다. 다만 문안을 작성하라는 지시가 발송까지 허용하지 않으며, 제품의 필수 확인·사람 인계 조건을 사용자 규칙으로 없앨 수는 없다. [Controls](https://learn.chatgpt.com/docs/dots/controls#how-action-review-works).

**정의 2에 넣을 문장:**

> 승인은 한 번의 확정된 행동을 허용하는 승인과, 정한 범위 안에서 반복 행동을 허용하는 위임으로 나눈다. 반복 위임에는 대상·행동·내용 조건·수신자·기간·횟수·누적 한도·철회 조건을 둔다. 실행 직전에 현재 권한과 남은 한도를 확인하며, 유효한 위임 안의 같은 행동을 다시 승인받지는 않는다. 범위를 벗어나거나 반드시 실행 시점에 확인해야 하는 행동은 별도로 결정받는다.

일회 승인의 내용 해시와 재사용 방지는 유지한다. 반복 위임은 위임 판본과 각 실행의 고유 번호를 기록한다. ‘되돌릴 수 있는 쓰기는 허용’이라는 분류에도 **이번 목적·대상·공개 범위에 대한 권한 확인**이 먼저 들어가야 한다. 되돌릴 수 있는 외부 공유도 무단 공개가 될 수 있다.

## R05. ‘멈춤’의 대상을 기록한다

**현재:** 취소·재개와 외부 처리 조회는 이미 있다. runtime.md의 기존 취소·철회·잔여 작업 정리 계약을 본 대화·위임 작업·예약·이벤트 구독의 실제 중단 기능에 연결해야 한다.

**공식 사실:** Dot의 Pause는 현재 주 작업을 멈추며, 모든 위임 작업이나 미래 예약을 일괄 중단하지 않는다. Team Task의 일시 정지도 미래 실행을 막는 기능이며 진행 중인 실행을 멈춘다고 의존해서는 안 된다. [Dot controls](https://learn.chatgpt.com/docs/dots/controls#stop-work), [Team Tasks](https://learn.chatgpt.com/docs/enterprise/teams).

**보완안:** 정의 2의 실행 제어·현재 진행 상태·운영 감시에서 다음을 구별한다.

| 요청 | 확인할 대상 |
|---|---|
| 현재 응답 중단 | 현재 응답·도구 실행, 이미 맡긴 백그라운드 업무의 계속 여부 |
| 이 업무 중단 | 부모 실행·자식 실행·대기 중인 도구·이 업무의 재시도 |
| 계속 맡긴 책임 종료 | 위 항목과 미래 예약·이벤트 구독·후속 약속 |
| 접근 철회 | 실행 권한·연결 토큰·브라우저 세션·파생 자료 접근 |

우리 시스템은 요청 범위에 맞는 중단을 조정하고, 각 대상의 응답을 받아 **중단 확인·아직 실행 중·결과 미확인**으로 남긴다. 이미 전송·접수된 일은 별도로 조회하고 취소·보완한다. 부모 프로세스가 종료됐다는 이유로 전부 멈췄다고 보고하지 않는다.

## R06. 개인 위임과 조직 실행, 결과 공개 범위를 구별한다

**현재:** 정의 2는 ‘실행하는 에이전트·대신하는 본인·밖으로 이름이 나가는 명의’를 이미 구별한다. 다만 ‘서비스마다 전용 계정, 사용자 본인 로그인은 사용하지 않는다’가 모든 환경의 정답으로 고정되어 있다. 이는 고객·업무를 분리하기 위한 기존 선택이다. 개인 소유자의 연결을 사용하는 dots가 이 선택을 충족하는지 따로 판정해야 한다.

**공식 사실:** Team Tasks는 팀 서비스 계정과 설정된 연결을 사용한다. 만든 사람의 개인 기억·지침·대화 이력을 물려받지 않는다. 새 팀원은 이전 실행과 생성 파일을 볼 수 있고, 개별 작업·실행별로 별도 접근 제한을 둘 수 없다. [Team Tasks](https://learn.chatgpt.com/docs/enterprise/teams).

공유 연결은 연결된 외부 계정의 권한으로 동작하므로, 작업을 요청한 사람의 개인 접근 범위보다 넓을 수 있다. 출처 링크를 붙이는 것만으로 결과 수신자에게 원본 접근권이 생기지는 않는다. [Workspace connections](https://learn.chatgpt.com/docs/enterprise/shared-connections).

**보완안:** 기본은 기존 조직용 전용 계정을 유지한다. 개인용 도입을 허용한다면 공식 위임 인증 방식만 별도로 지원한다. 명의 세 줄에 연결 계정·요청자·책임 소유자·허용된 결과 독자를 연결하고, 조회 권한과 **결과를 공개할 권한**을 따로 검사한다. 연결을 설치했다는 사실을 모든 업무의 사용 승인으로 해석하지 않는다.

서로 자료를 공유할 수 없는 고객을 하나의 Team에 묶지 않는다. 담당자 퇴사·팀 이동 때는 책임·예약·연결의 소유권과 잔여 접근을 함께 확인한다. 별도로 만드는 ChatGPT 서비스 계정은 현재 종량제 요금제에서 제공하며, 그 토큰을 쓰는 Codex CLI는 `0.142.0` 이상이 필요하다. 개인 구독 계정과 같은 조건으로 설계하지 않는다. 서비스 계정도 만든 사람의 권한·연결을 자동 상속하지 않는다. [Service accounts](https://learn.chatgpt.com/docs/enterprise/service-accounts).

## R07. 제품의 기억을 고객별 정본 기록으로 쓰지 않는다

**현재:** 장기 기억에는 고객 격리·출처·유효 기간·철회가 이미 있다. 이를 새로 추가할 필요는 없다. 문제는 Dot의 개인 기억을 이 저장소와 동등한 구현으로 취급할 수 있느냐다.

**공식 사실:** 현재 dots가 자체적으로 남긴 메모는 개별 항목을 직접 조회·수정·삭제할 수 없다. ChatGPT와의 기억 공유는 양방향이며, 공유를 꺼도 이미 전달된 내용까지 지우지는 않는다. 연결 해제도 새 접근을 막을 뿐 이미 얻은 문맥을 지우지 않는다. Dot 삭제는 별도 보관된 파일·Codex 스레드·ChatGPT 대화와 기억까지 모두 지우는 동작이 아니다. [Dots privacy FAQ](https://help.openai.com/en/articles/20001529-dots-privacy-security-and-safety-faqs).

**보완안:** ‘현재 작업 정보·진행 상태·장기 기억’에서 제품 대화 문맥, 제품 개인 기억, 고객별 사실·결정 기록, 직무 공통 지식을 구별한다. 출처·판본·권한·정정·삭제를 관리할 고객 기록은 기존 저장소를 정본으로 유지한다. 개별 고객 기록의 정정·삭제·반출을 증명해야 하는 업무에는 그 조건을 충족하지 못하는 제품 기억을 저장 경로로 쓰지 않는다.

기억을 다른 채널에서 참고하는 것과 다른 독자에게 공개하는 것도 구별한다. [Dot messaging](https://learn.chatgpt.com/docs/dots/channels).

로컬 Codex 기억은 ChatGPT 기억과 별도 저장소·설정이다. 기존의 하네스 자동 기억 끄기 원칙을 유지하면서 제품을 바꿀 때 각 저장소의 사용·생성 설정을 따로 확인한다. 반드시 적용할 규칙은 자동 기억의 회상에 맡기지 않는다. [Memories](https://learn.chatgpt.com/docs/customization/memories).

## R08. 공식 관리형 경로가 기존 실행 조건에 맞는지 비교한다

**현재:** 정의 1의 ①은 ‘하네스·도구는 한 사람의 PC’로 설명되어 있다. ②·③은 자료를 사내에 두는 자체 실행 경로다. 세 환경과 모델 선정은 확정된 조건이다. 관리형 클라우드 제품은 이름이 비슷하다는 이유로 ①에 포함하지 않는다.

**공식 사실:** Agents API는 OpenAI가 Codex 하네스·세션·조정·문맥 압축·복구를 관리한다. 실행 환경은 OpenAI 호스팅, 자체 환경, 환경 없음으로 선택할 수 있다. 자체 환경의 생성·연결·종료·보존은 고객 애플리케이션의 책임이다. [Agents API overview](https://developers.openai.com/api/docs/guides/agents-api/overview), [Architecture](https://developers.openai.com/api/docs/guides/agents-api/architecture).

**보완안:** 아래 표는 조사 후보 비교표로만 사용한다. 기존 환경·모델·자료 보관 조건을 모두 충족하는 부분만 정의 2의 구현 후보로 다룬다. ①의 실행 장소를 클라우드로 바꾸거나 새 환경을 추가해야 하는 경로는 이번 구현 변경에서 제외한다.

| 경로 | 주 용도 | 재사용할 수 있는 것 | 별도로 확인할 것 |
|---|---|---|---|
| 로컬 Codex | 개인·팀의 로컬 업무 | 도구 실행·문맥 관리·위임 | 켜진 장비·고객 격리·권한·복구 |
| Work / Dot / Team Tasks | 대화로 맡기는 작업·상시 업무·조직 반복 업무 | 제품의 작업 관리·연결·예약·검토 화면 | 계정·요금제·배포 상태·기억·공개 범위 |
| Agents API | 우리 서비스에서 호출할 관리형 에이전트 | 관리형 하네스와 지속 세션 | 데이터 보관·실행 환경·도구 서버·업무 상태 |
| 자체 실행 기반 | 사내 데이터·로컬 모델·통제 요구가 있는 업무 | 현재 Temporal·LangGraph 등 설계 | 직접 구현·운영할 책임과 실제 비용 |

직무 지식·평가·권한·완료 증거는 공장에서 관리한다. Dot 자체를 임의의 외부 제품 백엔드로 호출하는 공개 API는 이번 공식 자료에서 확인하지 못했다.

최근 [상용 개발 후보 목록](../../바깥조사/agent-foundations-2026-09-30/상용개발-후보목록.md)은 SDK를 자체 제품에 넣는 경로를 비교한다. dots는 사용자가 이용하는 제품이고, Agents API는 업체가 실행 흐름을 관리하는 API이며, Agents SDK는 우리 코드에서 조립하는 라이브러리다. 같은 후보처럼 묶어 기능 수로 순위를 매기지 않는다. 고객 기록·업무 상태·완료 판정의 소유와 수정 가능 범위를 먼저 맞춘다.

현재 Agents API는 미국 데이터 레지던시만 지원하고 ZDR을 지원하지 않는다. 자체 샌드박스를 선택해도 이 조건은 바뀌지 않는다. 따라서 ‘자료가 회사 밖으로 나가면 안 된다’는 ②·③을 그대로 대체할 수 없다. [Agents API data controls](https://developers.openai.com/api/docs/guides/agents-api/overview).

또한 Dot의 클라우드 컴퓨터와 연결된 로컬 컴퓨터는 서로 다른 실행 장소다. 로컬 장비의 로그인·VPN·파일이 클라우드에 자동으로 이어진다고 쓰지 않는다. [Computers and apps](https://learn.chatgpt.com/docs/dots/computers-and-apps).

## R09. 시작 신호는 공식 예약·이벤트 기능부터 비교한다

**현재:** 정의 2는 별도 수신 프로그램과 예약 실행기를 기본으로 두고 있다. 신호 보존·중복 제거·재개의 책임은 유지하되, 지원되는 경로를 직접 다시 만들 필요가 있는지 재검토해야 한다.

**공식 사실:** ChatGPT의 지원 요금제·화면에서는 예약과 앱 이벤트로 작업을 시작할 수 있다. 이벤트 기능이 모든 데스크톱·CLI·IDE 화면에 똑같이 있는 것은 아니다. [Scheduled tasks](https://learn.chatgpt.com/docs/automations).

MCP Events는 현재 MCP 2.0의 `2026-07-28` 프로토콜과 초안의 webhook 전달을 지원한다. 서버는 구독·갱신·해제·서명·권한 철회를 처리해야 한다. `2xx`는 수신 확인이며 업무 성공 확인이 아니다. 중복·역순·재전송과 되먹임도 시험 대상이다. [MCP Events](https://developers.openai.com/plugins/build/mcp-events).

**보완안:** ‘시작 신호’의 수단 선택을 ‘필요한 이벤트·주기·인증·실패 복구를 공식 기능이 충족하는가 → 부족한 부분만 수신기·스케줄러로 구현’으로 바꾼다. 현재의 사건 번호·중복 방지·상태 조회를 연결하는 어댑터를 둔다.

구독의 수명·갱신 실패·권한 철회·재시작 후 빠진 구간 확인을 계약에 포함한다. 재생할 수 없는 이벤트 원천은 주기적 원본 조회 등 별도 누락 확인 방법이 필요하다. ChatGPT 쪽 현재 통합이 지원하지 않는 polling·streaming·`gap`·`terminated` 제어 알림을 이미 지원하는 것으로 구현하지 않는다. [MCP Events integration limits](https://developers.openai.com/plugins/build/mcp-events#before-you-start).

## R10. 공장 배포물에 skill·MCP·plugin 표준을 연결한다

**현재:** 직종별 지식·기술 파일·도구 연결·배포 판본은 이미 있다. 이를 여러 실행 제품에서 설치하고 시험할 수 있는 패키지 형태가 더 필요하다.

**공식 사실:** 플러그인은 skill, MCP 서버, 선택적 UI와 훅을 묶을 수 있다. skill은 절차·자료·성공 조건을, 서버는 실제 데이터·인증·권한·통제된 행동을 맡는다. 웹에서 설치했다고 로컬 훅 스크립트까지 배치되는 것은 아니다. [Plugin architecture](https://developers.openai.com/plugins/concepts/plugins), [Build skills](https://developers.openai.com/plugins/build/skills).

**보완안:** ‘공장 설계’에 직종 구성을 표준 패키지로 내보내는 단계를 둔다. 현재 portable Agent Plugins 형식의 루트 `plugin.json`, `skills/`, 필요할 때 `mcp.json`을 우선 검토하고, OpenAI 전용 설정은 해당 확장 필드로 둔다. 기존 형식을 쓰는 배포와의 호환은 따로 검사한다. [Package your plugin](https://developers.openai.com/plugins/build/plugins).

직종 하나가 무조건 MCP 서버 하나를 필요로 하지는 않는다. 기존 도구로 충분하면 skill만 묶는다. 고객 기록·비밀 키·진행 상태는 배포물에 넣지 않는다. 패키지를 만들었다는 검사와 실제 직무를 해냈다는 검사를 분리한다.

**확인할 시험:** 같은 직종 패키지로 필요한 화면·실행 환경에서 설치, 도구 인증, 절차 선택, 결과 검사까지 되는가. MCP에서 가져온 skill을 바꾼 경우 새 버전을 다시 가져오고 배포했는가. 공식 가져오기는 실행 때마다 최신 파일을 읽는 방식이 아니라 스냅샷이다. [Import skills from MCP](https://developers.openai.com/plugins/build/skills#import-a-skill-from-mcp).

## R11. 모델 선정 정책과 허용 업무 검증을 구분한다

**현재:** 모델은 AA 지수와 속도 기준으로 고르고, 내부 업무 시험으로 모델을 선택하거나 이전 모델로 되돌리지 않는다는 결정이 있다. 모델 지정도 배포 판본에서 분리한다. 이 결정을 업무 시험 기반 모델 선정으로 바꾸는 것은 이번 보완 범위에 넣지 않는다.

**보완안:** 모델 선정, 실행 기록, 허용 업무를 분리한다. 선택은 기존 기준을 따르되, 실행 당시 사용한 모델·추론 설정·하네스·지침·도구 판본은 결과 기록에 남긴다. 모델 지정이 배포 판본 밖에 있어도 어떤 조건의 성적인지는 추적할 수 있어야 한다. 새 모델이나 실행 환경에서 필수 능력이 확인되지 않으면 해당 업무의 허용 범위를 좁히고 재검증한다. 내부 시험은 이 범위를 결정하며 모델 선정 기준을 대신하지 않는다.

**공식 사실:** dots에는 작업 공간의 일반 모델 설정·기본값이 적용되지 않는다. 따라서 정한 모델을 반드시 사용해야 하는 업무에 dots를 넣으려면 실제 모델을 확인·통제할 수 있는지 먼저 판정해야 한다. 현재 공식 안내만으로 그 조건이 충족됐다고 볼 수 없다. [Manage dots in ChatGPT workspaces](https://help.openai.com/en/articles/20001554-manage-dots-in-chatgpt-workspaces).

기존 [evaluation.md](../../evaluation.md)의 미공개 과제·동일 조건의 전문가 비교·채점 오류·표본 기준을 유지한다. 정의 2의 과제 5회 통과와 좋은/나쁜 견본 각 3개 구별은 초기 연결 확인에 쓸 수 있지만, 이것만으로 운영 성능을 입증하지 않는다. 오류 0건일 때의 `3 ÷ 허용 오류율`도 독립적인 성공·실패 관측에 쓰는 근사이며, 서로 연관된 사례나 연속 점수의 전문가 비교에 그대로 적용하지 않는다.

기존 검토의 수치도 같은 기준으로 구분한다. 판례 27건의 ‘전문가 대비 %’는 [대입 기준](../판례27건-스트레스검토/대입-기준.md)이 요구한 추정치다. 실제 에이전트와 전문가에게 같은 과제를 주어 얻은 성적이 아니다. 일부 사건은 장문 원문의 일부만 읽었다고 명시돼 있다. 예를 들어 [R04](../판례27건-스트레스검토/대입/R04.md)는 긴 줄의 앞부분만 읽은 구간이 있고, [R15](../판례27건-스트레스검토/대입/R15.md)는 약 86.9만 자 중 약 8.5만 자를 골라 읽었다. 따라서 이 수치는 보완 후보를 찾는 참고로만 쓰고 대체 능력의 근거로 집계하지 않는다.

현재 순서도에서 이미 고친 조건도 과거 결함으로 다시 추가하지 않는다. `CASE_CHANGED`의 사실·규칙·당사자 변화, `VALIDATE_DATA`의 취득 경로·증거능력·구속력, `KNOWN_CASE`의 적용 범위·해석 갈림, `COMPARE`의 쟁점 간 영향·제3자 동의가 그 예다. 남은 검증은 해당 조건을 실제 사례에서 찾아 적용하는지이며, 그림에 조건이 있다는 사실만으로 통과시키지 않는다.

**기존 시험에 더할 상황:** 권한 변경 후 여러 작업·문맥 압축·재개가 이어지는 경우, 부모는 멈췄지만 위임 작업은 계속되는 경우, 채널과 결과 독자가 달라지는 경우. OpenAI도 지속·선제 작업의 범위 유지를 별도로 평가한다. 그 평가를 우리 직무의 대체 성적으로 옮기지는 않는다. [Persistent and proactive workflow evaluations](https://deploymentsafety.openai.com/gpt-6-astra/alignment-in-persistent-and-proactive-workflows).

## R12. 훅만으로 승인·격리·완료를 보장하지 않는다

**현재:** 정의 2는 여러 절에서 훅을 승인 차단·기록·완료 확인의 핵심 구현으로 쓴다. 오늘 작성된 근거 문서도 훅 오류 때 실행이 계속될 수 있음을 알고 있지만, 훅이 자기 오류를 잡아 거부하도록 하면 해결된다고 본다. 프로세스가 실행되지 않거나 강제 종료되면 훅 내부 오류 처리는 작동할 수 없다.

**공식 사실:** Codex의 hosted `WebSearch`는 로컬 `PreToolUse`·`PostToolUse` 경로를 타지 않는다. 기존 실행에 입력을 보내는 `write_stdin`도 `PreToolUse`를 다시 거치지 않는다. 일부 훅 실패·시간 초과·지원하지 않는 응답은 도구를 막지 않는다. [Hooks — coverage and failure behavior](https://learn.chatgpt.com/docs/hooks).

**보완안:** 업무 권한·안전장치·분리 실행에 실제 실행 경로별 차단 위치를 둔다. 파일은 OS 권한·지원되는 sandbox, 네트워크는 실행 환경의 통제, 외부 쓰기는 자격 증명을 가진 서버·연결부에서 승인과 한도를 재검사한다. 훅은 지원되는 경로의 보조 검사와 기록에 쓴다. 우회 경로까지 동일한 조건이 강제되는지 시험하고, 확인하지 못한 경로에는 고위험 권한을 주지 않는다.

Dot·Work Cloud의 조정 위치와 로컬 실행 위치도 구별해야 한다. 관리형 원격 MCP 훅은 적용 조건과 지원 이벤트가 제한되며 로컬 command 훅이 자동으로 클라우드에 적용되지는 않는다. 정책 기본값과 사용자가 바꿀 수 없는 요구 조건도 구별한다. [Agent Security](https://learn.chatgpt.com/docs/enterprise/agent-security).

Permission profiles를 시험할 때도 설정 파일의 존재만 확인하면 안 된다. 네트워크 도메인 제한은 프록시가 실제로 켜져 있어야 적용되며, 명령의 네트워크 제한은 hosted 검색·MCP·브라우저까지 덮지 않는다. 기존 `sandbox_mode`와 새 프로필을 섞었을 때의 우선순위도 확인한다. 각 실행 경로에서 허용할 행동과 막을 행동을 실제로 대조한다. [Permissions — scope and enforcement](https://learn.chatgpt.com/docs/permissions#scope-and-enforcement).

Codex Auto-review는 적용되는 승인 요청을 별도 검토자가 검토하는 기능이다. `approval_policy = "never"`로 승인 요청이 발생하지 않는 경로까지 모두 검사해 주는 장치로 쓰지 않는다. [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review).

## R13. 필요한 절차·도구만 올리고, 모델별 지침을 재검토한다

**현재:** 정의 2는 절차 본문을 필요할 때 읽도록 이미 설계했다. 좋은 방향이다. 다만 모든 도구 목록을 앞부분에 고정하고, 바뀌면 새 대화로 옮기는 규칙은 도구 수가 늘어날 때 별도 검토가 필요하다.

**공식 사실:** Tool search는 필요한 도구 정의를 뒤쪽 문맥에 로딩해 캐시를 유지하도록 설계되어 있다. Responses API와 Agents API의 설정 방법은 같지 않다. [Tool search](https://developers.openai.com/api/docs/guides/tools-tool-search).

OpenAI는 Astra용 skill·AGENTS.md에서 불필요한 상세 절차, 과도한 사전 문서 읽기, 반복 검사, 무조건 사용하라는 긴 설명을 재검토하도록 안내한다. 강제 절차가 오히려 필요한 작업을 멈추게 할 수 있다는 취지다. [Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).

**보완안:** 현재 작업 정보에는 짧은 역할·목표·완료 조건·유효한 권한과 필요한 자료를 둔다. 절차·도구는 허용된 목록 안에서 필요할 때 읽고, 대규모 목록에는 검색·지연 로딩을 비교한다. 도구를 문맥에 읽었다는 사실과 실행 권한을 얻었다는 사실은 구별한다. 캐시보다 권한 철회·규칙 갱신이 우선이다.

공장 배포 때 ‘이 지침이 필요한 모델·직무·상황’을 확인하고, 제거 전후의 품질·중단·토큰·시간을 비교한다. 법·계약·고객 조건을 줄이라는 뜻은 아니다. **행동을 과하게 지시하는 문장과 실제로 강제할 조건을 나누는 일**이다.

## R15. 현재 기준 문서의 대응을 바로잡는다

본문 표를 직접 세면 정의 1의 재료는 **79개**, docs/materials.md의 본문 대응표는 **77개**다. 대응표에서 빠진 이름은 **‘못 찾음·없음 구분’과 ‘보고 주체 확인’**이다. docs/README.md도 현재 기준을 77개라고 설명한다.

**보완안:** 정의 1의 이름·계통·책임을 기준으로 현재 대응표와 전개 수식 생성기의 입력을 맞춘다. 사용 구조 생성기는 이미 79개를 기준으로 하므로 함께 구버전으로 취급하지 않는다. M01–M57에 어느 책임으로 연결할지 대조하고, 항목을 억지로 새 ID로 늘리지 않는다. 과거 실험·판례 대입·검토 당시의 55개·77개 숫자는 그 판본의 기록이므로 일괄 치환하지 않는다.

## 남은 확인

**요청 중 ‘모든 문서 전부 읽기’는 미완료다.** 판례 장문 원문·해설, 과거 판본의 잔여 차이, 내려받은 외부 소스 문서에는 아직 읽지 않은 범위가 있다. 도식의 시각 검수와 과거 조사에 인용된 외부 자료의 최신 재검증도 남아 있다. 위 보완안은 현재 정의·설계·검토·실험 문서와 링크한 공식 문서를 대조한 중간 결과다.

발표 당일 문서에는 과도기 차이가 있다. 문자 메시지는 Learn의 일부 안내와 Help Center의 미국 제한 베타 안내가 다르고, 초기 Dot 사용량 안내와 위임된 Work·Codex 사용량 안내도 범위가 다르다. 이 보완안은 특정 계정의 문자 기능·무제한 사용·무료 운영을 전제하지 않는다. 실제 도입 시에는 해당 계정·지역·요금제·관리자 설정에서 지원 여부를 확인해야 한다. [Dot messaging](https://learn.chatgpt.com/docs/dots/channels), [Getting started with your dot](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot), [Pricing](https://learn.chatgpt.com/docs/pricing).
