### 목표와 맡은 범위

| 재료 | 기준 |
|---|---|
| **지시·의도 파악** | ▶️ 주 모델이 일하기 실행의 첫 단계에서 한다<br>▶️ 맡을 때 묻고 알릴 항목, 질문에 깔린 전제 확인, 기한이 모자랄 때 채울 순서는 그 단계의 지시에 넣는다. 지켰는지는 독립 검사 실행이 판정한다<br>▶️ 그 단계의 답 형식에는 ‘물을 것’ 칸과 ‘쓸 기본값과 건너뛸 확인’ 칸을 둔다. 수신 서버는 물을 것을 한 메시지로 묶어 맡긴 사람에게 보낸다<br>▶️ 내보내기 검사는 쓴 기본값과 건너뛴 확인, 창구에서 받은 업무 종류와 대상이 결과물에 밝혀졌는지 그 칸과 맞춘다<br>▶️ 업무별 창구나 요청 서식으로 들어온 건은 수신 서버가 그 업무 종류를 붙인다. 그 밖의 건은 받기 실행이 업무 종류 하나를 추천하고, 수신 서버가 맡긴 사람에게 예나 아니오로 묻는다. 답이 오기 전에는 DBOS 단계 코드가 일하기 단계를 시작하지 않는다<br>▶️ 미리 허락할 행동과 그 한도는 요청 서식으로 받아 권한 판정 창구의 규칙으로 넣는다. 받지 못한 건은 미리 허락이 없는 것으로 판정된다<br>▶️ 대화를 맡는 업무 종류의 요청 서식은 위급할 때 답할 사람을 빈칸으로 받지 않는다 |
| **계약·합의 조건** | ▶️ 약속은 서버 MCP 서버의 진행 상태에 남긴다. 약속마다 협의 중, 확정, 바뀜, 끝남 가운데 하나의 상태와 근거 위치를 붙인다<br>▶️ 확정으로 바꾸는 것은 서명된 계약서나 상대가 확정한 메시지처럼 근거가 원문으로 남아 있을 때뿐이다. 맡긴 사람이 말로 맺은 합의를 알려 주면, 알려 준 그 메시지를 근거로 붙인다<br>▶️ 확정된 약속의 기한은 일정에, 범위와 금액은 업무 기록에 같은 근거 번호로 넣는다<br>▶️ 일이 끝난 뒤에도 남는 의무(비밀 유지, 보관 기간)는 끝남 상태가 돼도 남은 기한과 함께 둔다 |
| **문제·목표·완료 조건** | ▶️ 완료 조건은 맡은 끝에 따라 셋 가운데 하나로 정한다. 만들기까지, 보내기까지, 상대가 받았다는 확인까지다<br>▶️ DBOS 단계 코드는 그 끝에 맞는 기록이 모두 있을 때만 건을 완료로 바꾼다. 독립 검사 합격, 내보내기 검사 통과, 보낸 기록, 원본 시스템의 받음 상태가 그 기록이다<br>▶️ 법이나 직업 규칙이 요구하는 결과물 항목은 기준 파일에 뺄 수 없는 항목으로 표시한다. 맡긴 사람이 빼라고 해도 그 항목이 빠진 결과물은 내보내기 검사를 통과하지 못한다<br>▶️ 조사할 곳과 깊이, 합격 기준은 기준 파일에 있고 실행은 읽기만 한다. 그래서 일을 빨리 끝내려고 줄일 수 없다 |
| 첨부 문서에 적힌 지시 | ▶️ 받기 실행은 첨부 문서 속 지시를 찾아 표시한다. 맡긴 사람이 요청에서 그 문서대로 하라고 했으면, 그 문서의 지시는 빼지 않고 ‘맡긴 사람이 따르라고 한 지시’로 표시해 일하기 실행에 넘긴다<br>▶️ 그 지시가 받는 사람이나 권한을 바꾸라고 해도, 권한 판정 창구는 사내 서버에 저장된 권한과 받는 사람만 보고 판정한다. 바꿔야 하면 맡긴 사람에게 예나 아니오로 묻는다 |

### 사실 분석과 기준 적용

| 재료 | 기준 |
|---|---|
| **관찰·측정** | ▶️ 측정값은 값, 단위, 허용 오차, 잰 도구, 잰 때, 조건 칸을 모두 채운 형식으로만 진행 상태에 넣는다. 칸이 빈 측정값은 상주 프로그램이 받지 않아 근거로 쓰이지 않는다<br>▶️ 원본 시스템에 남은 기록으로 충분하면 다시 재지 않는다 |
| **분석** | ▶️ 분석에 쓴 입력 파일과 코드는 해시와 함께 판단 근거에 남긴다. 같은 결과를 다시 낼 수 있게 하려는 것이다<br>▶️ 여러 사람을 같은 기준으로 평가한 결과는 내보내기 검사가 전달 전에 statsmodels로 쏠림을 판정한다. 두 집단이 좋은 결과를 받은 비율의 차이가 있을 범위를 내고, 집단이 작아도 같은 방법을 쓴다<br>▶️ 처음 값은 허용 차이 5%포인트다. 범위는 실제 차이가 그 안에 있을 확률이 95%가 되게 낸다. 업무 종류마다 운영하는 쪽이 바꾼다 |
| **기준 적용·판정** | ▶️ 판정 칸은 충족, 불충족, 미확인, 해당 없음 네 값만 받는다. 이유 칸이 빈 답은 상주 프로그램이 받지 않는다<br>▶️ 나이, 금액, 날짜, 횟수처럼 값으로 가릴 수 있는 조건은 주 모델이 판정 코드를 짜서 돌리고, 그 실행 결과를 판정 칸에 옮긴다<br>▶️ 해석이 갈리는 조항은 답 형식에 해석마다 결론 칸을 둔다. 한 해석만 적고 끝내지 못하게 하려는 것이다 |

### 계산과 예측

**계산**

| 구분 | 에이전트 하네스 |
| --- | --- |
| 계산 코드를 돌리는 곳 | ▶️ Claude Code가 PC의 샌드박스 안에서 Python으로 돌린다. 샌드박스는 바깥 연결이 막혀 있다<br>▶️ 내보내기 검사는 저장해 둔 코드와 입력값으로 다시 돌려 같은 값이 나오는지 본다 |

▶️ 계산 코드는 회사 공용 계산 라이브러리가 정한 입력값 표로만 값을 받는다. 입력값마다 값, 단위, 기준일, 합계인지 소계인지 그 안의 항목인지, 그 값이 나오는 원문 위치를 모두 적는다.<br>
▶️ 이 라이브러리는 원문 위치마다 적힌 값이 서로 같은지 원문과 글자로 맞추고, 같은 계산에 합계와 그 안의 항목이 함께 들었는지 본다. 하나라도 걸리면 계산하지 않고 멈춘다.<br>
▶️ 내보내기 검사는 결과물에 적힌 금액, 기한, 비율이 계산 실행 기록에 있는지 맞춘다. 기록에 없는 값이 있으면 내보내지 않는다.

| 계산 | 고른 것 | 고른 까닭 |
|---|---|---|
| 금액과 정확한 십진수 | Python `Decimal` | 0.1 같은 값을 오차 없이 담는다. 표준 라이브러리라 따로 들일 것이 없다 |
| 단위 변환 | Pint | 값에 단위를 붙여, 다른 단위끼리 더하면 오류를 낸다. astropy.units는 천문학 라이브러리 전체를 들여야 해서 고르지 않았다 |
| 기호식 | SymPy | 기호식 전반을 다루는 오픈소스는 이것뿐이다. SymEngine과 python-flint는 다루는 범위가 좁다 |
| 수치해석 | SciPy | 같은 범위를 한 라이브러리로 덮는 대안이 없다 |
| 표 집계 | DuckDB | PC 안에서 서버 없이 큰 표를 SQL로 센다. 그래서 고객 자료가 PC 밖으로 나가지 않는다. 공개 성능 비교 ClickBench에서 Polars, DataFusion보다 빠르거나 비슷하다 |
| 통계와 쏠림 판정 | statsmodels | 두 비율 차이의 범위를 기본으로 Newcombe 방법으로 낸다. 이 방법은 건수가 적은 집단에도 쓸 수 있다. SciPy는 비율 하나의 범위만 낸다 |
| 법령이 정한 계산 | 회사 공용 계산 라이브러리의 Python 함수 | 조문 번호를 줄마다 붙여 조문과 맞춰 볼 수 있고, 따로 들일 컴파일러가 없다. Catala는 조문 대조에 맞지만 컴파일러를 소스에서 빌드해 들여야 하고, 한국 법령에 쓴 사례를 찾지 못해 고르지 않았다. OpenFisca는 조문과 줄을 맞추는 구조가 아니다 |
| 제출처가 지정한 계산 | 제출처의 공식 계산기 | 제출처가 받는 값이 곧 그 계산기의 값이다. 우리 계산은 맞춰 보는 데만 쓰고, 둘이 다르면 입력과 원문으로 어느 쪽이 맞는지 가리기 전에는 내지 않는다 |
| 공휴일 | 한국천문연구원 특일 정보 | 공식 출처다. 사내 서버가 공공데이터포털에서 날마다 받아 저장하므로, 2025년 9월과 10월처럼 포털이 27일 동안 멈춰도 기한 계산은 멈추지 않는다. Python `holidays` 라이브러리는 임시공휴일이 새 버전이 나와야 들어와 고르지 않았다 |

**법령이 정한 계산**

▶️ 기간, 세율, 이자, 끝수처럼 법령이 정한 계산은 회사 공용 계산 라이브러리에 함수로 둔다. 모든 PC가 같은 버전을 부르고, 주 모델이 그때그때 짜지 않는다.<br>
▶️ 함수의 줄마다 근거 조문(법령 이름, 조, 항, 호)과 그 조문의 시행일을 붙인다. 프로그램이 이 표시로 조문 원문과 코드 줄을 나란히 놓은 대조표를 만들고, 그 분야 전문가는 이 대조표로 맞춰 본다.<br>
▶️ 새 버전은 법령을 맡은 기관이 낸 계산 사례를 모두 통과하고 전문가의 승인이 Git에 남아야 낼 수 있다. 기관이 낸 사례가 없는 조문은 전문가가 손으로 계산한 사례로 대신한다. 처음 값은 5건 이상이다.<br>
▶️ 조문의 경계값마다 시험이 하나 이상 있어야 한다. 기준 금액의 바로 위와 아래, 기간의 마지막 날, 끝수가 정확히 절반인 값이 경계값이다.<br>
▶️ 근거 조문이 개정되면 프로그램이 그 조문 표시가 붙은 함수를 다시 검토할 것으로 표시하고, 개정 시행일 뒤의 사건에는 부르지 못하게 막는다. 시행일 전의 사건은 옛 버전으로 계산한다.

| 항목 | 기준 |
|---|---|
| 반올림과 끝수 | ▶️ 끝수 처리는 조문 표시를 붙인 계산 함수 안에 둔다<br>▶️ 함수마다 반올림 방식을 꼭 적게 하고, 적지 않으면 라이브러리가 오류를 낸다. `Decimal`은 방식을 적지 않으면 정확히 절반인 값을 짝수 쪽으로 보내 1234.5를 1234로 만든다. 사사오입이면 1235여야 하므로 그대로 두면 틀린다 |
| 기한 | ▶️ 기한은 이 라이브러리의 기한 계산기로 센다<br>▶️ 계산기는 세기 시작하는 날, 첫날을 세는지, 마지막 날이 쉬는 날이면 어느 쪽으로 넘기는지, 영업일 달력, 시간대를 입력으로 받는다<br>▶️ 쉬는 날로 보는 날은 조문마다 달라서, 계산기는 적용할 조문의 쉬는 날 범위를 따로 받는다 |
| 입력이 범위로만 확인될 때 | 범위의 양 끝값으로 각각 계산하고, 결과도 범위로 적는다 |

**분야 기준 파일에 두는 것**

▶️ 한 분야에만 쓰는 계산 규칙은 공통 규칙에 넣지 않고 그 분야의 기준 파일에 둔다.<br>
▶️ 법률 분야 기준 파일: 기간의 마지막 날이 토요일이나 공휴일이면 다음 날로 넘기는 민법 제161조의 쉬는 날 범위. 기한 계산기에 넘기는 값이다.<br>
▶️ 세무 분야 기준 파일: 국고금은 10원 미만 끝수를 계산하지 않는 규칙.

**예측**

▶️ statsforecast의 단순한 방법(직전 값, 계절 단순 예측)을 기준선으로 먼저 돌린다. 기준선이 없으면 다른 모델이 나은지 가를 수 없다.<br>
▶️ 다른 모델은 같은 업무 자료로 기준선과 겨뤄 이겨야 쓴다. 견줄 첫 후보는 t0-gamma다. 공개 예측 평가 fev-bench에서 계절 단순 예측보다 49.9% 나아, 회사가 쓸 수 있는 Apache-2.0 허가를 가진 모델 가운데 가장 높다. 매개변수가 2.6억 개라 PC에서 돌릴 수 있다. TimesFM 3.0은 상업 사용을 막는 허가라 고르지 않았다.<br>
▶️ 겨룰 때는 자료 끝에서 예측할 기간만큼 가리고, 그 앞 자료만으로 가린 부분을 맞혀 본다. 이 일을 3번 되풀이해 오차를 잰다. 오차가 기준선보다 10% 이상 작아야 채택한다.<br>
▶️ 실제 결과가 나오면 예측값과 함께 기록한다. 최근 3번의 오차가 겨룰 때 잰 오차의 1.5배를 넘으면 다시 겨룬다.<br>
▶️ 관측이 30개보다 적으면 숫자로 예측하지 않고, 일어날 수 있는 시나리오로 적는다.<br>
▶️ 이 절의 숫자는 처음 값이다. 업무 종류마다 운영하는 쪽이 바꾼다.

### 방법을 고르고 작업으로 나누기

| 재료 | 기준 |
|---|---|
| **대안·전략 판단** | ▶️ 주 모델이 일하기 실행 안에서 비교한다<br>▶️ 처리 방향을 정하는 단계의 답 형식에는 방안마다 효과, 비용, 위험 칸을 둔다. 지금 상태를 유지하는 방안과 더 확인한 뒤 정하는 방안은 따로 꼭 채울 칸으로 둔다<br>▶️ 처음 세운 가정은 진행 상태의 가정 목록에 따로 적는다. 환율, 잔액, 재고처럼 값으로 된 가정은 DBOS 단계 코드가 실행 직전에 원본에서 다시 조회해 맞춘다. 다르면 실행하지 않고 새 실행으로 다시 판단한다. 값이 아닌 가정은 독립 검사 실행이 결론과 맞춘다 |
| **업무 절차·실행 계획** | ▶️ 한 업무 시스템에서 처음 하는 종류의 행동은 그 시스템의 시험 계정에서 한 번 성공한 뒤에 실제 계정으로 한다. 시험 계정이 없는 시스템은 첫 실행을 미리 허락 범위에서 빼고 결정 요청으로 받는다<br>▶️ 여러 건을 바꾸는 행동은 처음 값 5건을 먼저 하고, 원본 시스템 조회로 맞게 반영된 것을 본 뒤 나머지를 한다 |

**사람에게 넘기기**

승인은 결정 요청 화면에서 예나 아니오 하나로 받는다.

| 넘기는 경우 | 가려내는 부품 | 받는 사람 |
|---|---|---|
| 미리 허락 밖의 되돌릴 수 없는 행동, 받은 권한이나 한도 밖의 행동 | 권한 판정 창구. DBOS 단계 코드가 실행 전에 묻는다 | 맡긴 사람 |
| 업무 능력 시험으로 확인된 범위 밖의 일 | DBOS 단계 코드가 맡을 때 허용 목록과 맞춘다 | 맡긴 사람 |
| 판단이 서지 않는 일 | 일하기 실행의 답 형식에 있는 ‘넘김’ 칸. 다시 판단한 실행과 앞선 실행의 결론이 다르면 DBOS 단계 코드가 두 결론 칸을 맞춰 보고 넘긴다 | 맡긴 사람 |
| 법이나 약속이 사람의 결정을 요구하는 일 | 받기 실행과 독립 검사 실행이 기준 파일의 목록대로 찾아 표시한다 | 맡긴 사람. 이해충돌과 고객끼리 맞서는 일은 운영하는 쪽 책임자 |
| 법이 자격자의 판단을 요구하는 일 | 기준 파일의 자격자 일 목록과 권한 판정 창구 | 그 일을 맡은 자격자 |

**되돌릴 수 없는 행동으로 보는 것**

법적으로나 물리적으로 되돌릴 수 없는 것만 되돌릴 수 없는 행동이다. 맡긴 사람이 미리 허락한 대상과 한도 안이면 묻지 않는다.

- 돈을 보내거나 결제를 확정하는 것
- 법원이나 기관, 상대방에게 내거나 보내는 것. 받은 쪽이 읽거나 효력이 생기면 거둘 수 없다
- 계약을 확정하거나 서명하는 것
- 복구본 없이 지우는 것과, 정한 때에 저절로 지워지게 예약하는 것
- 사람 확인 없이 되돌릴 수 없는 처리를 이어 하는 시스템에 넣는 것. 예를 들어 다음 날 자동으로 지급하는 급여 시스템에 넣는 것이다
- 주인이 허락하지 않은 비밀을 밖에 알리는 것
- 변경 기록이 남지 않고 바꾸기 전후 상태도 저장할 수 없는 곳에 쓰는 것

바꾸기 전 값을 저장해 둔 기록 수정, 초안 저장, 사용 중지처럼 다시 켤 수 있는 설정 변경, 취소 기간이 남은 예약은 되돌릴 수 있는 행동이다.

**결정 요청**

▶️ 결정 요청 화면에는 DBOS 단계 코드가 미리 맞춰 본 실제 대상과 값, 근거 원문 조각, 추천과 그 까닭, 답 기한이 뜬다.<br>
▶️ 근거 원문 조각은 예와 아니오 단추와 같은 화면에 펼쳐 띄운다. 이 화면에서 온 답만 받고, 화면을 연 사람과 때, 답을 PostgreSQL에 남긴다.<br>
▶️ 아니오를 누르면 까닭 한 줄을 받는다. 그 까닭을 넣은 새 실행으로 다시 판단한다.<br>
▶️ 같은 대상과 값에 24시간 안에 받은 승인이 있으면 다시 묻지 않는다.<br>
▶️ 답 기한이 지나면 화면의 예 단추가 닫힌다.<br>
▶️ 법이 자격자의 판단을 요구하는 일은 사내 로그인 계정에 자격 기록이 이어진 사람만 예를 누를 수 있다. 그 밖의 일은 맡긴 사람이나 맡긴 사람이 정한 사람이 답한다.

**기다림과 다음 사람**

| 무엇 | 처음 값 |
|---|---|
| 답 기한 | 업무 기한에서 남은 일에 걸릴 시간을 뺀 때. 남은 일은 실행 한 번에 1시간, 밖으로 나가는 행동 하나에 1시간으로 센다 |
| 화면을 열지 않을 때 | 보낸 뒤 근무시간으로 1시간이 지나면 사내 메신저로 다시 알린다. 2시간이 지나면 기준 파일에 정한 다음 사람에게 보낸다 |
| 화면을 열었지만 답이 없을 때 | 답 기한에 다음 사람에게 보낸다. 다음 사람도 없으면 DBOS 단계 코드가 그 부분과 거기 기대는 단계를 멈춘 채 둔다 |
| 한 사람이 하루에 받는 결정 요청 | 30건. 넘치는 건은 수신 서버가 보내지 않고 보류한 채 맡긴 사람에게 알린다 |

처음 값은 업무 종류마다 운영하는 쪽이 바꾼다.

**표본 감사**

결론을 먼저 직접 쓰기, 틀린 곳을 넣은 시험 건, 두 사람 승인은 늘 하지 않는다. 운영하는 쪽 검사자가 무작위로 뽑힌 건을 감사할 때만 한다.

▶️ DBOS 단계 코드가 결정 요청을 만들 때 무작위로 뽑는다. 처음 값은 5%이고, 업무 종류마다 한 달에 10건 이상 뽑는다. 한 달 건수가 10건보다 적으면 모두 뽑는다. 뽑혔는지는 에이전트와 승인자에게 알리지 않는다.<br>
▶️ 뽑힌 건은 검사자에게도 간다. 검사자의 화면에는 원문만 먼저 뜨고, 검사자가 결론과 그 판단을 적어야 에이전트의 추천과 값이 열린다.<br>
▶️ 뽑힌 건은 승인자와 검사자가 모두 예라고 해야 실행한다. 둘이 다르면 실행하지 않고, 검사자가 원문과 계산으로 가린 결과를 붙여 승인자에게 다시 묻는다. 검사자의 답이 답 기한까지 없으면 승인자의 답대로 실행하고 감사는 뒤에 마친다.<br>
▶️ 미리 허락으로 실행한 건도 같은 비율로 뽑는다. 검사자는 실행 뒤에 같은 방법으로 감사하고, 틀렸으면 그 건을 바로잡는 일을 새 건으로 만든다.<br>
▶️ 검사자는 승인자마다 한 달에 2건, 틀린 곳을 넣은 시험 건을 실제 결정 요청처럼 보낸다. DBOS 단계 코드는 시험 건에 표시를 해 두어 승인돼도 실행하지 않는다.<br>
▶️ 승인자가 최근 시험 건 10건 가운데 8건보다 적게 잡아내면, 그 업무 종류의 승인자 목록에서 빼고 맡긴 사람에게 알린다. 시험 건이 10건 쌓이기 전에는 빼지 않는다.<br>
▶️ 처음 값은 업무 종류마다 운영하는 쪽이 바꾼다.

**위급할 때**

▶️ 받은 글에서 수신 서버가 운영하는 쪽이 정한 위험 낱말을 찾거나 받기 실행이 위험 발언을 찾으면, DBOS 단계 코드가 다른 단계를 기다리지 않고 도움 연락처 안내를 바로 보낸다. 안내는 모든 업무 종류에 미리 허락된 고정 문구다.<br>
▶️ 이어서 수신 서버가 위급할 때 답할 사람에게 사내 메신저로 알린다. 처음 값 10분 안에 답이 없으면 DBOS 단계 코드가 미리 허락받은 조치를 한다. 업무 종류마다 운영하는 쪽이 바꾼다.<br>
▶️ 이 조치로 보내는 글은 위치와 위험의 내용 두 칸뿐인 서식으로만 만든다.

**사람의 답을 받는 곳**

| 구분 | 에이전트 하네스 |
| --- | --- |
| 실행과 사람의 답 | ▶️ Claude Code 실행은 사람의 답을 기다리지 않는다. 물을 것이 생기면 답에 적고 끝난다<br>▶️ DBOS 단계 코드가 사람의 답을 기다리고, 답이 오면 상주 프로그램이 사내 서버의 기록을 넣은 새 실행으로 잇는다<br>▶️ 훅은 사람에게 묻지 않고 허락이나 막음만 답한다 |

결정 요청 화면과 사내 메신저는 둘 다 수신 서버가 맡는다.

| 통로 | 쓰는 일 | 지금의 선택과 고른 까닭 |
|---|---|---|
| 결정 요청 화면 | 예나 아니오로 받는 모든 승인, 근거를 띄운 기록 | 수신 서버가 내는 웹 화면이다. 사내 로그인으로 들어온 사람만 답할 수 있다. 근거를 띄운 화면에서 온 답인지 기록할 수 있어 승인 통로로 고른다 |
| 사내 메신저 | 결정 요청이 왔다는 알림과 화면 주소, 맡을 때 묻는 물음과 그 답, 다시 알림, 위급 알림 | 회사가 이미 쓰는 메신저에 수신 서버를 봇으로 붙인다. 승인자가 이미 보고 있는 곳이라 새 메신저를 들이지 않는다. 사내 로그인과 이어진 계정의 답만 받는다. 메신저 단추로는 근거를 띄웠는지 기록할 수 없어 승인은 받지 않는다 |

| **재사용 자료** | ▶️ 서식, 코드, 이미지, 글꼴은 사내 서버의 자료 목록에 출처, 사용 허가, 버전을 함께 올린 것만 쓴다. 내보내기 검사는 실행 기록에서 쓴 자료를 찾아 목록과 맞추고, 목록에 없거나 칸이 빈 자료가 들어간 결과물은 내보내지 않는다<br>▶️ 원본과 고친 것은 다른 버전 번호로 둔다<br>▶️ 자료마다 그 자료를 쓴 결과물을 기록한다. 자료에 결함이 생기거나 권리가 바뀌면 이 기록으로 그 자료를 쓴 결과물을 찾는다 |
| **표현 방식·스타일** | ▶️ 표현 기준은 실제 견본 파일로 남긴다<br>▶️ 글자 수와 필수 문구는 검사 코드로 센다<br>▶️ 자연스러움과 전체 인상은 독립 검사 실행이 견본과 완성물을 나란히 놓고 판정한다 |
| **내용 재구성** | ▶️ 일하기 실행은 바꿔 쓰거나 요약한 문장마다 원문 위치를 붙인다<br>▶️ 독립 검사 실행이 그 문장을 원문과 짝지어, 단정하는 정도와 적용 대상이 그대로인지 판정한다 |
| **결과물 만들기·수정** | ▶️ 결과물은 제작 프로그램의 자동화 기능이나 그 파일 형식을 다루는 편집 라이브러리로 만든다. 같은 입력에서 같은 파일이 나와 다시 만들 수 있다<br>▶️ 내용을 고치면 원본 프로그램에서 목차와 수식, 참조를 다시 계산한다<br>▶️ 요구받은 형식으로 만들지 못하면 대신 쓸 형식을 맡긴 사람에게 예나 아니오로 묻는다<br>▶️ 대신 쓸 형식으로 냈더라도 필수 형식 항목은 채우지 못한 것으로 남긴다 |
| **형식·구조 변환** | ▶️ 원본 프로그램의 내보내기 기능을 먼저 쓴다<br>▶️ 변환한 뒤 표, 수식, 그림, 링크의 개수와 표 칸의 값을 원본과 프로그램으로 맞춘다<br>▶️ 한 시스템의 자료를 다른 시스템으로 옮길 때는 어느 필드가 어느 필드로 가는지 대응표를 먼저 만든다. 옮긴 뒤 행 수와 금액 합계를 양쪽에서 맞춘다 |

**메시지 대화의 지금의 선택**

▶️ 음성 통화는 맡지 않는다. 대화는 글로 주고받는 메시지만 맡는다.<br>
▶️ 답 하나가 받기 실행, 일하기 실행, 독립 검사 실행, 내보내기 검사를 모두 거쳐 나간다. 그래서 바로 답해야 하는 실시간 응대는 맡지 않는다.<br>
▶️ 같은 상대가 이어 보낸 메시지는 수신 서버가 처음 값 2분 동안 모아 한 건으로 DBOS에 넣는다.<br>
▶️ 답이 처음 값 15분 안에 나가지 않으면 DBOS 단계 코드가 받았다는 답을 고정 문구로 보낸다. 빈자리가 없는 미리 허락된 문구라 결정 요청 없이 나간다.

### 업무 시스템에 반영하기

**원칙**

▶️ 바깥 업무 시스템을 바꾸는 행동(기록 수정, 신청과 거래, 설정, 게시)은 Claude Code 안에서 하지 않는다. Claude Code 실행은 답의 행동 제안 칸에 적기만 하고, DBOS 단계 코드가 요청 번호를 붙여 실행한다.<br>
▶️ 실행 안에서 바로 하면, 끊긴 단계를 다시 돌릴 때 같은 행동이 또 나간다. 승인과 실행 직전 대조를 모델이 건너뛸 수도 있다.<br>
▶️ 사내 기록(기억, 진행 상태, 판단 근거)은 실행 안에서 서버 MCP 서버로 쓴다.

**행동 제안 칸**

Claude Code 실행의 답은 행동마다 행동 종류, 업무 시스템, 대상, 값, 근거 위치, 되돌릴 방법을 적는다. 칸이 하나라도 비면 상주 프로그램이 받지 않는다. 여러 건이면 건마다 따로 적는다.

**실행 순서**

1. DBOS 단계 코드가 요청 번호를 만들어 제안과 함께 PostgreSQL에 먼저 저장한다. 번호는 건 번호와 단계, 순번으로 만든다. 그래서 그 단계를 처음부터 다시 돌려도 같은 번호가 나온다.
2. 상대 시스템에서 실제 대상과 값을 미리 맞춰 본다. 받는 사람의 이름, 바꿀 기록의 지금 값, 보낼 파일의 해시가 여기서 정해진다.
3. 권한 판정 창구에 묻고 예산을 확인한다. 미리 허락 범위 밖이면 앞 단계에서 맞춘 값으로 결정 요청을 만들고 답을 기다린다.
4. 승인을 받은 행동은 보내기 직전에 승인 번호와 실제로 보낼 대상, 값을 권한 판정 창구에 넣어 다시 묻는다.
5. 요청 번호를 붙여 보낸다. 상대에게 요청 번호를 적을 참조 칸(참조 번호, 메모, 적요)이 있으면 그 칸에도 넣는다.
6. 상대의 응답과 따로 원본 시스템에서 최종 상태를 조회한다. 끝나지 않았으면 다음 단계로 넘어가지 않는다.
7. 결과를 기록하고, 예약한 비용을 정산한다.

**실패할 때**

| 상황 | 처리 | 처음 값 |
|---|---|---|
| 요청이 상대에게 닿지 않은 것이 확실하다. 연결 자체가 안 됐거나, 처리하지 않았다고 상대 문서가 밝힌 오류가 왔다 | 같은 요청 번호로 다시 보낸다 | 3번까지, 30초, 2분, 10분 뒤 |
| 닿았는지 모른다. 응답 시간을 넘겼거나 중간에 끊겼다 | 다시 보내기 전에 원본 시스템을 조회한다. 상대가 처리를 마칠 시간을 기다린 뒤 요청 번호로 찾고, 처리됐으면 그대로 기록한다 | 응답을 기다리는 시간 30초. 조회 전 기다림은 상대가 밝힌 처리 시간, 밝히지 않았으면 10분 |
| 조회로 처리되지 않은 것이 분명하다. 요청 번호로 찾을 수 있는 곳에서 두 번 조회해 모두 없다 | 같은 요청 번호로 다시 보낸다 | 두 조회 사이 10분 |
| 조회가 처리 중이라고 나오거나 분명하지 않다. 상대가 중복 방지를 지원하고 유효 기간 안이다 | 같은 요청 번호로 다시 보낸다. 상대가 같은 번호를 한 번만 처리한다 | 3번까지 |
| 조회가 처리 중이라고 나오거나 분명하지 않다. 상대가 중복 방지를 지원하지 않거나 유효 기간이 지났다. 요청 번호로 찾을 수 없어 대상과 금액, 때로만 찾아야 하는 곳, 조회할 길이 없는 곳도 여기에 든다 | 다시 보내지 않는다. 맡긴 사람에게 ‘상대 시스템에 이 요청이 들어가 있습니까’를 예나 아니오로 묻고, 아니오일 때만 다시 보낸다. 묻는 동안에도 DBOS 단계 코드는 조회를 이어 가고, 결과가 나오면 그 결정 요청을 닫는다 | 1시간마다 조회 |
| 여러 건 가운데 일부만 처리됐다 | 처리되지 않은 요청 번호만 같은 방법으로 다시 다룬다 | |
| 다시 보내도 끝내 실패했다 | 그 행동과 거기 기대는 단계를 멈추고 맡긴 사람에게 알린다 | |

밖으로 나가는 행동을 하는 업무 도구는 요청 번호를 적을 참조 칸과 처리를 마치는 데 걸리는 시간도 등록한다. 요청 번호를 보관하는 기간을 문서로 밝히지 않은 곳은 중복 방지를 지원하지 않는 곳으로 다룬다.
