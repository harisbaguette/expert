## 🔴

### R1. 실행 제어 — 번호 없는 요청이 답 없이 끝나면 '실패'로 적혀 두 번 나갈 수 있음 (고침)
- 위치: 순서도 `Q4{{"번호를 받아 준 요청인가"}}` → 아니다 → `F["실패로 기록한다"]` → `C` → `RE["다시 짠다"]`·`K["복구한 뒤 계획대로 이어 간다"]`. 표 "상대가 번호를 받아 주지 않는다 | 다시 보내지 않는다"에 결과를 모를 때의 처리가 없음.
- 무엇이 틀렸나: 송금처럼 두 번 나가면 안 되는 요청을 번호 없이 보냈는데 답이 없으면, 상대 쪽에서 처리됐는지 모르는 상태다. 이것을 실패로 적으면 다시 짜기나 이어 가기에서 새 요청이 나가 두 번 처리될 수 있음.
- 어긋남: 정의 1 신뢰성 절 L1405 "결과를 모르는 행동을 확인 없이 다시 해서 두 번 일어난다 | 실행 제어". 정의 2 현재 진행 상태 "결과 불명 … 다시 실행하지 않는다. 원천에 결과를 확인한다". 신청·거래 처리는 번호를 받지 않는 상대도 참조 칸·금액·시각 대조로 조회하게 함.
- 고친 것: Q4 글자를 "두 번 나가면 안 되는 요청인가"로 바꿈(선·배치 그대로). 표의 결과 불명 행 조건에 "번호를 받아 주지 않는 상대에게 보낸 요청의 결과를 모른다"를 더하고 "실패로 적거나 새로 보내지 않는다"를 넣음.

### R2. 업무 도구·시스템 ① 화면만 있을 때 — Claude Code 브라우저 연동이 사람 로그인을 그대로 씀 (고침)
- 위치: "Claude Code는 하네스의 브라우저 조작 도구를 쓴다".
- 무엇이 틀렸나: Claude Code의 Chrome 연동은 사람이 쓰는 브라우저의 로그인 상태를 공유한다("shares your browser's login state, so it can access any site you're already signed into"). 같은 절 "①의 셸과 브라우저 | 같은 열쇠나 같은 로그인 세션으로 이 검사를 건너뛰지 못하게 막는다"와 정면으로 어긋나고, 다른 고객 계정·연결부 검사를 우회하는 길이 됨. WSL 안에서는 지원도 안 됨("Chrome integration isn't supported in WSL") — 분리 실행은 Windows의 Claude Code를 WSL2에서 돌리게 함.
- 근거: https://code.claude.com/docs/en/chrome
- 고친 것: 두 하네스 모두 컨테이너의 Playwright, 그 건에 허락된 계정만 로그인한 빈 브라우저, 사람 브라우저의 로그인을 빌리는 하네스 연동은 쓰지 않음.

## 🟡

### Y1. 운영 감시·복구 — 30초 주기로는 ①의 '세 배에 죽음'을 Healthchecks로 만들 수 없음 (고침)
- 위치: "살아 있다는 신호를 정해진 주기마다 보낸다 | 30초마다", ① "주기의 세 배가 지났다 → 죽음", ① 감시 = Healthchecks.
- 무엇이 틀렸나: Healthchecks API는 기다릴 시간(timeout)과 유예 시간(grace)의 가장 짧은 값이 60초다. 30초 주기면 모름(60초)은 되지만 죽음은 빨라야 120초(주기 네 배)라 90초가 안 됨.
- 근거: https://healthchecks.io/docs/api/ ("Minimum: 60 (one minute)")
- 고친 것: 주기 기본값 1분. ① 생사 판정에 "기다릴 시간 = 주기 두 배, 유예 = 주기 한 번, 1분보다 짧게 잡지 않는다"를 더함. ②·③ 심장박동 시한은 "주기의 세 배"라 3분으로 따라감.

### Y2. 나눠 맡기기 ① — Claude Code 기본값이 두 층·동시 10과 다름 (고침)
- 위치: "조각이 다시 조각을 부르는 일 | 하지 않는다", ① 깊이 두 층, 동시 수 10.
- 무엇이 틀렸나: Claude Code는 기본으로 하위 에이전트가 주 대화 아래 세 층까지 다시 부르고, 동시 20개까지 돌린다. 설정을 안 하면 규칙이 깨짐. Codex는 동시 수 기본값을 문서에 적지 않고(예시 6), 깊이 제한이 안 먹는 버그 보고가 있음.
- 근거: https://code.claude.com/docs/en/sub-agents ("up to three layers below the main conversation", "when 20 subagents are running"), https://learn.chatgpt.com/docs/agent-configuration/subagents , https://github.com/openai/codex/issues/32027
- 고친 것: ① 칸에 "Claude Code는 주 대화 아래 한 층, 동시 10으로 묶는다. Codex도 묶는다. 둘 다 실제로 막히는지 시험한다"를 더함.

### Y3. 분리 실행 ① 고객 자료 — Codex의 폴더 단위 읽기 제한은 시험 기능(Beta)뿐 (고침)
- 위치: "셸 명령이 열 수 있는 세 폴더 밖에 닿는 것은 샌드박스의 읽기 범위로 막는다".
- 무엇이 틀렸나: Codex에서 읽기를 폴더 단위로 좁히는 길은 permission profiles인데 "Beta. Permission profiles are under active development and may change." 문서 자체 규칙(시작 신호·기술 고르기: 시험 기능은 지원으로 치지 않음)에 걸림. 기본 샌드박스로는 작업 폴더 밖도 읽혀 다른 고객 건 폴더가 열림. Claude Code는 `denyRead`·`allowRead`로 정식 지원.
- 근거: https://learn.chatgpt.com/docs/permissions , https://learn.chatgpt.com/docs/sandboxing , https://github.com/openai/codex/issues/11316 , https://code.claude.com/docs/en/sandboxing
- 고친 것: Codex는 건마다 따로 만든 운영체제 사용자나 세 폴더만 연결한 컨테이너에서 돌리게 함.

### Y4. 분리 실행 ① "샌드박스가 뜨지 않는다 → 하네스를 시작하지 않는다" — Codex에는 그런 설정이 없음 (고침)
- Claude Code는 `sandbox.failIfUnavailable`로 정식 지원. Codex 문서는 bwrap이 없거나 사용자 이름공간을 못 만들면 "startup warning"만 적음.
- 근거: https://code.claude.com/docs/en/sandboxing , https://learn.chatgpt.com/docs/sandboxing
- 고친 것: ① 코드 실행 칸에 "Claude Code는 안 뜨면 시작하지 않게 설정, Codex는 감싼 실행 프로그램이 시작 전에 확인"을 더함.

### Y5. 분리 실행 끝 문단 — URL이 본문에 있고, 셸 전용 제한 경고가 Codex Windows에만 붙어 있음 (고침)
- 위치: "Codex를 Windows에서 돌리는 조건은 [공식 Windows sandbox 문서](https://learn.chatgpt.com/…)를 따른다. 명령에 건 네트워크 제한이 원격 검색, MCP, 브라우저에도 …"
- 무엇이 틀렸나: 공통지시가 금지한 출처 URL. 그리고 "샌드박스 제한은 셸 명령에만 걸린다"는 두 하네스 공통 사실이다(Claude Code 샌드박스는 Bash·PowerShell·Monitor 명령에만, Codex 프로필은 "only local sandboxed command execution").
- 근거: https://code.claude.com/docs/en/sandboxing , https://learn.chatgpt.com/docs/permissions , https://learn.chatgpt.com/docs/windows/windows-sandbox (실제 있는 공식 문서임을 확인. developers.openai.com/codex 가 이 도메인으로 308 이동)
- 고친 것: URL을 빼고 문서 이름만 남김. 제한이 셸에만 걸린다는 문장을 두 하네스 공통으로 고침.

### Y6. 실행 제어 재시도 — 무작위 흔들기·상대가 준 대기 시각·한 곳에서만 재시도가 빠짐 (고침)
- 위치: "3번까지 다시 보낸다. 보내는 간격은 매번 두 배로 늘린다."
- 무엇이 틀렸나: 업계 방식은 두 배 늘리기에 무작위 흔들기를 섞어 여러 요청이 같은 순간에 다시 몰리지 않게 하고, 재시도는 한 층에서만 한다(층마다 3번이면 3×3으로 불어남). 상대가 `Retry-After`로 시각을 주면 따른다.
- 근거: https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/ , https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/ , RFC 9110 §10.2.3 Retry-After
- 고친 것: 처리 칸에 세 가지를 더함. 숫자(3번, 두 배)는 그대로.

### Y7. 실행 제어 번호 — 같은 번호·같은 내용 재사용과 번호 보관 기간이 빠짐 (고침)
- 무엇이 틀렸나: 다시 보낼 때 새 번호를 붙이면 번호가 소용없다. 상대는 번호를 영원히 기억하지 않는다. Stripe는 24시간 뒤 지울 수 있고 지운 뒤 같은 번호가 오면 새 요청으로 처리하며, 같은 번호에 다른 내용이 오면 오류를 낸다.
- 근거: https://docs.stripe.com/api/idempotent_requests
- 고친 것: 행 "다시 보낸다 | 처음 붙인 번호와 처음 내용을 그대로 쓴다. 상대가 번호를 기억해 주는 기간이 지났으면 같은 번호로도 다시 보내지 않는다"를 더함. 신청·거래 처리 조회 순서 2도 같은 뜻으로 이미 맞춰져 있음을 확인.

### Y8. 실행 제어 ②·③ — Temporal 기본 재시도는 끝없음 (고침)
- 무엇이 틀렸나: Temporal 활동의 기본 재시도는 최대 횟수 무한(간격 1초, 두 배, 상한 100배). 따로 안 정하면 "3번까지"와 "번호 없는 상대에게 다시 보내지 않는다"가 깨짐. 심장박동 시한 초과도 한 번의 시도로 다시 돌아 다른 일꾼이 같은 요청을 또 보낼 수 있음.
- 근거: https://docs.temporal.io/encyclopedia/retry-policies , https://docs.temporal.io/encyclopedia/detecting-activity-failures
- 고친 것: 환경별 정답에 "다시 보내기" 행을 더함(① 전용 도구가 번호를 기록과 대조, ②·③ 걸음마다 횟수를 정하고 번호 없는 상대 걸음은 다시 돌리지 않음).

### Y9. 시작 신호 — "분당 60건까지 받는다"와 "버리지 않는다"가 부딪침 (고침)
- 무엇이 틀렸나: 받는 속도의 상한으로 읽으면 넘는 신호를 거절하게 만들어짐. 같은 표가 "먼저 저장한 뒤 접수 응답"이라 모든 신호는 저장돼야 함.
- 고친 것: "들어온 신호는 모두 대기열에 넣고, 꺼내 담당을 깨우는 속도에만 상한 | 분당 60건까지 깨운다".

### Y10. 시작 신호 웹훅 — 오래됨 기준값이 없고, 서명에 시각이 없는 원천을 다룰 길이 없음 (고침)

- 고친 것: 기본값 "보낸 시각이 5분보다 오래됐으면 버린다", 처리 "서명에 시각이 없는 원천은 고유 번호로만 다시 보낸 신호를 가린다".

### Y11. 시작 신호 ① 받는 문 — 사내 서버가 사람 컴퓨터의 헤드리스 실행을 직접 띄울 길이 없음 (고침)
- 위치: "사내 서버 한 대에서 수신 문 프로그램이 신호를 받아 헤드리스 실행을 띄운다".
- 무엇이 틀렸나: 정의 1 환경 표에서 ①의 하네스·도구는 한 사람의 PC에 있다. 서버에서 PC의 프로세스를 직접 띄울 수 없음.
- 고친 것: "수신 문이 대기열에 넣고, 하네스가 도는 컴퓨터의 대기 프로그램이 대기열을 가져가 헤드리스 실행을 띄운다".

### Y12. 실시간 대화 — ③ 제외가 빠짐 (고침)
- 무엇이 틀렸나: 부품 절 "③은 실시간 음성 대화를 맡지 않는다". 그런데 이 재료의 "②·③" 칸이 LiveKit·GLM-5.3-Flash 등을 ③에도 주는 것처럼 읽힘. GLM-5.3-Flash는 총 320B라 DGX Spark 128GB에 올릴 수도 없음.

- 고친 것: "③ 추가 | 음성 대화는 맡지 않고 ②로 넘긴다" 행을 더함.

### Y13. 실시간 대화 답 모델 — "40점을 넘는"이 규칙 "40점 이상"과 어긋나고, 가장 가까운 후보를 설명하지 않음 (고침)

Qwen3.8-Flash-Next(활성 6B, 공개 가중치)는 AA 화면에 40점으로 보여 검토자는 규칙대로면 이것이 답이라고 읽는다. 페이지 내장 값은 39.82라 40 이상이 아님. 이전 근거 기록(`docs/검토기록/재료/환경-계통-7문항-검토-2026-09-30.md` L175 "활성 10B 아래 최고는 K2 Horizon MoVA 36B A4B 25점")은 AA의 small·tiny 페이지만 봤는데, 이 분류는 총 파라미터 기준이라 활성이 작은 큰 MoE 모델을 놓침.
- 근거: https://artificialanalysis.ai/models/qwen3-8-flash-next (내장 `intelligenceIndex: 39.8223`, 활성 6B, 총 180B), https://artificialanalysis.ai/models/open-source ("size classifications use total parameters"), GLM-5.3-Flash 내장 값 41.81·활성 18B.
- 고친 것: "40점 이상인"으로 맞추고, Qwen3.8-Flash-Next가 화면 40점이지만 반올림 전 39.8점이라 빠진다는 문장을 더함. 정답 GLM-5.3-Flash는 그대로.

### Y14. 실시간 대화 끝 문단 — 뜻 없는 참조 두 개 (고침)
