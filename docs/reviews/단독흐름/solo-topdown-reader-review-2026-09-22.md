**단독 상황 순서도 — 위에서 아래로 읽는 검토 · 2026-09-22**

아직 처음부터 끝까지 자연스럽고 논리적인 순서도라고 보기는 어렵다. 재료의 역할을 설명하는 상자, 계속 작동하는 기반, 실제로 수행할 행동이 같은 실행선 위에 섞여 있다. 그 결과 어떤 기능은 너무 늦게 등장하고, 일부 분기에서는 필요한 확인을 거치지 않거나 이미 한 일을 다시 할 수 있게 읽힌다.

현재 원본의 도형 179개와 연결 232개를 읽고, 재료 정의와 대조했다. 게시된 PNG와 같은 SVG에서 만든 1100px 폭 화면 18장을 모두 확인했다. 아래는 **도식에 실제로 있는 연결 문제**와 **독자가 다르게 해석할 수 있는 표현 문제**를 구분한 결과다. 실행 중인 프로그램의 장애를 재현했다는 뜻은 아니다. 이번 작업에서는 검토 기록만 추가했다.

**위에서부터 확인한 구조·순서 문제**

1. **계속 쓰는 기반이 중간에 한 번 거치는 작업처럼 보인다.** — 역할·순서 혼동
   - 위치: `model_initial`, `model`, `control`, `isolation`, `monitor`, `tools`. [현재 설명](../../../전문가%20에이전트%20정의.md#환경-)
   - `AI 모델 → 정보·자료 이해`는 두 번 이해하는 것처럼 보인다. 검색·조회·질문은 이미 위에서 했는데, 도구 연결과 실행 제어는 한참 뒤에 나온다. 장애 감시도 실행 제어 뒤에서만 시작하는 모양이다.
   - 원문에서 모델·실행 제어·운영 감시는 계속 쓰는 기반이다. 기반의 적용 범위를 표시하고, 실행선에는 그때 하는 행동이 드러나게 해야 한다. 각 재료를 없애거나 이름을 바꾸라는 뜻은 아니다.

2. **새 요청과 기존 업무에 도착한 답변의 재개 위치가 구분되지 않는다.** — 분기 의미 불명확
   - 위치: `live → signal → context_initial`, 별도로 있는 `wait → identity`.
   - 실시간 대화에서 받은 모든 요청·답변은 처음 요청을 이해하는 길로 간다. 아래의 대기 중인 결과는 검증 지점으로 돌아간다. 같은 답변이 어느 길로 들어가야 하는지 알 수 없다.
   - 새 업무, 조건 변경, 기다리던 답변을 구분해 해당 업무의 필요한 지점으로 연결해야 한다. 조건이 달라졌을 때만 목표·계획을 다시 검토하는 편이 자연스럽다.

3. **초기 질문·검색·조회·시험에 적용되는 권한과 한도가 흐름에서 빠져 있다.** — 적용 범위 누락 · 우선 수정
   - 위치: `communicate0`, `search`, `now`, `capability0`가 첫 `guard`보다 앞에 있다.
   - 안전장치 설명은 정보를 주고받거나 실행하기 전에 확인한다고 되어 있다. 그러나 준비 단계의 외부 조회나 자료 요청에도 같은 기준이 적용되는지는 표시되지 않았다. 뒤쪽 안전장치를 통과하지 않고 이 행동들에 도달할 수 있다.
   - 처음부터 적용되는 공통 조건과 이번 업무를 조사하며 추가로 확인하는 규칙을 구별해야 한다. 준비 단계도 이미 정해진 권한·한도 안에서 진행한다는 범위를 보여 주면 된다. 모든 질문마다 새 승인 절차를 넣을 필요는 없다.

4. **선택해서 확인한 항목을 언제 다 모았다고 보는지 모호하다.** — 합류 조건 불명확
   - 위치: `search`의 선택 항목과 `evidence_use`의 지식·경험·기록 가지.
   - 필요한 항목만 고른다는 설명은 있다. 다만 각 항목의 결과와 항목을 거치지 않는 직행선이 같은 선으로 합쳐진다. 여러 항목을 골랐으면 모두 끝나야 하는지, 하나만 끝나도 되는지 드러나지 않는다. 특히 직행선의 `확인한 자료`는 생략 조건이 아니다.
   - `추가로 확인할 항목 없음`과 `고른 항목의 확인 완료`를 구분해야 한다. 위쪽 자료·규칙 두 가지에는 이미 완료 조건이 있으므로, 그 부분의 문제가 재발했다고 보지는 않았다.

5. **근거를 끝내 구할 수 없을 때의 다음 행동이 없다.** — 예외 경로 누락
   - 위치: `evidence_usable → evidence_repair → search`.
   - 상자에는 판단을 보류한다고 쓰였지만, 나가는 선은 다시 검색하는 것뿐이다. 자료가 존재하지 않거나 접근할 수 없는 경우에도 같은 길을 반복한다.
   - 추가 확보 가능, 답변 대기, 확보 불가를 구분하고, 확보 불가 시 해당 판단의 보류·범위 조정으로 연결해야 한다. 부족한 근거로 통과시키자는 뜻은 아니다.

6. **한국 법령의 위계 예가 모든 업무의 필수 조사 순서로 연결돼 있다.** — 설명과 실행선 불일치
   - 위치: `law → law_constitution → law_statute → law_decree → law_ministry`.
   - 위에는 국가·분야에 맞는 법을 확인한다고 쓰고, 아래에는 한국 중앙정부 법령의 예라고 썼다. 그런데 화살표는 모든 업무가 이 네 상자를 순서대로 통과하게 한다. 위계를 설명하는 관계와 실제 조사 절차가 섞였다.
   - 업무에 적용되는 법령을 찾는 경로와, 충돌할 때 참고할 위계 관계를 구분해야 한다. 한국에 한정된 예라는 적용 범위도 흐름에 반영해야 한다.

7. **시행일·경과조치 확인이 특정 충돌 상황에서만 필요한 것처럼 보인다.** — 확인 시점 불명확
   - 위치: `law_conflict → law_special → law_new`.
   - `law`의 본문에는 적용 시점을 확인한다고 되어 있다. 그러나 구체적인 시행일·경과조치 상자는 같은 효력의 법이 충돌하고 특별 규정이 없는 길에만 있다. 글과 상세 흐름의 범위가 다르다.
   - 법을 고르는 앞부분에서 대상 시점과 적용 조건을 확인하고, 충돌 분기에서는 이미 확인한 법 사이의 관계를 판단하도록 정리하는 것이 명확하다. 이는 도식 구성에 대한 판단이다. 부칙이 시행일과 적용례·경과조치를 다룬다는 점은 [법제처 설명](https://lawmaking.go.kr/lmKnlg/jdgStd/info?astSeq=16)에서 확인했다.

8. **구체적인 계획과 실행 대상이 정해지기 전에만 실행 위험을 검토한다.** — 필요한 검토 위치 누락
   - 위치: `risk → strategy → plan → progress → guard`.
   - 앞의 위험 확인은 방법을 비교하는 데 유용하다. 하지만 도구·대상·입력이 구체적으로 정해지는 것은 뒤의 작업 진행 단계다. 그 계획에서 새로 드러나는 위험을 확인하는 연결은 없고, 안전장치는 정해진 규칙·승인·한도와 대조한다고만 설명한다.
   - 구체적인 작업이 정해지거나 바뀌었을 때 해당 위험을 확인하도록 해야 한다. 계획 전 검토와 실행 직전 검토의 역할을 구별해야 한다.

9. **장애 복구 뒤 조건이 달라졌을 때의 재검토 길이 없다.** — 재개 조건 누락
   - 위치: `monitor → state → progress → control → guard`.
   - 저장한 진행 상태로 돌아오는 길은 있다. 하지만 중단된 동안 기한·자료·업무 조건이 바뀌었는지에 따라 계획이나 자료 확인으로 돌아가는 길은 없다.
   - 조건이 그대로면 이어 가고, 바뀌었다면 영향을 받은 판단부터 다시 검토하도록 해야 한다. 거래 상자에 있는 중복 실행 전 상태 확인까지 없다고 판정한 것은 아니다.

10. **사람이 직접 처리한 결과도 AI가 다시 실행하는 길로 간다.** — 내용과 복귀 경로 불일치 · 우선 수정
    - 위치: `handoff → identity0 → approval_valid → guard → tools`.
    - 사람에게 넘기기에는 승인·판단뿐 아니라 직접 수행도 포함돼 있다. 돌아오는 길은 승인 답변만 확인한 뒤 실행을 재개한다. 사람이 이미 완료한 작업의 결과를 검증하고 상태에 반영하는 길이 없다.
    - 승인 답변, 조건을 바꾸는 판단, 직접 처리한 결과를 나눠야 한다. 완료 결과는 결과 검증으로, 승인만 받은 경우는 해당 실행으로 연결해야 한다.

11. **이미 정한 작업을 다시 여섯 번 분류한다.** — 중복 판단·선택 의미 불명확
    - 위치: `progress`, `type0`부터 `type5`, `choose0`부터 `choose5`.
    - 위에서 구체적인 작업을 고른 뒤 아래에서 자료 정리인지, 계산인지, 제작인지 등을 다시 묻는다. 번역 파일 만들기처럼 여러 분류에 걸치는 일은 어디로 가야 하는지도 망설이게 된다. 아무 항목에도 맞지 않으면 같은 준비 과정으로 되돌아갈 뿐이다.
    - 한 번에 선택한 작업 하나를 실행한다는 단위를 분명히 하고, 실제로 정해진 작업으로 바로 연결하는 구조가 필요하다. 설계와 제작을 반드시 한 번에 모두 실행해야 한다는 문제로 보지는 않았다.

12. **게시·배포나 중요한 설명을 하기 전에 내용을 검증했다는 조건이 없다.** — 선행 확인 누락 · 우선 수정
    - 위치: `tools → … → publish → out4 → identity → counter → verify`; 대화도 `talk → out3 → identity` 순서다.
    - 실제 외부 행동을 한 뒤 처리 결과를 확인하는 것은 필요하다. 그러나 공개할 내용이나 중요한 결론 자체를 미리 확인하는 길이 보장되지 않는다. 게시·배포를 첫 작업으로 골라도 공통 내용 검증에 앞서 공개할 수 있게 그려져 있다.
    - `내용 준비·검증 → 허용된 외부 행동 → 실제 반영 확인`을 구분해야 한다. 승인된 버전이라는 문구만으로 내용 검증까지 마쳤다고 보기는 어렵다. 단순 확인 질문마다 완성된 납품 절차를 거치게 만들 필요는 없다.

13. **검증 불가의 원인을 전부 답변 대기로 처리하고, 기한 초과 출구도 없다.** — 분기 누락 · 우선 수정
    - 위치: `vdecision → wait → identity`.
    - 확인하지 못한 이유는 답변 미도착뿐 아니라 자료 충돌, 검사 실패, 확인 방법 부족일 수도 있다. 현재는 모두 답을 기다리는 상자로 간다. 본문은 기한이 되면 이어 간다고 하지만 유일한 복귀선은 `새 결과 도착`이다.
    - 원인에 맞는 보완·재검사·사람 확인으로 보내야 한다. 답변 대기는 답변 도착과 기한 초과를 나누고, 기한 초과 시 정해 둔 후속 조치로 연결해야 한다.

14. **다음 작업과 작은 수정도 긴 준비 과정으로 되돌아간다.** — 불필요한 전체 반복
    - 위치: `more / vdecision / repair → context2 → checks_start → … → strategy → plan`.
    - 오탈자 수정이나 계획된 다음 작업도 자료·규칙 확인, 목표 검토, 전략 선택, 능력 확인을 다시 통과한다. `바뀐 내용만 재확인`이라는 본문이 있지만, 어떤 단계는 그대로 유지하는지가 화살표에는 없다.
    - 남은 계획대로 진행, 해당 결과만 수정, 조건 변경으로 재계획을 구분해야 한다. 필요한 검사를 생략하지 않으면서 실제로 영향을 받은 단계로 돌아가게 해야 한다.

15. **전달 승인자가 수정 조건을 주면 내용 재검사를 건너뛸 수 있다.** — 변경 후 재검증 경로 누락 · 우선 수정
    - 위치: `delivery_approval → delivery_guard → delivery_allowed → delivery`.
    - 사람에게 넘기기 설명에 `수정 조건`이 포함돼 있다. 그런데 답변 뒤에는 권한·파일·공개 범위를 검사하는 안전장치로만 돌아간다. 내용을 고치거나 새 조건에 맞게 품질을 다시 검사하는 분기가 없다.
    - 변경 없이 승인한 경우와 수정·범위 변경을 요구한 경우를 나눠야 한다. 수정 요구는 관련 작업과 검증으로 돌아가야 한다.

16. **일하는 과정 평가는 인수가 끝난 뒤에만 나온다.** — 재료의 사용 시점 일부 누락
    - 위치: `receipt → record_read → process_eval`.
    - 마지막 회고 위치 자체는 자연스럽다. 다만 원문은 각 단계가 끝났을 때도 필요한 절차·권한·방법을 평가한다고 정의한다. 현재 도식에는 진행 중 중요한 단계의 과정 평가가 보이지 않는다.
    - 결과만 맞고 과정에서 필수 절차를 빠뜨린 상황을 언제 발견하고 되돌리는지 표시해야 한다. 모든 사소한 작업마다 회고 상자를 반복할 필요는 없다.

17. **나중에 성과를 확인하는 가지가 현재 업무의 완료와 어떤 관계인지 모호하다.** — 후속 처리 범위 불명확
    - 위치: `outcome → learnneed`, `outcome → effect_wait → outcome`.
    - 두 선이 함께 진행하는지, 하나를 고르는지 설명이 부족하다. 끝 도형에서는 남은 후속 일을 계속 챙긴다고 하지만, 처음 분기하는 자리에서 현재 업무는 마쳐도 되는지 알기 어렵다.
    - 후속 확인을 등록한 뒤 현재 업무 정리는 계속 진행한다는 관계를 표시하고, 나중의 신호가 그 후속 확인을 재개하게 해야 한다.

18. **이미 인수된 업무를 끝내려면 능력 개선까지 해야 하는 길이 있다.** — 서로 다른 작업의 완료 조건 혼합
    - 위치: `improveneed → testenv → improve → capability → improve_apply → memory2 → finish`.
    - 개선 필요를 고르면 시험에 한 번 들어가기 전에는 이번 업무를 닫고 개선을 후속 과제로 남기는 길이 없다. 시험에 실패한 뒤에야 보류를 선택할 수 있다. 이미 전달·인수된 업무의 완료가 다음 업무를 위한 개선에 종속된다.
    - 이번 업무 정리와 개선 과제 실행을 구별해야 한다. 기존 결과를 바로잡기 위한 필수 수정과 미래 업무를 위한 능력 개선도 서로 다른 일이다.

19. **개선 시험 통과가 곧 실제 적용 허가처럼 연결된다.** — 적용 조건 누락
    - 위치: `passed → improve_apply`.
    - 시험한 범위·버전만 적용한다는 조건은 생겼다. 그러나 실제 도구·지식·방법을 바꿔도 되는 권한과 적용 조건을 확인하는 공통 경로는 연결되지 않았다.
    - 시험 통과와 실제 적용 가능 여부를 구별해야 한다. 이미 승인된 범위라면 바로 적용할 수 있되, 변경에 적용되는 공통 규칙이 이 가지에도 유지된다는 점이 보여야 한다.

**화면에서 읽기를 방해하는 부분**

20. **규칙 구간과 자료 구간의 길이 차이, 긴 복귀선 때문에 맥락을 놓치기 쉽다.**

    - 정상적인 다음 작업도 먼 위쪽으로 돌아가므로 한 화면에서 전후 관계를 읽기 어렵다. 실무 분류 역시 이미 고른 작업을 여러 화면에 걸쳐 다시 찾게 한다.
    - 순서 문제를 먼저 고친 뒤, 관련 검사·보완·복귀를 가까이 두고 큰 단계가 보이게 정리해야 한다. 도형을 작게 줄이거나 그림을 임의로 여러 장으로 나눌 문제는 아니다.

    - 문서의 PNG 바로 아래에 Mermaid 코드 블록이 있어, Mermaid 지원 뷰어에서는 같은 흐름이 다시 표시된다.
