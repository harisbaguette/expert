# API 모델 기본 능력과 재료 55개 대조

검토일: 2026-09-11. 대상은 현재 작업 폴더의 [재료 55개](../materials.md)이며, [실행 계약](../runtime.md), [평가 규약](../evaluation.md), [목표 문서](../../전문가%20에이전트%20정의.md)를 함께 읽었다. ChatGPT·Claude 등의 소비자용 앱 기능은 판단 근거에 포함하지 않았다.

**별도 마련할 것을 줄일 수 있다. 권고는 독립 항목 2개 통합, 11개 구축 범위 축소, 42개 현 책임 유지다.** 다만 이는 문서와 API 공급 범위를 대조한 설계 권고다. 두 항목의 모든 책임이 모든 모델에 완성품으로 들어 있다는 뜻이나, 실제 직무 시험에서 삭제 후 성능이 입증됐다는 뜻은 아니다.

현재 문서는 이미 재료를 ‘기능과 책임’의 목록으로 정의하고, 실행 계약에서 문제 정의·해석·방법 선택·재계획을 모델에 맡긴다. 따라서 55개를 각각 새 엔진이나 프롬프트 묶음으로 만들라는 요구는 아니다. 보완할 점은 **각 재료에서 모델로 충족하는 부분과 추가로 확보할 부분이 한 항목에 섞여 있다는 것**이다. 이를 구분하면 재료 번호를 줄이기 전에도 실제 준비량을 줄일 수 있다.

| 권고 | 개수 | 해당 재료 | 의미 |
|---|---:|---|---|
| 통합 | 2 | M34·M48 | 범용 사고는 M01에 맡기고, 고유 기준·증거·실행 책임을 기존 재료에 배정하여 독립 항목을 통합 |
| 축소 | 11 | M07·M21·M22·M23·M26·M30·M35·M38·M42·M43·M44 | 일반 능력을 따로 만드는 작업을 생략하고, 부족한 지식·고유 입력·실행·검증만 확보 |
| 유지 | 42 | 위 13개 외 전부 | 이 검토 기준으로 책임을 없앨 근거가 부족함. 적용되는 업무에서만 갖추며 기존 서비스·라이브러리로 충족 가능 |

‘유지’는 42개 자체 개발이나 모든 업무에서의 활성화를 뜻하지 않는다. M01은 모델 API를 사용하면 되고, 다른 항목도 설정·입력 자료·기성 서비스·공통 코드로 충족할 수 있다. ‘통합’도 책임과 평가를 없애는 처리가 아니다.

**비교 기준**

OpenAI·Anthropic·Google Gemini·DeepSeek의 공식 API 문서를 대조했다. 특정 최상위 모델에만 있는 기능을 공통 전제로 삼지 않았으며, 시장의 모든 API 모델을 실험하거나 지원율을 계량한 조사는 아니다. 범용 지시 이행 모델의 일반적인 텍스트 이해·생성·추론을 출발점으로 삼되, 지원 입력·도구 호출·구조화 출력·추론 수준은 선택한 모델에서 확인해야 한다. 임베딩 전용·음성 전용·구형 모델까지 동일 능력을 가진다고 가정하지 않는다.

| 제공 층위 | 예 | 이번 판단 |
|---|---|---|
| 모델의 기본 능력 | 주어진 글 이해·요약·번역·분류·초안 작성, 일반 지식 활용, 대안 비교·계획·오류 가설 생성 | 우선 모델에 맡긴다. 전문 수준의 정확성과 장기 수행 신뢰성은 별도 평가 |
| 모델/API의 호출 형식 | 도구 선택·인자 생성, 지원 스키마에 맞는 출력 | 지원되는 형식을 재사용한다. 도구 정의·실행 구현·업무상 유효성 검사는 추가로 필요 |
| 공급자의 선택 기능 | 서버 검색·코드 실행, 대화 저장·압축, 관리형 에이전트 | 요구를 충족하면 직접 구축을 대체할 수 있다. 선택 API·설정·지원 모델의 기능으로 기록 |
| 해당 업무의 정보와 실행 | 고객 자료, 목표·권한·한도, 원본 파일, 실제 시스템 작업, 지속 기록·실측·평가 기준 | 모델 기본 능력으로 생겨나지 않으므로 필요한 만큼 확보 |

도구 호출과 실행의 구분은 네 공급자에서 공통으로 확인된다. OpenAI·Gemini·DeepSeek의 사용자 정의 함수는 모델이 호출 내용과 인자를 만들고 애플리케이션이 실행한다. Anthropic도 사용자 측 도구와 공급자 측 도구를 구분한다. 지원 기능을 연결하면 실행 코드를 줄일 수 있지만, 함수 호출 가능 여부만으로 해당 업무 시스템까지 연결된 것은 아니다. [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), [Gemini function calling](https://ai.google.dev/gemini-api/docs/function-calling), [DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/), [Claude tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview).

API에 저장 기능이 전혀 없다는 전제도 틀리다. OpenAI의 Conversations API는 대화 항목의 지속 저장을 제공한다. 반면 Claude의 Memory tool은 애플리케이션이 저장 작업을 수행하는 방식이다. 따라서 저장·기억의 직접 구현 여부는 공급 기능에 따라 달라지며, 고객 구분·정정·약속의 유효성·외부 행동 복원 책임까지 자동 충족되는지는 따로 확인해야 한다. [OpenAI conversation state](https://developers.openai.com/api/docs/guides/conversation-state), [Claude memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool).

**우선 통합할 두 항목**

M34 ‘판단 규칙’에서 대안을 비교하고 반증을 고려하며 다음 행동을 선택하는 범용 사고는 M01의 역할과 겹친다. 직무마다 이런 사고법을 별도 규칙집으로 마련하는 것을 기본 요구로 삼을 이유는 부족하다. 일반 판단은 모델에 맡기고, 모델이 알 수 없는 목적·허용 손실·고유 정책과 실제로 도움이 된 전문 지침만 제공하는 편이 낫다. OpenAI는 추론 모델에 간결한 지시와 명확한 목표·제약을 주고, 사고 과정을 일일이 지시하거나 예제를 처음부터 추가하기보다 필요에 따라 보완하도록 권한다. 이 지침은 추론 모델에 관한 것이며 모든 소형 모델의 성능 보장은 아니다. [OpenAI reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices).

M48 ‘실패 원인 분석’에서도 관측된 오류를 읽고 여러 원인 가설과 수정안을 만드는 일은 M01로 처리할 수 있다. 추가로 필요한 것은 실제 로그·재현 환경·대조 결과·수정 후 확인이다. 이 부분은 기존 M42·M47·M50과 연결하면 된다. Anthropic의 에이전트 설계 자료도 모델의 추론·계획·오류 대응을 사용하면서 환경의 실제 피드백과 시험을 연결하는 구조를 설명한다. 여기서 M48 통합은 그 자료와 현 재료 정의를 대조한 검토자의 설계 판단이다. [Anthropic Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents).

| 통합 대상 | 책임을 남길 위치 |
|---|---|
| M34의 대안 비교·반증·전략 판단 | M01의 모델 능력 및 M49의 직무별 평가 |
| M34의 직무 고유 판단법·숙련 사례 | M21·M22의 필요한 보완 지식 |
| M34의 고유 정책·손실 제약·목표 우선순위 | M27–M29·M33·M36의 실제 적용 조건 |
| M34의 조건부 전략·전환 신호·선택 근거 | M35의 계획, M25의 현재 상태, M47의 결정 기록 |
| M48의 원인 가설·수정안 도출 | M01의 분석 능력 |
| M48의 실제 원천 대조·재현·영향 확인 | M42의 진단·수정·재검증과 필요한 M10·M11 환경 |
| M48의 오류 분류·원인 증거·수정 담당 기록 | M47의 기록 |
| M48의 다음 업무에 반영할 개선 | M50의 변경 관리와 M49의 회귀 평가 |

이렇게 책임을 옮기는 안을 채택하면 독립 목록은 55개에서 53개가 된다. 책임 목록으로 55개를 유지하고 두 항목의 충족 방식을 ‘모델과 기존 검증·개선 기능’으로 적어도 구현량은 동일하게 줄일 수 있다. 번호 감소 자체가 비용 절감의 근거는 아니다.

**준비량이 크게 줄어드는 부분**

M21 ‘업무 지식’은 직업별 기본 교과서를 모두 다시 만드는 방식으로 시작할 필요가 없다. 모델의 기존 지식을 활용해 평가하고, 최신 사항·비공개 방법·특수 장비·오답이 확인된 영역에 한해 보완한다. 정확한 원문 근거가 요구되는 업무의 M12–M18은 그대로 필요하다. ‘모델이 그 개념을 안다’와 ‘이번 판단에 적용할 공식 판본과 출처가 확보됐다’는 별개다.

M22 ‘감각·사례·암묵지’도 모든 직무에 대해 먼저 전문가 면담과 사례집을 완성해야 하는 전제는 과하다. 이미 충분히 수행하는 부분은 그대로 쓰고, 목표 수준에 못 미친 판단·예외 대응·표현에 효과가 있는 실제 사례만 보충한다. 모델이 생성한 그럴듯한 사례를 실제 숙련자의 경험으로 표시해서는 안 된다. 직무의 숙련도를 평가하는 책임은 유지하되, 외부 사례 수집은 부족함이나 고유 요구가 확인될 때 활성화하는 편이 타당하다.

M35의 일반 계획 수립, M38의 질문·설명·응답 생성, M42–M44의 논리 점검·반례 생성·누락 후보 탐색도 모델을 먼저 활용한다. 추가 준비는 정해진 업무 순서·설계 계약·상대 정보·협상 권한·실제 검사 도구·독립 증거에 집중한다. 같은 내용을 ‘계획용’, ‘응대용’, ‘반박용’ 규칙집으로 각각 크게 만드는 것은 기본 요구에서 제외할 수 있다. 간단한 구성부터 시작해 필요할 때 복잡도를 늘리라는 공급자 설계 지침과도 맞는다. [Anthropic Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents).

M26은 주의해서 줄여야 한다. 특정 공급자의 기본 제한을 길게 되풀이하는 문구는 중복일 수 있지만, 운영자의 공통 원칙과 다른 공급자에서도 지켜야 할 기준까지 삭제할 수는 없다. ‘여러 모델이 비슷한 안전 응답을 한다’는 이유로 M31의 실제 권한 검사와 M32의 정보·실행 경계를 생략하는 것도 타당하지 않다.

**55개 전수 판정**

아래의 ‘모델에 맡길 부분’은 능력 활용 방안이며 무오류 보장이 아니다. ‘추가로 확보할 것’도 해당 업무에 필요한 범위에 한한다. 범용 모델 기본 능력으로 삭제할 수 있는지에 초점을 맞췄으며, 재료끼리의 모든 중복을 없애는 전면 구조 개편은 다루지 않았다.

| ID·재료 | 판정 | 모델에 맡길 부분 | 추가로 확보하거나 기존 재료에 남길 것 |
|---|---|---|---|
| M01 모델 | 유지 | 이해·생성·추론·계획·도구 선택의 중심 | API 연결·설정·모델별 지원 범위와 실제 직무 평가. 모델 자체를 새로 개발할 필요 없음 |
| M02 실행 순환 | 유지 | 다음 행동과 재시도·중단 후보 판단 | 호출·실행·결과 반환, 취소·오류·예산 처리. SDK·관리형 서비스 재사용 가능 |
| M03 저장·이어받기 | 유지 | 복원한 상태를 이해하고 후속 판단 | 저장점·실행 기록·외부 결과 대사·중복 방지. 대화 저장만으로 모두 충족되지 않음 |
| M04 나눠 맡기기 | 유지 | 과제 분해·담당 선택·결과 통합 | 실제 실행 주체·소유권·결과 회수·공유 예산·정보 경계 |
| M05 작업창 | 유지 | 주어진 맥락 이해·요약·관련성 판단 | 무엇을 입력할지, 한도·참조·필수 상태 보존. 지원 API의 압축·캐시 재사용 가능 |

| M08 실시간 통로 | 유지 | 주어진 입력에 대한 즉시 응답 생성 | 지원 음성/영상 API·통신, 지연·끼어들기·복구·깊은 판단 연결 |
| M09 산출물 제작·편집 | 유지 | 내용·코드·명세 생성, 지원 모델의 미디어 생성 | 파일 저장·프로그램 편집·객체 보존·변환·패키징·실제 열기 확인 |
| M10 도구·전문 작업 환경 | 유지 | 사용할 도구·인자 선택과 결과 해석 | 실제 API·SDK·CLI·GUI·장비, 계정·라이선스·실행 환경 |

모델이 그럴듯한 분석·JSON·코드를 생성해도 실제 검증 결과가 확보된 것은 아니다. 지원 스키마를 강제하는 기능을 쓸 수 있더라도 값의 사실성·실제 권한·업무 완료는 별도로 확인한다. OpenAI 역시 구조화 출력에서 내용상 오류가 남을 수 있음을 설명한다. [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

**구축할 때 적용할 기준**

1. 해당 직무의 목표·합격 기준·실제 자료·필수 도구를 마련하고, 간결한 업무 지시로 모델의 기본 성능을 먼저 측정한다. 지식집·사고법·예제·고정 절차를 전부 선구축하지 않는다.
2. 부족한 부분이 정보 부재인지, 모델 능력인지, 도구·상태·권한·실행 결함인지 구분한다. 원인에 맞는 자료·모델·코드·지침만 보완한다.
3. 추가한 지식·사례·프롬프트·검사 단계가 보호된 새 과제에서 품질·누락·비용·지연에 주는 효과를 비교한다. 효과가 입증되지 않은 범용 지시는 기본 구성에서 제외하는 쪽으로 판단한다.
4. 저장·권한·외부 실행·실측·독립 평가처럼 모델의 기본 사고로 충족되지 않는 부분은 실제 구현 또는 서비스 연결로 확보한다. 공급자가 제공하는 경우 지원 범위와 동작을 확인해 재사용한다.
5. 재료의 ‘상시·단계별·조건부’와 별개로 **모델 활용 / 고유 자료·설정 / API·기성 서비스 / 직접 구현** 중 무엇으로 충족하는지 표시한다. 한 항목에 여러 방식이 함께 들어갈 수 있다. 모델이 충족한 부분에 별도 제작 일을 배정하지 않는다.
